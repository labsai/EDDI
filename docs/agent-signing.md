# Agent Signing Keys

An agent can sign what it writes: its messages in group conversations and its own audit entries. Another agent can be set to trust only messages that verify. This page covers the keys, what signing and verifying change, and how to read the failures they cause. The cryptography itself — Ed25519, the envelope format, the post-quantum outlook — is in [Cryptography](cryptography.md) and [Architecture → Cryptographic Agent Identity](architecture.md#cryptographic-agent-identity).

## Generating and revoking keys

Keys are generated by an administrator with the `eddi-admin` role: **Generate signing key** in the agent's *Security & Identity* section of the Manager, or

```
POST /agentstore/agents/{id}/signing-keys?version={current}
```

A leaked or retired key is revoked the same way — **Revoke** next to the key, or

```
POST /agentstore/agents/{id}/signing-keys/{keyVersion}/revoke?version={current}
```

The private key stays in the [secrets vault](secrets-vault.md). The public key is added to the agent's `identity.keys` as a new agent version, and the agent signs its group-conversation messages with the newest key at once.

- **Key version 0** is the legacy `identity.publicKey`, which is removed. Generating a key keeps it, and peers trust it for v0 signatures until it is revoked.
- **Revoking** deletes the private half from the vault, best effort. It does not stop anyone holding another copy from signing, and a node that already loaded the key can keep signing audit entries with it for up to 60 seconds (longer if the vault delete failed); those entries verify as `AGENT_KEY_REVOKED`. Once no node can load it, revoking the newest key stops the agent signing until a new one is generated.
- **A revoked key is trusted for nothing**, whenever it signed, audit entries included. A peer that verifies treats such a message as not verifying.
- **`identity` is engine-owned.** An agent save — through the Manager, the Platform Operator, an import or a sync — keeps the stored identity whatever the body says, so editing `identity.keys` or `validUntilMs` does nothing. Only the two endpoints above change keys.

Neither the Platform Operator nor any MCP tool can generate or revoke a key, on purpose: whoever mints or retires an agent's key decides what signs as that agent.

## Turning signing on

`security.signInterAgentMessages` on the agent turns signing on. A save with it on is refused with `400` unless the newest key is well-formed, not revoked, inside its validity window, and its private half is in the vault (`503` if the vault cannot be asked). A new agent cannot be created with it on. That `400` stops **every** save of such an agent — workflow repoints included — until it has a usable key or the flag is off.

`security.requirePeerVerification` needs no key of the agent's own.

A ZIP import or a sync never carries signing onto an agent that cannot sign: it turns the flag off and says so — the `X-Agent-Signing-Turned-Off` header on an import, `warnings` in a sync result. The Manager's import dialog and Sync page show both.

## Signed audit entries

An agent's own audit entries are signed by the agent version a conversation runs, so they stay unsigned until a version that declares the key and has signing on is deployed.

An entry's `agentSignature` is `v<keyVersion>:<signature>`, or plain Base64 on entries written by 6.7.0 or earlier, which is checked against the legacy `identity.publicKey`. The [audit verify endpoints](audit-ledger.md#agent-signatures) report:

| Code | Counted in | Meaning |
| --- | --- | --- |
| `AGENT_SIGNATURE_INVALID` | `invalid` | The signature does not verify: **tampering** |
| `AGENT_SIGNATURE_MISSING` | `agentSignatureUnproven` | No signature where the version would have signed |
| `AGENT_KEY_REVOKED` | `agentSignatureUnproven` | Signed with a key revoked since |
| `AGENT_KEY_UNAVAILABLE` | `agentSignatureUnproven` | The agent was permanently deleted, or (legacy entries) the version declares no `identity.publicKey` |

The three "unproven" codes mean the content is intact: they are not tampering.

## Agents that verify their peers

An agent with `requirePeerVerification` sees every message another agent wrote that does not verify — unsigned, edited, retyped, copied from another discussion or round, or signed with a revoked key or outside its key's validity window — as `[withheld: ...]`, in every prompt it is given: role turns, task-force prompts and `listGroupTasks` included.

- Its own messages are checked the same way when it signs. Only a verifying agent that does not sign sees its own unchecked.
- A message no agent wrote is shown as "User", "System" or the name followed by "(not an agent, unverified)" — "Anonymous (not an agent, unverified)" under `ANONYMOUS` scope.
- A synthesis under the engine's or the user's name is withheld, and the agent is never given the stored window summary.
- A message from an agent that has since been deleted is withheld too.
- Revoking a key or deleting an agent hides its messages from every prompt built **afterwards**, not from what a member was already shown, which stays in that member's own conversation history. To keep a leaked key's text away from the members, start a new discussion.
- It gets no artifact tools (artifacts are not signed).
- In every conversation, 1:1 chats included, it neither loads nor recalls a group- or global-visible user memory whose value another agent last wrote. Its own memories, the user's and its team's lessons are shown. A `longTerm` property it sets for a global key is written like any agent's, replacing another agent's value and making it the writer.

### Tasks and handoffs

- A task another member filed with its task tools, or another team's agent handed off (`handoff_to_team` with `AUTO` intake), is shown to it only while that agent signs verifiably.
- A team with such a member files an `AUTO` handoff from an agent that does not sign verifiably to its intake inbox, for a person to accept.
- Its cadence does not pull a backlog task whose agent stopped signing: the task waits on the backlog as `PENDING`, and a cadence fire that leaves nothing to run records why in the schedule's fire history (the Error column of a `COMPLETED` fire on the Schedules page), naming the agent. To free it, give that agent a signing key again (or turn its signing back on), or delete the task and file it again.
- A task of its own whose text does not verify for it fails without it being asked, with "Its task text could not be verified, and this member requires peer verification".
- As a verifier it judges only the tasks it may read; the rest stay `COMPLETED` with the note "task(s) not verified: their text or result could not be verified".
- A handoff an `onDecision` rule files, or one a person accepted from the inbox, reaches it as configured task text, and the cadence question quotes the tasks it pulls. Recommend `REVIEW` handoff intake for a team whose members verify.
- An agent `create_sub_agent` makes has no signing key, so its contributions are withheld from verifying readers. In such a group, leave `dynamicAgents.allowCreation` off and recruit agents that have keys.
- A nested group's question is filtered when any of its agents (a member, its moderator or facilitator) verifies.

### Group records

Once any member, the moderator or an enabled facilitator has `requirePeerVerification` on, the group's own records — vote options and ballots, the negotiation table, the `SERVICE` convergence judge, retrospective lessons, a standing team's cadence feedback — count only entries that verify for **every** reader, with no reader's own entries exempt. So:

- an unsigned synthesis, or a verifying moderator that does not sign, makes a vote end with "The vote could not run: only 0 option(s) were available";
- a facilitator's `CALL_VOTE` is refused unless the facilitator signs verifiably.

In such a group every agent that writes to the discussion should sign — a moderator, synthesizer or facilitator that is not a member included — and an agent that verifies should sign too.

Member display names must be unique within the group. An agent member may not be named "Moderator" while the moderator is not a member, nor "Facilitator" while an enabled facilitator is another agent; each such save is refused with `400`.

## Troubleshooting

| Symptom | Usual cause |
| --- | --- |
| A save of the agent fails with `400` after signing was switched on | No usable key: generate one, or turn `signInterAgentMessages` off |
| An imported or synced agent no longer signs | The import or sync turned signing off because the agent had no usable key (`X-Agent-Signing-Turned-Off`, sync `warnings`) |
| A member sees `[withheld: ...]` | The author does not sign verifiably: no key, signing off, a revoked key, or an edited message |
| "The vote could not run: only 0 option(s) were available" | A verifying member, moderator or facilitator, and a writer that does not sign |
| A backlog task stays `PENDING` on a standing team | Its agent stopped signing; the schedule's fire history names it |
| Audit verify reports `AGENT_SIGNATURE_INVALID` | Tampering — the entry's content does not match its signature |
