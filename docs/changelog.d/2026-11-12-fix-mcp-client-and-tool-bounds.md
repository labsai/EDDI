## 🔒 fix(mcp): bound MCP discovery and tool contributions; govern rule-triggered MCP results; /v1 and oversight hardening (2026-11-12)

**Repo:** EDDI (`fix/mcp-client-and-tool-bounds`)

### What changed and why

A remote MCP server is untrusted, and an editor can point the `discover-tools` probe at any URL. Eight findings from the security review:

1. **Unbounded `tools/list` pagination.** langchain4j pages a listing while the server returns a cursor, with only a per-request timeout; a server that always returns one held the thread and filled the heap before `ToolSchemaGovernor` saw anything. `BoundedListingMcpTransport` wraps every client's transport and fails the next request once one listing passes `eddi.mcp.list.max-pages` (20), `eddi.mcp.list.max-items` (2,000) or `eddi.mcp.list.deadline-ms` (30 s). Counted per thread and list method; a request without a cursor starts a new listing. The client is then dropped. Discovery now builds its `McpToolProvider` with `failIfOneServerFails(true)`: with it off, a failed listing came back as an empty result and was cached as "no tools".
2. **MCP clients never evicted.** The size and idle bound of the client cache is delivered by PR #1401 (`eddi.mcp.client-cache.max-size`, `eddi.mcp.client-cache.expire-after-access-ms`), not here; this branch leaves `clientCache` as it was. What it adds: clients are built with `autoHealthCheck(false)`, so no client holds a scheduler thread of its own; the `discover-tools` probe uses the new `probeTools`, which builds a client, lists and closes it — the client never enters the cache and its tool list is not cached; and a client whose listing hit a bound is removed from the cache and closed.
3. **Tool governance counted schema bytes only.** The per-server budget now charges each tool's name and description too; a server contributes at most `eddi.mcp.tools.max-per-server` tools (128) to an agent, counted in `McpToolsProvider` after that agent's `toolsWhitelist`/`toolsBlacklist` — the discovered list is cached per server and shared by every agent, so capping it there would have hidden a whitelisted tool past position 128 on a large server (the cached list itself is bounded by `eddi.mcp.list.max-items` and the name and size rules); a tool name outside `^[A-Za-z0-9_.-]{1,64}$` (checked by a character walk) is dropped with a sanitized, abbreviated WARN. New metric outcome `dropped_invalid_name`; the count cap logs a WARN naming the server and how many tools it dropped.
4. **No default cap on tool results.** `ToolResponseTruncator` treats a missing `toolResponseLimits` as the built-in defaults (50,000 chars, `headTail`), and `ToolLoopRunner` reserves the provenance envelope's room against that default as it does for a configured limit. `defaultMaxChars: 0` (or `0` per tool) still disables. No deployment-wide default property was added: the limit is per LLM task, and a second source for it would collide with the truncator rework in flight.
5. **Remote strings and credential URLs logged raw** in `McpToolsProvider`, `ToolSourceRegistry` and `McpCallsTask`: tool names through `LogSanitizer.sanitize`, server URLs through `UriRedactor.redactUri`.
6. **Rule-triggered MCP results skipped result governance.** `McpCallsTask` redacts directive-shaped spans (`RemoteTextGovernor.redactResultDirectives`, the LLM path's result pattern) before the result is parsed and stored, over the whole result and before the size cap. Not wrapped in a provenance envelope: the stored value is what designers template (`{memory.current.mcpCalls…}`), often a parsed JSON object, and an envelope would change its shape; the redaction never touches a quote or backslash, so JSON stays JSON. Switch: `eddi.mcpcalls.result-screening.enabled` (default `true`). httpcall results stored by `ApiCallExecutor` get no screening either; they are out of scope here.
7. **/v1 adapter.** An OIDC principal whose name equals `eddi.openai-compat.default-user` is refused (it would own every anonymous conversation), and `openai-anonymous` joins `ReservedPrincipals.NAMES`. A client `system` message over `eddi.conversations.max-input-chars` is refused with `400 input_too_large`.
8. **Agent-originated oversight changes.** `AgentCallOversightGuard` refuses (403) a `PUT /agentstore/agents/{id}` carrying `X-EDDI-Agent-Call` that changes the stored `hitlConfig.oversight`, using `OversightWriteGuard`'s own comparison. On main no MCP tool writes an existing agent's `hitlConfig` (`update_agent` patches the descriptor; `update_resource` has no agent type), so the REST store is the path that needed it; the check sits in the store method, so an in-process caller acting for a marked request is covered too. Its twins are checked up front as well, before any workflow or extension is written: a merge import (`RestImportService.requireNoAgentOriginatedOversightChange`, for an archive agent that matches an existing one) and an upgrade/sync (`UpgradeExecutor.requireNoAgentOriginatedOversightChange`, for an agent diff that is UPDATE or CONFLICT). Both fail the operation with 403.

### Upgrade note

Agents whose LLM tasks set **no** `toolResponseLimits` used to receive every tool result whole; they now get at most 50,000 characters per result (`headTail`: start and end kept, the middle replaced by a note). An agent that needs larger results sets `toolResponseLimits.defaultMaxChars` (or `perToolLimits`) on its task; `0` turns the cap off. See [langchain.md](../langchain.md#tool-response-limits).

### Design decisions

- The listing bound wraps the transport outside `createTransport`, so tests that read the concrete StreamableHttp transport back are unaffected, and every default method of `McpTransport` is delegated explicitly.
- New configuration is field-injected with initialisers equal to the defaults, so directly constructed instances keep their constructors.
