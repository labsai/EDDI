## ✨ feat(workforce): sidebar of conversations, Home, the chat in the URL; the widget follows rawHtml (2026-11-05)

**Repo:** EDDI (`feat/workforce-sidebar-home`, stacked on `refactor/manager-chat-on-conversation` with #1273 and #1282 merged in)

The frontend half of phase 4 of the frontend unification plan (`planning/frontend-unification-plan.md`, T1.1, T1.2, T1.4 and T1.15; B1/B2/B4; decisions D7 and D9), for every Workforce role, end users first.

### What changed and why

- **Sidebar (T1.1, T1.2).** [`session-list.tsx`](../../ui/manager/src/components/workforce/session-list.tsx) lists the signed-in person's chats and team sessions in the Workforce sidebar: Pinned, Today, Yesterday, Previous 7 days, Previous 30 days, then one group per month ([`workforce-sessions.ts`](../../ui/manager/src/lib/workforce-sessions.ts), local calendar days). A chat shows its B2 `title`, or the agent's name and the date before it has one; a team session shows its question. Chats are renamed inline (Enter saves, Esc cancels, one request even though the field blurs as it closes), pinned and unpinned through `PATCH /conversationstore/conversations/{id}`, and deleted through the owner `DELETE` after a confirmation; team sessions can only be deleted (the backend keeps no title or pin for them). Every write updates the TanStack cache first and puts it back when the server refuses ([`use-workforce-sessions.ts`](../../ui/manager/src/hooks/use-workforce-sessions.ts)). Reads are the owner-scoped `GET /conversationstore/conversations` and `GET /groups/{id}/conversations` for the teams the person can see (catalog or store by role) — nothing an `eddi-user` is refused. Two details: an admin's listing holds every user's conversations, so it is narrowed to their own by the recorded owner; and the conversations members hold inside a team session (owned by the person who started it) are left out of the chats via `memberConversationIds`.
- **Home (T1.4).** [`workforce-home.tsx`](../../ui/manager/src/components/workforce/workforce-home.tsx): a composer first with an agent picker (the agent of the most recent chat, else the first listed), the picked agent's review notice and its `appearance.starters` as chips, then the five most recent conversations, then the catalog. Agent cards show the B4 display name, avatar (initials on the accent colour when there is none or it fails to load) and accent colour. Sending, or a starter, opens a new chat with the text as its first message; the text travels in **router state** ([`workforce-chat-start.ts`](../../ui/manager/src/lib/workforce-chat-start.ts)), never in the URL, so a link still only preselects an agent (the chat's deep-link rule). Authors get the composer and the recent list above their dashboard.
- **Catalog appearance (backend).** `IRestCatalog.CatalogAgent` gains `appearance` and `conversationControls`, built with `AppearanceProfile.of` / `ControlsProfile.of` from the configuration `CatalogService` already reads for the deployed version — so a card needs no profile call. A six-argument constructor keeps the old shape (no appearance, default controls). [`CatalogServiceTest`](../../src/test/java/ai/labs/eddi/engine/catalog/CatalogServiceTest.java) covers both; [`catalog.md`](../catalog.md) shows the new fields. No new endpoint, so `openapi-operations.json` is unchanged.
- **T1.15 — the conversation in the URL.** `ChatPanel urlSync` (Workforce only) keeps `?agentId=…&conversationId=…` in the address bar in both directions: the parameters are acted on once per pair, and the conversation on screen is written back once the URL's own conversation has loaded (read from the live store, so a half-switched render cannot overwrite it). A reload or a second tab opens the same conversation. The Manager's `/manage/chat` still clears the parameters once read. The widget's direct routes (`/chat/:environment/:agentId[/:userId]`, risk R10) are untouched; `location.test.tsx` pins them.
- **`conversationControls` (B4) in the shared chat.** The Manager's `ChatPanel` (Manager and Workforce) reads them from the profile (`useAgentReviewProfile`) and drops undo, redo, attachments (button, paste and drop), ratings and quick replies the agent switched off; `streaming: false` sends without streaming (`agentStreaming` in the chat store). The rule itself — every switch on unless `false`, `rawHtml` off unless `true` — is `parseConversationControls` in `@eddi/core`, shared with the widget.
- **The widget follows `rawHtml` (D9) — a behaviour change.** `Message` now renders raw HTML only when the host passes `enableRawHtml` (default **off**) and otherwise shows it as text (`escapeRawHtml`). `ChatWidget` passes the agent's `conversationControls.rawHtml` from the profile; until the profile answers, when it reports no controls, and for every agent that does not set `rawHtml: true`, `<b>bold</b>` in a reply is shown as that literal text. The parser stays a lazy chunk. The widget honours the other switches too (undo, redo, attachments via a new `Composer attachments` prop, quick replies, ratings, streaming); the `hide*` URL parameters can only hide more. [`chat-ui-embedding.md`](../chat-ui-embedding.md#upgrading-html-in-replies-is-off-by-default) says what to do when upgrading.
- **The Manager's chat history** shows a conversation's title instead of its id once it has one.
- **Platform Operator.** The two prompt bullets #1273 and #1282 each added are both kept; the revision goes from their 53 to **54**. The prompt also learns that catalog entries carry appearance and controls (avatars on other hosts need the Manager's `img-src`) and what the Workforce sidebar does. No allow-list change: renaming stays the owner's act.
- **i18n.** `Workforce.sessions.*` and `Workforce.home.*` in all eleven locales; the layout uses logical properties only.

### Design decisions

- The first message goes through router state, not `?q=`: a crafted link must not make anyone say anything (the same reason deep links only preselect). A reload cannot resend it — the chat drops the state the moment it takes it, and the URL write that follows replaces the history entry.
- Team sessions are listed but cannot be renamed or pinned: B2 lives on conversation descriptors, and group conversations have no such fields. Pinning them would need a backend change, not a client-side store.
- The catalog carries appearance rather than each card fetching `/profile`: one request for the whole Home, and the same views the profile serves.
- Raw HTML off by default in `Message` itself, not only in the widget: any future host of the shared component starts safe.
