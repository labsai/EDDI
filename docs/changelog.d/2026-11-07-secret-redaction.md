## 🔒 fix(secrets): bearer redaction in any case, fail-closed export scrub, legacy KEK removed, loud grant-check errors (2026-11-07)

**Repo:** EDDI (`fix/secret-redaction`)

### What changed and why

- **`SecretRedactionFilter` redacts a bearer token whatever the scheme's case.** The shape rule matched only `Bearer` with a capital B, the explicit-scheme rule listed `Basic|Token|Digest` but not bearer, and the name-bound rules stop a value at the space after the scheme word, which at six characters is under their floor. So `authorization: bearer <token>` and `Authorization: BEARER <token>` went through `redact()` unchanged, and so did a canonical `Authorization: Bearer <token>` with a token under 20 characters. The bearer rule is now case-insensitive and starts at a word boundary (`forbearer …` is prose, as for the `sk-` rules), except that the second character of an escape does not count: in serialized text a line break before the scheme is `\n`, and the canonical rule, which had no boundary, matched there. Its replacement stays `Bearer <REDACTED>`, the spelling the already-redacted checks recognise, so a second pass changes nothing. The explicit `authorization:` rule now lists `bearer` too, with no length floor, like `Basic`. `redact()`'s Javadoc, orphaned above `redactCredentialShapes`, is back on `redact()`.
- **`SecretScrubber.scrubJson` fails closed.** It caught every exception and returned the input — credentials included — with a WARN. Serializer output can still fail to parse (Jackson's read constraints, such as the 1,000-level nesting limit, do not bind the writer), and a bug in the scrub walk failed open the same way. It now throws `IllegalStateException` on a parse or write failure, carrying neither the input nor Jackson's exception (whose message quotes source text), and lets any other exception propagate. `containsCredential` already failed closed on the same input. At the callers the export aborts, or stops writing the snippet or schedule section at that document. An agent sync's remote source skips the document (the sync fails when it is the agent itself), and `RemoteApiResourceSource` remembers the refusal like a failed read, so a document several steps name is not fetched again for each of them.
- **The legacy fixed-salt KEK path is gone from `EnvelopeCrypto`.** `deriveKeyFromString(String)` (deprecated since 6.0.2), its `LEGACY_SALT` and `sha256Hex` had no caller in main code: the provider derives every KEK with the salted overload, `VaultSaltManager` holds the only live copy of the legacy salt, and `VaultChecksum.legacy` is the production legacy checksum. The four tests that built legacy checksum fixtures use `VaultChecksum.legacy`. `EnvelopeCryptoTest` now runs its encryption tests on random DEKs (no PBKDF2) and covers the salted overload's salt-length guard, which nothing tested.
- **The deploy-time grant check says when it could not check.** `VaultGrantChecker.isGranted` treated every metadata-read exception as granted and logged it at DEBUG — right for a secret that does not exist yet, but identical for a vault-store outage or a corrupt row. The resolver checks no grants, so that agent kept access to a restricted secret until its next deploy, with no trace. A not-found secret and an unparseable reference stay quiet; any other failure now logs a WARN naming the secret and the agent. It is still let through, as the class contract chooses. Documented in [secrets-vault.md](../secrets-vault.md#what-counts-as-granted).

### Design decisions

- **No new counter for the skipped grant check.** A store failure is already counted by `eddi.vault.errors.count` inside `VaultSecretProvider.getMetadata`; the WARN line names which agent and secret went unchecked, which a counter cannot.
- **The preflight's `checked` stays `true` when a grant could not be read.** Reporting `false` needs the checker to return the count of unverifiable references alongside the violations, which changes the method every gate test mocks. Left as a follow-up; the page says so.
- **The scrubber's exception drops its cause.** A parse error's message quotes the token it stopped at, which can be the credential, and a cause is printed with the stack trace that logs the exception. The exception class name is kept.
