## Email channel: consulting another agent (2026-11-23)

**Repo:** EDDI · **Branch:** `feat/email-consult` (stacked on `feat/email-addressing`, #1496) · **Plan:** `planning/email-channel-v2-plan.md` §10 (Phase 6, on `docs/email-channel-v3-control-plan`)

**What changed:**

- **`targets[].consultable`** (email only): names of other `AGENT` targets of the same integration, each with a different agent, at most 10. Validated in `RestChannelIntegrationStore` in a second pass (a target may name one after it), names stored as the targets spell them; refused on a GROUP target, for a GROUP or same-agent entry, and on every other channel type. Save warning `email.consult-not-enabled` (`EmailAgentToolsInspector.targetsWithoutConsultTool`) when the agent has no LLM task with `enableBuiltInTools` and `converse_with_agent` whitelisted.
- **`mail.consultRequested`** (`[{target, agentId}]`), decided by the new `integrations/email/EmailConsults` before the turn: the sender is authenticated; the mail named the target by address, plus-tag or mention (the routed target and `alsoAddressed`, so a new mail naming two targets works too); a target of the running agent that admits the sender lists it; the named target's own `allowedSenders` admit the sender. Otherwise a continuation keeps `mail.route.redirectRefused`.
- **`converse_with_agent` from an email turn** (`DynamicAgentToolsProvider.emailScope`, `ConverseWithAgentTool.CallerScope`): reaches only the agents in the current step's `mail.consultRequested` (the stored `{type, value}` form of the context is read too). An anonymous sender's turn, a consulted agent's turn, and scheduled or self-continuation turns of an email conversation reach nobody. The consulted agent runs as `email-consult:<integrationId>:<hash of integration and address>`. For these consultations the USE check asks about the integration's owner (`ResourceAccessGuard.ownerOf`; an erased or synthetic owner counts as none, and the email identity is checked instead, which fails closed). A group member's turn of an email discussion keeps its group's `allowedDelegationTargets` but is checked as the email identity: lending the owner's rights there would open every agent the owner may use (review finding). Depth ceiling 1 via `delegationDepthMax`; no continuation by `conversationId`; the consulted conversation is ended as soon as it answers; one that pauses for an approval is ended undecided and the consultation refused (an answer it gives later could never reach the asking turn).
- **No other dynamic-agent tools from a mail's turn**: `create_sub_agent`, `find_agents_by_capability` and `recruit_agent` are not assembled for `email:`, `email-anon:`, `email-consult:` or `email-thread:` users; they would run as the sender with no bound (review finding). `handoff_to_team` and A2A tools stay designer-configured.
- **GDPR**: because the consult identity is derived from the address, `EmailIdentityGdprParticipant` erases and exports the consulted conversations together with the sender's own; nothing has to be read before anything is deleted.
- **`email-consult:`** (and `email-thread:`, reserved for v2 Phase 5) are in `ReservedPrincipals.PREFIXES`; `email-consult:` is in `hasNoPersistentMemory`: no long-term memory read or written, no memory tool. It is not an email sender identity, so `EmailReplyRecipients` never answers it and its conversation has no ledger row: nothing is mailed from it. `emailIntegration` joins `ClientContextGuard.RESERVED_KEYS`.
- Save warning `email.consult-owner-cannot-use` (in `RestChannelIntegrationStore`) when the owner may not use a consulted agent, asked exactly as at run time (no admin bypass, no team shares).
- MCP `create_channel_integration` description and warning text, [`email-integration.md`](../email-integration.md) ("Bringing in another agent", keys, warnings and context tables), [`passing-context-information.md`](../passing-context-information.md) and [`configuration-reference.md`](../configuration-reference.md) (reserved key), Manager target editor ("Can consult", client-side checks incl. duplicates and observers, 10 new strings in all 11 locales), Platform Operator prompt (revision 84).
- Tests: processor (requested, not listed, consulted target's `allowedSenders`, rejecting owner target, new mail with two targets, unauthenticated, subject word), store validation, provider scope (identity, owner principal, unknown owner, unrequested agent, malformed context, continuation, depth on both sides, group member, anonymous, ordinary callers), memory handler, reply sender, identity helpers, inspector, and `ChannelTargetConsultableParityTest` against real MongoDB and PostgreSQL.

**Design decisions:**

- The plan relied on `allowedDelegationTargets`, which a standalone agent cannot configure (it gets the permissive default). The per-turn `consultRequested` list is therefore the boundary for every `converse_with_agent` call a mail's turn makes, not only requested ones. **Upgrade note:** an email agent that delegated through `converse_with_agent` before now delegates only when a mail requests a consultation, and its delegate runs memory-less; an email agent that used `create_sub_agent`, `find_agents_by_capability` or `recruit_agent` no longer gets them on a mail's turn.
- A consultation always starts a new conversation and ends it after one answer; multi-turn consultations within one mail's turn are separate conversations.
- The consult identity is keyed to the sender (a hash, so the consulted agent learns nothing) rather than random: GDPR reaches it from the address alone, which is simpler and order-independent compared with recording conversation ids on ledger rows.
- A pausing consultation is refused rather than continued: plan §10.2 puts the approval on the consulting agent's `converseWithAgent`.
- `mail` is not a reserved context key: `ClientContextGuard` strips every key that *starts with* a reserved one, which would take `mail…` keys from every client; its one trusted reader acts only for email identities, which no client can own.

**Open:** the `origin=email` taint of the v3 plan (C1) is not on this base. Not run here: an IT for the stored conversation-memory form of `context:mail` and for memory isolation through the real conversation store.
