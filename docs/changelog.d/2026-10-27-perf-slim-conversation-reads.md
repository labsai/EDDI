## ⚡ perf(conversations): current-step and approval-status reads no longer transfer the whole conversation (2026-10-27)

**Repo:** EDDI (`perf/slim-conversation-reads`)

### What changed and why

Every read of a conversation loaded its whole stored document, and for an agent with tools that document is 0.5–3 MB after twenty turns, almost all of it step history. On a staging deployment whose link to MongoDB was intermittently bandwidth-limited (~100 KB/s for whole-document reads, while small reads stayed at 0.3 s and EDDI itself was idle), `GET /agents/{conversationId}/approval-status` and the chat-reload read `GET /agents/{conversationId}?returnCurrentStepOnly=true` took 11–29 s, and the approval card's spinner showed for that long. Both responses describe only where the conversation is now.

- **New store read, `IConversationMemoryStore#loadConversationMemoryTail`**, returning a `ConversationMemoryTail`: the document with `conversationSteps` and `conversationOutputs` cut to their last element, no `redoCache`, and none of the pending tool-call batch's resume-only fields (`chatTranscriptJson`, `gatingAssistantMessageJson`, `traceSoFar`, `fingerprint`, each call's `argumentsRaw`), plus the totals the projection still needs from what stayed behind — step, output and redo counts, and the `audit:cost` / `audit:discarded_cost` values for `conversationCost`. **MongoDB:** one aggregation (`$match` on `_id`, `$set` with `$slice: -1` and the computed totals, `$unset`). **PostgreSQL:** one query using `->-1`, `jsonb_array_length` and `jsonb_path_query_array`. The spend values come back in document order and are summed in Java with the same filter and the same left-to-right addition as before, so the cost is bit-identical, not merely close.
- **`IConversationMemoryStore#loadConversationMemorySnapshotForApprover`** for `approval-status?detail=full`: that response *is* the whole snapshot, so it still carries the history; only the resume-only batch fields — which `sanitizePendingToolCallsForApprover` nulls before serving — stay on the server (MongoDB: all five; PostgreSQL: the four batch-level ones, `argumentsRaw` sits inside an array `#-` cannot wildcard and is small).
- **Wired into:** `ConversationService.readConversation` (both overloads) when `returnCurrentStepOnly=true` — which serves REST `GET /agents/{conversationId}`, the managed-agent read, MCP `read_conversation` and the A2A status read; `RestAgentEngine.getApprovalStatus` and `McpHitlTools.getApprovalStatus` (summary → tail, `detail=full` → approver read). A RULE pause's `pauseDetails.actions` comes from the tail's last step; only when that step has no actions does it load the full history and walk back, as before.
- **Unchanged:** every write path, undo/redo, resume, the conversation log, export, `returnCurrentStepOnly=false` (and `null`), and every other caller of `getConversationMemorySnapshot` / `loadConversationMemorySnapshot`.
- `ConversationMemoryUtilities.convertSimpleConversationMemory` was split into a shared body taking the rendered lists plus the totals explicitly, so the full-snapshot and the tail projection run the same code.
- A document still storing a step under EDDI 5's `packages` key (read by the load's `@JsonAlias`, not by the server-side expressions) is detected in the same round trip and loaded in full, so its cost is never under-counted.

### Not covered

`detail=full` still transfers the step history — the response is the full snapshot. The Manager's own approval card uses the summary.

```decision-log
| 2026-10-27 | Current-step and approval-status reads load a server-side projection (last step/output + computed totals) instead of the whole conversation document | Whole-document reads ran at ~100 KB/s on a bandwidth-limited database link; 0.5–3 MB documents made these reads take 11–29 s | Caching the snapshot (stale across nodes, does not help the first read); a `$slice` find projection without totals (undoAvailable, output/step pairing and conversationCost need the full lengths and every step's spend) |
```
