## 🔒 fix(slack,hitl): bind Slack events and approvals to their integration, conversation and pause; scope the approver's identity (2026-09-26)

**Repo:** EDDI (`fix/slack-hitl-binding`)

### What changed and why

Fixes the Slack and HITL findings of the 2026-09-25 review (H4a–H4d, H5, A2 and the Slack user-id collision).

- **H4a — events are bound to the app that signed them.** `/integrations/slack/events` verified a body against the pooled signing secrets and then routed by the `channel` the body named, so anyone holding one integration's secret (anyone who can create an integration holds its own) could run turns, as any Slack user, against another integration's agents, answered with that integration's bot token. `SlackSignatureVerifier.matchingSecret` now reports *which* secret matched; the webhook hands it to the handler with the envelope's `team_id` / `api_app_id` (`SlackEventEnvelope`), and every route the handler takes — fresh resolution, thread lock, DM default, group follow-up, observers, help and error notices — must belong to an integration (or legacy connector) whose own secret that is (`ChannelTargetRouter.matchesInbound` / `channelMatchesInbound`, constant-time compare). New optional `platformConfig.teamId` / `appId` pin the workspace/app further; unset keeps today's behaviour.
- **H4d — DMs are no longer routed to "the first integration".** `resolveDefaultForDm` iterated an immutable map whose order is randomised per JVM, so a DM went to an arbitrary integration (differently per pod). It now takes the verified secret and envelope ids, considers only integrations that secret authenticates, prefers one that pins more of the envelope's ids, then the lowest name. A DM thread reply, whose lock carries no credentials, gets the same integration attached (`integrationForDm`) — previously it had no bot token at all.
- **H4c — a Slack decision must target a conversation of the deciding integration.** `/interactive` verified with the secret of the integration named in the button, checked that integration's approver list, then resumed whichever conversation id the button named. The handler now requires the conversation's agent to be one of the integration's targets **and** the conversation to have been started by it: Slack-started conversations now carry a `channelIntegration` start context; a conversation started before that is accepted when its `channelIntent` names the integration's own channel. A group discussion's group must be one of the integration's targets. The name that binds a card to its integration is now unique among routed integrations of a type and may not contain `|` (validated in `RestChannelIntegrationStore`); if legacy data still has two integrations with one name, `getIntegrationByName` binds to neither.
- **H4b — a decision is bound to the pause it was made for.** New optional `HitlDecision.pauseId` (the pause start's epoch milliseconds, `HitlDecision.pauseIdOf`), reported as `pauseId` by conversation and group `approval-status` (REST and MCP). `ConversationHitlService.resumeConversation` refuses a mismatching decision before the CAS, and re-checks after it against the snapshot the resume runs on (restoring the pause if it changed in between) — `IConversationService.PauseMismatchException`, REST `409`, MCP `errorCode: PAUSE_CHANGED`. `GroupHitlCoordinator.resumeDiscussion` checks it against `pausedAt`. Slack cards carry it in the button value (`<integration>|<subject>|<pauseId>`; group cards via a new `HitlPauseEvent.pausedAt`); a stale card is marked "out of date", a card without a pause id (older release) is refused the same way, and a card whose pause could not be identified at posting time is rendered without buttons.
- **H5 — the approver's identity covers what the approver saw.** A resume bound the approver as the caller for the whole resumed turn, so every later `${caller:token}` call — including all calls after a RULE pause, which previews nothing — went out with an admin's token. Now: approver == conversation owner → unchanged. Otherwise the turn runs with **no caller** (caller-bound calls fail closed, like a scheduled turn), and the approver is bound on a separate `CallerIdentityContext` approver slot that `ToolLoopResumer` promotes to the caller only around each explicitly approved tool call (`callAsApprover`). `propagate()` carries the new slot. A resumed group discussion runs as the approver only when the approver started it (`GroupHitlCoordinator.resumeCallerFor`).
- **A2 — the approver view drops the batch fingerprint.** `sanitizePendingToolCallsForApprover` now nulls `PendingToolCallBatch.fingerprint`, an unsalted SHA-256 over tool names and raw arguments (an offline guessing oracle next to the redacted arguments). It is still persisted for the no-progress guard.
- **Slack user ids are namespaced by team.** Bare `U…` ids are unique per workspace only; two people in different workspaces shared conversations and long-term memory. EDDI now uses `slack:<teamId>:<userId>` (team from `user_team`, `team`, else the envelope). Existing thread mappings under the bare id are still found and reused. `eddi.slack.namespace-user-ids=false` restores bare ids.

### Compatibility

- **Behaviour change (intended):** after upgrade, new Slack conversations use namespaced user ids, so long-term memories stored under a bare Slack id are not visible to them unless `eddi.slack.namespace-user-ids=false`. Running threads continue unchanged.
- **Behaviour change (intended):** approval cards posted before this release cannot be used (no pause id); decide those pauses from the Manager/API.
- **Behaviour change (intended):** a HITL resume by someone other than the conversation owner no longer carries a caller identity outside the approved tool calls.
- REST/MCP shapes are additive: `pauseId` on the decision body, the `approval-status` summaries and as an optional MCP `resume_conversation` argument; `pausedAt` on the group `HitlPauseEvent`. Stored configs: new optional `platformConfig.teamId` / `appId`; a stored integration whose name contains `|` or duplicates another routed one keeps working until it is next saved (then the save is refused).

### Design decisions

- Pause identity is the pause start timestamp in epoch milliseconds, not a new stored field: every pause stamps a fresh `hitlPausedAt` / `pausedAt`, Mongo keeps milliseconds, and REST already exposes `pausedAt` — no migration.
- The Slack path pre-checks the pause and ownership for clear messages, but the authoritative checks run in the engine (under the conversation CAS; for groups right after the read — the group CAS itself is `fix/group-conversation-state`'s).
- Conversation-to-integration binding uses a start context rather than a new persisted field, so no schema change; a REST client can set the context only on its own conversations, which gains it nothing.

### Follow-ups

- The group approve path still reads, checks and CAS-writes on state only; the pause-id check there has a read-to-CAS window until `fix/group-conversation-state` lands a state-and-version CAS.
- `GroupHitlCoordinator.submitHumanInput` binds the submitting human member for the rest of the discussion — the same class as H5, not in this finding's scope.
- The Manager approvals UI should pass `pauseId` from `approval-status` into its resume call (backend accepts it; omitted keeps the old behaviour).

```decision-log
| 2026-09-26 | HITL decisions may carry a pauseId (epoch-ms of the pause start); Slack cards always do | A stale Slack card or a REST/MCP decision could approve a later, different pause | A stored random pause UUID (needs a schema field and migration for RULE pauses) |
| 2026-09-26 | A non-owner approver's identity is bound only around the tool calls they approved; the rest of the resumed turn has no caller | ${caller:token} calls after an approval ran with the approver's token, including un-previewed calls after a RULE pause | Keeping the whole-turn binding (privilege escalation); dropping it entirely (breaks approved caller-bound calls) |
```
