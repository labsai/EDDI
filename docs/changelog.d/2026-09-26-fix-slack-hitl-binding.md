## 🔒 fix(slack,hitl): bind Slack events and approvals to their integration, conversation and pause; scope the approver's identity (2026-09-26)

**Repo:** EDDI (`fix/slack-hitl-binding`)

### What changed and why

Fixes the Slack and HITL findings of the 2026-09-25 review (H4a–H4d, H5, A2 and the Slack user-id collision).

- **H4a — events are bound to the app that signed them.** `/integrations/slack/events` verified a body against the pooled signing secrets and then routed by the `channel` the body named, so anyone holding one integration's secret (anyone who can create an integration holds its own) could run turns, as any Slack user, against another integration's agents, answered with that integration's bot token. `SlackSignatureVerifier.matchingSecret` now reports *which* secret matched; the webhook hands it to the handler with the envelope's `team_id` / `api_app_id` (`SlackEventEnvelope`), and every route the handler takes — fresh resolution, thread lock, DM default, group follow-up, observers, help and error notices — must belong to an integration (or legacy connector) whose own secret that is (`ChannelTargetRouter.matchesInbound` / `channelMatchesInbound`, constant-time compare). New optional `platformConfig.teamId` / `appId` pin the workspace/app further; unset keeps today's behaviour.
- **H4d — DMs are no longer routed to "the first integration".** `resolveDefaultForDm` iterated an immutable map whose order is randomised per JVM, so a DM went to an arbitrary integration (differently per pod). It now takes the verified secret and envelope ids, considers only integrations that secret authenticates, prefers one that pins more of the envelope's ids, then the lowest name. A DM thread reply, whose lock carries no credentials, gets the credentials of an integration **or legacy connector** that the verified secret authenticates *and* that has the locked target among its own targets (`threadCredentialsForDm`); otherwise the event is dropped. Attaching "whatever integration the secret authenticates" (as a first cut of this branch did) would have let one app's secret continue a DM thread locked to another app's agent. Previously such a reply had no bot token at all.
- **H4c — a Slack decision must target a conversation of the deciding integration.** `/interactive` verified with the secret of the integration named in the button, checked that integration's approver list, then resumed whichever conversation id the button named. The handler now requires the conversation's agent to be one of the integration's targets **and** the conversation to have been started by it: Slack-started conversations carry a `channelIntegrationId` start context with the integration's store **resource id** (runtime-only `ChannelIntegrationConfiguration.resourceId`, set by the router, never serialized) — not the name, which could be renamed away and reused by a new integration. Conversations started before this binding carry no id and are not decidable from Slack; their cards are posted without buttons (`NOT_BOUND_NOTICE`), and they remain decidable from the Manager and the API. A group discussion must have been started through the integration — the Slack adapter records an origin mapping (`IUserConversationStore`, intent `channel:slack-group-origin:<gcId>`, user `integration:<resourceId>`) when it starts one — and its group must be a target. Approver entries may be team-scoped (`T…:U…`), and when the integration pins `teamId` a clicking user from another team (`user.team_id`, Slack Connect) is refused. The name that binds a card to its integration is now unique among routed integrations of a type and may not contain `|` (validated in `RestChannelIntegrationStore`); if legacy data still has two integrations with one name, `getIntegrationByName` binds to neither.
- **H4b — a decision is bound to the pause it was made for.** New optional `HitlDecision.pauseId` (the pause start's epoch milliseconds, `HitlDecision.pauseIdOf`), reported as `pauseId` by conversation and group `approval-status` (REST and MCP). `ConversationHitlService.resumeConversation` refuses a mismatching decision before the CAS, and re-checks after it against the snapshot the resume runs on (restoring the pause if it changed in between) — `IConversationService.PauseMismatchException`, REST `409`, MCP `errorCode: PAUSE_CHANGED`. The pre-CAS comparison runs only while the conversation is `AWAITING_HUMAN`: an already-resolved conversation has no current pause, so a decision for it gets the ordinary state conflict (`409` naming the state, MCP `WRONG_STATE`), not "pause changed". `GroupHitlCoordinator.resumeDiscussion` checks it against `pausedAt` and throws `IGroupConversationService.GroupPauseMismatchException` (a `GroupDiscussionException`, so REST still answers `409`); the MCP `approve_group_phase` tool takes an optional `pauseId` argument like `resume_conversation` and answers `PAUSE_CHANGED`. Slack cards carry it in the button value (`<integration>|<subject>|<pauseId>`; group cards via a new `HitlPauseEvent.pausedAt`); a stale card is marked "out of date" (compared only while the conversation or discussion is still paused, so a card clicked after someone else decided reads "already resolved"), a card without a pause id (older release) is refused the same way, and a card whose pause could not be identified at posting time is rendered without buttons.
- **H5 — the approver's identity covers what the approver saw.** A resume bound the approver as the caller for the whole resumed turn, so every later `${caller:token}` call — including all calls after a RULE pause, which previews nothing — went out with an admin's token. Now: approver == conversation owner → unchanged. Otherwise the turn runs with **no caller** (caller-bound calls fail closed, like a scheduled turn), and the approver is bound on a separate `CallerIdentityContext` approver slot that `ToolLoopResumer` promotes to the caller only around each explicitly approved tool call (`callAsApprover`). `propagate()` carries the new slot. A resumed group discussion runs as the approver only when the approver started it (`GroupHitlCoordinator.resumeCallerFor`).
- **A2 — the approver view drops the batch fingerprint.** `sanitizePendingToolCallsForApprover` now nulls `PendingToolCallBatch.fingerprint`, an unsalted SHA-256 over tool names and raw arguments (an offline guessing oracle next to the redacted arguments). It is still persisted for the no-progress guard.
- **Slack user ids can be namespaced by team (opt-in).** Bare `U…` ids are unique per workspace only; two people in different workspaces could share conversations and long-term memory. `eddi.slack.namespace-user-ids=true` identifies users as `slack:<teamId>:<userId>` (team from `user_team`, `team`, else the envelope — sender-signed, not verified, so this prevents accidental collisions, not impersonation). It defaults to **false**, because switching an existing deployment changes every user's id for templates (`{userInfo.userId}`), long-term memory and GDPR. When enabled, users of the *legacy team* (`eddi.slack.legacy-team-id`, or the one `teamId` every routed integration pins — never derived while a legacy agent-level Slack connector is routed, since it pins no workspace and its users' bare ids could be any team's; the derived value reflects the current configuration only, so operators who need certainty set the property) keep their bare-id threads and get their bare-id long-term memories copied to the namespaced id on first contact (only while the namespaced id has none; copy, not move). With no legacy team nothing is aliased. Every Slack-started conversation now carries the raw `slackUserId` and `slackTeamId` as start context. `SlackIdentityStartupCheck` logs a WARN when namespacing is off and more than one Slack app is configured.

### Compatibility

- **No user-id change by default.** Enabling `eddi.slack.namespace-user-ids` changes `{userInfo.userId}` for Slack users and, for a legacy-team user, leaves their data under two ids until the bare-id data is erased — a GDPR export/erasure must name both.
- **Behaviour change (intended):** conversations and group discussions started through Slack before this release cannot be decided from Slack buttons (no integration binding); decide them from the Manager/API.
- **Behaviour change (intended):** approval cards posted before this release cannot be used (no pause id); decide those pauses from the Manager/API.
- **Behaviour change (intended):** a HITL resume by someone other than the conversation owner no longer carries a caller identity outside the approved tool calls.
- REST/MCP shapes are additive: `pauseId` on the decision body, the `approval-status` summaries and as an optional argument of the MCP `resume_conversation` and `approve_group_phase` tools (an additive MCP tool-schema change); `pausedAt` on the group `HitlPauseEvent`. Stored configs: new optional `platformConfig.teamId` / `appId`; a stored integration whose name contains `|` or duplicates another routed one keeps working until it is next saved (then the save is refused).

### Design decisions

- Pause identity is the pause start timestamp in epoch milliseconds, not a new stored field: every pause stamps a fresh `hitlPausedAt` / `pausedAt`, Mongo keeps milliseconds, and REST already exposes `pausedAt` — no migration.
- The Slack path pre-checks the pause and ownership for clear messages, but the authoritative checks run in the engine (under the conversation CAS; for groups right after the read — the group CAS itself is `fix/group-conversation-state`'s).
- Conversation-to-integration binding uses a start context (the integration's resource id) rather than a new persisted field, so no schema change; a REST client can set the context only on its own conversations, which gains it nothing. The group binding is an origin mapping in the existing user-conversation store for the same reason — no change to the group conversation document, which `fix/group-conversation-state` is reworking.
- User-id namespacing is opt-in (lead decision): it only helps multi-workspace deployments, while switching it on silently would break memory, templates and GDPR lookups for every existing single-workspace one.

### Follow-ups

- The group approve path still reads, checks and CAS-writes on state only; the pause-id check there has a read-to-CAS window until `fix/group-conversation-state` lands a state-and-version CAS.
- `GroupHitlCoordinator.submitHumanInput` binds the submitting human member for the rest of the discussion — the same class as H5, not in this finding's scope.
- Once `fix/reserved-context-keys` (PR #831) lands, add `channelIntegrationId`, `channelIntent`, `slackUserId` and `slackTeamId` to its reserved context keys: they are engine-owned, and a REST client can currently stamp them onto its own conversations (harmless for the binding, which only a Slack-started conversation's start context can satisfy for another user's conversation, but still engine-owned).
- The integration-name uniqueness check is generic in its message but still reveals that a name is taken, and fails open on store errors or concurrent creates; `getIntegrationByName` failing closed on a duplicate bounds the impact.
- The Manager approvals UI should pass `pauseId` from `approval-status` into its resume call (backend accepts it; omitted keeps the old behaviour).
