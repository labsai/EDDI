## fix(schedule,alerts): agent tests no longer alert, sparse crons end cleanly, timeouts cancel their turn, caps (2026-11-18)

**Repo:** EDDI (`fix/schedule-and-alert-defects`)

### What changed and why

Findings L1-L6 and the confirmed parts of L8 of the November 2026 code review (scheduling, alerts, agent tests).

- **Agent-test conversations raise no alerts (L1).** `ConversationStepRunner.reportTurnOutcome` and `OutputMatchHook.onCleanTurn` skip a conversation whose user id is in the `agent-test:` namespace, so a test case that expects a failure no longer pages the on-call channel. Metrics and the test runner's own reporting do not go through this hook. Rating alerts are untouched (a test conversation is not rated).
- **A sparse cron no longer strands and re-fires its schedule (L2).** `SchedulePollerService.onFireCompleted` records the fire as completed even when no next fire can be computed, and then disables the schedule with `disabledReason: "no-next-fire"` (counter `eddi.schedule.nextfire.exhausted`) instead of leaving the row CLAIMED, where its lease ran out and it fired again about five times. The bookkeeping write is retried three times before it is left to the lease. `CronParser` now finds the successor of every satisfiable expression (see the second review follow-up below: the longest gap is 40 years), so `0 9 29 2 *` keeps firing; an expression that can never match is still refused at save time.
- **A fire timeout cancels the turn it started (L3).** `ScheduleFireExecutor` cancels the running turn through `IConversationService.cancelConversation` when the fire times out, and every turn of one due fire carries the Idempotency-Key `schedule:<id>@<lastFired>`, so a retry queued behind a first turn that committed after all is answered as skipped, as `ContinuationFireHandler` does with its key.
- **Dead-lettered schedules leave the due scan (L4).** The poller query already excluded them by status; the cost was walking their index entries. Mongo gets an index `(enabled, fireStatus, nextFire)` and Postgres a partial index `(next_fire, id) WHERE enabled AND fire_status <> 'DEAD_LETTERED'` plus the matching predicate in `findDueSchedules`. Rows keep `enabled` and `nextFire`: retry and dismiss are unchanged, and `countPendingSchedulesByName` / `readScheduleByName` return what they returned before (a dead-lettered row still counts as pending).
- **Schedule caps and a warning (L5).** `eddi.schedule.max-per-owner` (200) and `eddi.schedule.max-total` (10000) bound the enabled schedules created through the API (`createdBy` set); create and enable beyond them answer `429 SCHEDULE_LIMIT`. `0` turns a limit off. A new `IScheduleStore.countEnabledSchedulesCreatedBy`. The create response carries `warnings` for a recurring schedule with no `maxCostPerFire` or a persistent conversation that never rolls over (a response-only field, never stored). No default cost cap was added.
- **Fresh persistent conversation (L6).** `POST /schedulestore/schedules/{id}/reset-conversation` clears the schedule's persistent conversation id and ends the old conversation when it is idle. Not added to the MCP tools (a new tool, not a pass-through).
- **L8, confirmed parts.** `AlertMaintenanceSchedule` removes duplicate `alerts-maintenance` schedules (keeps the oldest) at startup and right after creating one. Deleting a schedule ends its idle persistent conversation. The suspicion that editors may delete or disable system-managed schedules (e-mail poll, ingestion, lesson/cadence) with workspaces off is not a privilege gap: with workspaces off an editor may edit the integration or knowledge base the schedule belongs to, and each is re-created when that resource is saved; left as is.

### Review follow-up (same branch)

- The timeout cancel now stops only the fire's own turn. A `new`-strategy fire cancels its own conversation; a `persistent` fire calls the new `IConversationService.cancelInFlightTurn(conversationId, "scheduleFireId", runId)`, which signals the in-flight turn only when it carries that run id (no state change, no pause cancelled, no continuation disarmed, no approval audit). A turn still queued carries `callerGivesUpAtEpochMs` and is dropped at the front of the queue. The watchdog interrupt and a manual fire that times out cancel too; a shutdown drain (`ScheduleFireExecutor.beginShutdown`) does not.
- The run id and idempotency key derive from the occurrence's due time (`nextFire` at claim) instead of `lastFired`, so a skipped fire no longer makes the next regular fire reuse the key and be swallowed; a manual fire gets a key per click; a requeued dead letter is a new occurrence. A "skip" that is really an already-committed earlier attempt now completes the occurrence. The `window: "RUN"` tool-quota scope follows the same id.
- Delete and reset end the old conversation with a compare-and-set from the state read, not an unconditional end.
- `removeDuplicates` keeps an enabled, not dead-lettered copy in preference to an older broken one.
- Caps: with authorization off only the total limit applies; the docs state which schedules count and that the limit is soft.

### Second review follow-up (same branch) — a scheduled turn runs once

- **The environment-qualified `say` admits a keyed turn like the conversation-id one.** The scheduler sends its turn through `IConversationService.say(environment, agentId, …)`, which skipped `TurnIdempotencyService.admitOrServe`: its stored-key check ran only when a queued turn was rebuilt over a newer document, so a retry that loaded the conversation after the first attempt's turn committed ran the input a second time. Both overloads now go through one private `ConversationService.sayKeyed` (a stored key is answered from its step, a key still running on this node is waited for, a refused one is released); a call without a key takes the old path unchanged.
- **`conversationStrategy: new` keeps one conversation per occurrence.** Each retry used to start another conversation, where the conversation-scoped key could not find a first turn that committed late. The first attempt now records its conversation on the schedule (`occurrenceRunId`, `occurrenceConversationId`, written by the new `IScheduleStore.recordOccurrenceConversation`, conditional so a racing attempt adopts the first record) before its turn is sent, and a retry of the same occurrence continues it — on any node. A recorded conversation that is gone, another user's or agent's, or ended without the turn is replaced; a record that cannot be written fails the attempt before anything is sent. A retry that finds its own conversation still busy with an earlier attempt is `FAILED` (retried), not `SKIPPED` (which re-armed past the occurrence). The two fields are fire-path state: kept out of JSON both ways, never exported, absent on old rows (none).
- **The no-next-fire disable is one fenced write.** `markCompleted` gained a `disabledReason` overload: completion and `disabledReason: "no-next-fire"` are one update filtered on the fire's claim, on MongoDB and PostgreSQL, and the retry of a failed completion is fenced the same way. The separate `setScheduleEnabled` by id (and the read-then-write check that only narrowed its window) is gone, so an operator's enable or cron change after the claim was released is never overwritten.
- **The give-up time of a fire's turn counts from the poller's dispatch**, the origin of the watchdog (stamped as the transient `ScheduleConfiguration.dispatchedAt` by `dispatch` and by a manual claim), so a queued turn is dropped no later than the interrupt however long startup took; the fire stops waiting for its turn at the same moment. The "no late turn" comment now says what holds: a queued turn is dropped, a running one is asked to stop and, if it still commits, its key keeps the retry from running it again.
- **Cron horizon.** The longest gap between two matches of any expression this parser accepts is 40 years (29 February on one weekday, e.g. `0 9 29 2 */7`: 2088 → 2128 across 2100), measured in `CronParserTest` over 1600-2800. Whether an expression can match at all is decided from its fields (`CronParser.canEverMatch`: only non-existent dates never match), so "never matches" is said exactly when true and costs no scan; the scan window is twice the gap plus a year (81 years), and its cost is bounded by the real gap. Save, `previewCron` and `onFireCompleted` all go through `computeNextFire` and agree. An earlier local fix had raised the window to 400 years instead.
- **Alert maintenance dedupe by id.** Offset pages can shift during the scan; schedules are collected by id before the survivor is chosen, so a survivor read twice is no longer deleted as its own duplicate.

### Design decisions

- Test conversations are excluded at the two turn hooks, not by adding an environment to alert rules (the finding's alternative); rules keep no notion of environment.
- The scan window is widened rather than a sparse-cron refusal added at save time: every satisfiable expression has a next fire within 40 years, and unsatisfiability is decided from the fields before any scan, not by exhausting a window.
- The occurrence's conversation is recorded on the schedule row, not found through the fire log: the fire log is written when an attempt ends, so an attempt whose node died after its turn was stored left nothing a retry could find. The record is written before the turn is sent.
- One admission path for both `say` overloads rather than an unconditional stored-key check in the turn builder: the builder check runs on the request thread and would have surfaced a duplicate as an exception, and it would not wait for a duplicate still running on this node.
- Caps count `createdBy` rather than `userId`: it is stamped from the authenticated principal, so it cannot be chosen by the caller and engine-minted schedules are not counted.
- The reset is its own endpoint (`/reset-conversation`, like `/enable`, `/retry`) rather than a flag on PUT, which would have changed the interface signature every caller uses.

### Behaviour changes an upgrader will notice

- A leap-day cron keeps firing; a schedule whose cron has no next fire is disabled with `no-next-fire`.
- Creating or enabling beyond 200 own / 10000 total enabled API-created schedules answers 429.
- A timed-out scheduled turn is cancelled, so it stops at its next task boundary.
- New indexes are created on first start (`idx_schedules_due_by_status` on Mongo, `idx_schedules_due_live` on Postgres).
- `POST /schedulestore/schedules/{id}/reset-conversation` is new; `ui/manager/src/test/mocks/openapi-operations.json` lists it.
- A `conversationStrategy: new` retry continues the conversation its occurrence's first attempt started instead of starting another; a retry whose conversation is still busy with that attempt is recorded `FAILED` and retried. The schedule tables gain two fire-path fields (PostgreSQL: `occurrence_run_id`, `occurrence_conversation_id`, added on start).
- A scheduled turn's give-up time and the fire's wait now count from the poller's dispatch, so a slow conversation start shortens the turn's share of `eddi.schedule.fire-timeout` instead of extending the fire past it.

### What is left

Rating alerts for test conversations and the MCP option for the reset are not done here. The Platform Operator prompt is deliberately not changed on this branch: the operator files are collected into one dedicated change for the whole fix series. That change has to teach the operator three things from this branch — the `429` answer with code `SCHEDULE_LIMIT` (and the `eddi.schedule.max-per-owner` / `max-total` limits behind it), the `disabledReason: "no-next-fire"` state, and `POST /schedulestore/schedules/{id}/reset-conversation` with its recovery use (a write: not for the allow-list without its own review).

The idempotency of a scheduled turn lasts as long as its key: `eddi.turns.idempotency.ttl-seconds` (600) and the conversation's last 50 steps; with the TTL at `0` it is off. A retry later than that runs again.
