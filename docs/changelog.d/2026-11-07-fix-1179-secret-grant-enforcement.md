## 🔒 fix(secrets): enforce agent grants where a secret is resolved (#1179) (2026-11-07)

**Repo:** EDDI (`fix/1179-secret-grant-enforcement`)

### What changed and why

A secret's agent grant (`allowedAgents`) was checked only when an agent was deployed. On a cluster the grant-impact scan that guarded secret creation missed two deployments: one that passed the deploy gate on another node after the scan had read the shared records, and an `autoDeploy=false` deployment on another node, which has no record. Both could resolve a secret their grant left out, from the vault or from the resolver's cache. An agent deployed before its grant was narrowed also kept resolving until it was redeployed.

The grant is now also checked **at every resolution**, for the agent the value is resolved for, so it holds on every node, whatever any scan saw.

- **`SecretAccess`** (new) names on whose behalf a reference is resolved. `SecretResolver.resolveValue` and `resolveSecrets` no longer have an overload without one, so every call site had to decide, and the compiler keeps it that way. There are three kinds. **agent**: the grant must list the agent or be open. **no agent**: the grant must be open to every agent, the rule `ServiceJudgeVaultGrants` already applied to group judges. **outside agent grants**: deployment infrastructure the grant never governed, so the grant is not read. An agent access without an id fails closed.
- **Cache.** The resolver caches the grant next to the plaintext, both keyed on the secret, and checks the grant for the asking access *before* the cache on every resolution. The cache is keyed on the secret, not the agent, so the guarantee is about authorization: under `enforce`, an agent the grant in effect on that node leaves out cannot get the value from the cache. A grant write now evicts the cached grant, locally and through the cluster's secret-changed event (a node that misses it keeps the grant for at most the cache TTL); a grant-only write evicts only the grant (`SecretResolver.invalidateGrant`), so it closes no MCP session and drops no model: `PUT …/grant` deliberately did not before, and the append endpoint (`VaultGrantService`) never had to.
- **Downstream caches.** `SecretResolver.requireGranted` checks the grant without resolving. It runs before each cache that holds a client built from a secret: `ChatModelRegistry` (sync and streaming), `EmbeddingModelFactory`, `EmbeddingStoreFactory`, MCP tool assembly (`discoverTools`, `resourceBridgeTools`), A2A discovery and `ConnectionResolver` (before a cached OAuth token is handed out). The old `VaultGrantChecker` Javadoc gave the `ChatModelRegistry` cache as the reason resolution-time checks were impossible. That is now covered.
- **Fail closed.** A grant that cannot be read is refused at resolution (the deploy gate still lets unreadable metadata through). A missing secret stays unresolved when the resolver itself is asked; before a downstream cache (model, store, connection) it is refused as `SecretMissingException` under `enforce` and `warn`, so a cached client cannot outlive its secret — a 400 configuration error, not counted as a refusal. `eddi.vault.grant-enforcement` governs the grant check: `enforce` refuses, `warn` logs once per secret and asker (per hour), `off` reads nothing. The new counter `eddi.vault.grant.refusals` counts refusals. The new `ConnectionException.Reason.SECRET_NOT_GRANTED` and `SecretNotGrantedExceptionMapper` map a refusal to 403; the knowledge-base inspection, search, evaluation and delete endpoints answer 403 instead of a 502 that blamed the provider.
- **Where a refusal lands.** The LLM task, HTTP calls and connections fail the turn. A refused cascade step escalates to the next step; the judge's refusal fails the turn. An MCP server or A2A peer whose key is refused is left out of the agent's tools and logged. A guardrail whose model key is refused is undecided, so its `failMode` applies; the refusal is logged in full. A parser's semantic fallback whose embedding key is refused gives no match and leaves its embedded examples untouched for the agents that are granted.
- **The impact scan is advisory.** `VaultGrantImpactAnalyzer.refusalToCreate` is now `warningOnCreate`. A secret create no longer answers 409. It succeeds and carries a `warning` field (an `X-Eddi-Warnings` header on the space endpoint) naming the deployed agents the new grant leaves out. `GrantImpact.complete()` is documented as "every source was read", not "every deployment was seen". The grant endpoint's warning no longer says those agents "keep running".

### Call-site decisions

| Kind | Call sites |
| --- | --- |
| agent | `LlmTask` (all six model builds), `CascadingModelExecutor` (steps and judge; a judge refused its key now fails the turn instead of falling back to the heuristic), `GuardrailModelClient`, `ToolResponseTruncator` via `ToolLoopRunner`, `ConversationSummarizer`, `DreamService`, `ApiCallExecutor` (body, path, headers, query, `${connection:}` headers), `McpToolsProvider`, `McpCallsTask`, `A2AToolsProvider`, `RagContextProvider`, `ConversationTitleService` (LLM titles), the parser's `semanticFallback` (`InputParserTask`) |
| no agent | knowledge-base ingestion and document delete (`RagIngestionService`, `IngestionPipeline`), `KnowledgeBaseInspector`, the editor's MCP discovery probe (`RestMcpCallsStore`), `ServiceConvergenceJudge`, `LessonConsolidationService`, group window and stance summaries |
| outside agent grants | `OutboundHttp` proxy credentials, the `web_search` Brave key (deployment configuration), `SystemMailer`, `AlertSenders`, `ChannelTargetRouter`, `RestChannelIntegrationStore`, the email-channel transport, the OAuth token endpoint (`OAuthTokenService`, `RestConnectionAuthorization`; the client secret or, for JWT bearer, the private key), and the shared MCP and A2A sessions *after* the agent check at tool assembly |

**Behaviour change:** ingesting into a knowledge base whose embedding or store key is granted to specific agents only is now refused. Grant such a key to `["*"]` and restrict it with `allowedHosts`. Channel integrations and alert rules, which editors also author, stay outside agent grants for now. Moving them to the "no agent" rule would cut off existing channels whose tokens are restricted, so it needs save-time validation first (follow-up).

- **Bound to the credential, checked at the call** (review round on PR #1463). The model, embedding-model, vector-store, MCP and A2A caches are now keyed on the configuration with its `${vars:…}` expanded, and that one expansion is what the grant is checked against and the client is built from: a variable repointed to another secret is another key, never a hit on a client built with the old one. MCP tool executors (cached and shared) are wrapped per agent so each call reads that agent's grant again; A2A task calls resolve their credential for the calling agent instead of outside grants. A connection, MCP or A2A credential whose `${vars:…}` no longer resolves is refused rather than checked vacuously; a variable holding another variable is expanded to the final credential (`GlobalVariableResolver.expandFully`) before the cache key and the grant check are taken from it. The editor's MCP probe refuses `${connection:…}`.
- **Knowledge-base work.** Deleting a file and removing a source check the store grant before any state changes (the source removal is refused with 403 before the configuration is saved); an ingestion run re-reads the grant for the model and store it holds, and a refusal ends the run as `FAILED` with the grant's message instead of being counted as one failed document; knowledge-base search checks the store grant before paying to embed the query. A run re-checks the grant of the store and model it holds against the binding they were built from (not a fresh expansion), before every store write and delete; a run refused a grant reconciles no deletions, so a document it could not process is never tombstoned as missed. A source removal whose cleanup is refused after the save keeps the uploaded files.
- **Refusals are not blips.** `DreamService.isTransientLlmFailure` never classifies a grant refusal as transient, so Dream and lesson consolidation report a refused key as a failure even when its name contains `429` or `timeout`. A summarization retry asks the registry for its model on each attempt. An HTTP call whose key is refused is refused at the HITL gate, before a human approves it. A guardrail reprompt's refusal goes through the reprompt failure path.
- **Races and edges** (a later review round). The resolver binds its grant check to the value it returns: a value read while that secret was invalidated is not released on the earlier check, but resolved again (at most three attempts, then left unresolved); other secrets' invalidations, such as a bulk grant edit, do not count, and a resolution that reads no grant is not retried. A resolution also waits out an invalidation of its secret that is part-way through its evictions (value gone, old grant still cached), and a value or grant read across an invalidation is never cached, not even momentarily (an atomic conditional insert instead of put-then-remove). The one window left is between a vault write and its invalidation call, which any cache in front of the vault has. `expandFully` stops at 64 KB, checked while each pass is built (`resolveValueWithin`), so a variable that repeats its own reference cannot grow exponentially; the unfinished expansion is refused wherever a grant is checked. A2A Agent Cards are evicted whenever a connection or a vault value changes, locally or through the cluster event (a card fetched across the change is never published, by an atomic conditional insert, and every card carries the eviction generation it was published under, so a reader rejects one that slipped in while an eviction ran), so a card fetched with a rebound connection's old secret is not served. The connection registry and the vault tell the A2A card cache when an invalidation starts, before anything is evicted, and when it has finished; no card is published or read in between, and A2A discovery reads the grant again when a credential changed while it ran, taking the peer's tools back out on a refusal. The expansion budget counts the literal text between references too. A pre-cache grant check (`requireGranted`) waits out an invalidation of its secret that is part-way through and, under `enforce`, refuses with the transient `SecretChangingException` (503, not counted as a grant refusal; `ConnectionException.Reason.SECRET_CHANGING` on the connection path) if it does not settle, and its grant read is bound to one settled state the way a resolution is, retrying when an invalidation started during the read. An A2A card's cache key includes the credential references its `${connection:…}` names, so a rebinding is another key even on a node that only reloaded the connection when its entry expired. An MCP server or A2A peer whose apiKey cannot be expanded fails alone instead of ending discovery. A Dream citation retry refused a secret fails the cycle; the classifier checks the whole cause chain for a refusal before any message. An ingestion run refused after the embedding call counts the embeddings it paid for, and an unreadable file whose cleanup is refused is one failed document, not two.

**Manager:** the grant dialog's warning and two doc comments said narrowed agents "keep running". They now say that under `enforce` the agents lose access — on this node at once, on the others as the change propagates — in all 11 locales. **Platform Operator:** the prompt now explains runtime grant refusals. Revision bumped.
