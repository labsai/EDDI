## ✨ feat(llm): `converse_with_agent` hands files to the delegate — `documents.sharing.delegation` (2026-11-21)

**Repo:** EDDI (`feat/doc-delegation-attachments`) — work package WP-1.2 of the PDF documents plan. Depends on WP-0.1 (`documents` config foundation) and WP-1.1 (`AttachmentShareService`). Off by default: an agent that configures nothing gets exactly the three-argument tool it had.

### What changed and why

An agent could delegate to another agent but could not give it the PDF the user had uploaded. With `documents.sharing.delegation: true` on its LLM task, `converse_with_agent` takes a fourth, optional argument, `attachments`: names of files of the calling conversation. The delegate receives them as if its own user had attached them.

- **The first live `documents` keys:** `sharing.delegation`, `sharing.maxFilesPerShare`, `sharing.maxSharesPerTurn`, `sharing.maxDepth` (`DocumentsConfigValidator.LIVE_KEYS`). Every other key is still refused at save; `sharing.handoff` is now the example in the docs and tests.
- **Operator bounds** `eddi.documents.sharing.max-files-per-share` (5), `.max-shares-per-turn` (10), `.max-depth` (3), each with a **built-in bound** that applies when the property is unset (`DocumentBounds.BOUND_DEFAULTS`). Without that, the bound properties being commented defaults would have left the counts unbounded. A bad value falls back to the built-in bound with a WARN. Each property is looked up by its own constant, so `ConfigurationReferenceCoverageTest` sees them.
- **`ConverseWithAgentAndFilesTool`** (new): the same tool name with the fourth parameter. langchain4j reflects one specification per `@Tool` method, so the argument cannot be conditional; `DynamicAgentToolsProvider` assembles exactly one of the two classes. The four-argument class wraps the ordinary `ConverseWithAgentTool`, whose body moved into a package-private `converse(…)` both call; the three-argument `@Tool` method and its specification are unchanged.
- **Gate (I8):** the four-argument class only when the effective `sharing.delegation` is on, `allowDelegation` is on, and the conversation's **memory** shows a stored file on this or an earlier turn (the scan that gates `readAttachment`). Building the tools never reads the attachment store; only a call with `attachments` does.
- **`AttachmentShareBinding`** (new, per turn, bound to the calling conversation's memory): resolves the names against the conversation's listing (built on demand, minus withheld files), calls `AttachmentShareService.share` with `ShareReason.DELEGATION` and the full `ShareParties`, and stores the `attachments:shared` rows.
- **Target rule (I1):** files go only to a conversation this conversation started. The tool records every conversation it starts under the new step key `delegation:started` (`MemoryKeys.DELEGATIONS_STARTED`) — only while `sharing.delegation` is on, so an agent that configures nothing stores nothing new. A model-supplied `conversationId` that is not recorded there gets every file refused (`Refusal.TARGET`), no store read and no grant; the message is still delivered and the result says why.
- **On the delegate's turn:** each shared file goes on the message turn's context as `attachment_<n>` = `{storageRef, fileName}`, the shape a client's stored reference has, so the delegate's own pipeline resolves it against its grant and its forwarder renders it. Not on the start context, which reaches step 0 only.
- **Share depth:** a new reserved context key `attachmentShareDepth` (`ClientContextGuard.RESERVED_KEYS`), set to the caller's depth + 1 when something is shared and read back like `delegationDepth` (current step, else the deepest earlier step). A→B→C→D at `maxDepth` 3: D cannot pass the file on.
- **Per-call cap:** `min(maxFilesPerShare, eddi.attachments.max-per-turn)`, since the delegate's turn takes no more. The result names the cap when it refused a file.
- **The result** leads with what was shared and what was refused and why, then the delegate's answer.
- **Name-keyed switches extended:** `ToolObjectReflector.sourceForBuiltInTool` (source `dynamic`, so `requireApproval: ["dynamic:*"]` still gates it and `exempt: ["builtin:*"]` does not un-gate it), `ToolNameResolver.canonicalForClass` (slug `converse_with_agent`) and `AnswerToolConfigValidator.ENGINE_TOOL_CLASSES`. The class is `@Vetoed`, so `ToolCacheService` never caches it.
- **Wiring:** `AgentOrchestrator` field-injects `AttachmentShareService`, `DocumentSettings` and `eddi.attachments.max-per-turn` and passes them to the provider as `DynamicAgentToolsProvider.FileSharing`. Under direct construction they are null, which means the three-argument tool.

### Design decisions

- **`shareTo(target, targetAgentId, names)`** takes the target agent id beyond the plan's signature: `ShareParties` and the step records need it.
- **The target check lives in the binding**, not only in the tool, so no caller of `shareTo` can send files to a conversation this one did not start. The plan's "matrix row" for it is therefore in `ConverseWithAgentToolAttachmentsTest`, not in `AttachmentShareAuthorizationMatrixTest`, which tests the service.
- **A refused target delivers the message without files** rather than refusing the call, following the plan's wording ("the `attachments` argument is refused").
- **`attachmentShareDepth` carries no chain ceiling** (unlike `delegationDepthMax`): each hop applies its own effective `maxDepth`, which the operator bound caps.
- `InMemoryAttachmentStore` (the WP-1.1 test helper) is now public so the LLM-module tests use the same owner-or-grant fake.
- **Platform Operator:** no change here. The plan defers the operator text for phases 0–2a to WP-2a.7, so there is no `operator-revision.json` bump. No MCP tool or UI change.
