## 🐛 fix(webhook): the replay-protection cache could evict live keys, was per node, and a few edges leaked or orphaned (2026-10-24)

**Repo:** EDDI (`fix/webhook-dedup-replay`)

### What changed and why

Review of the signed inbound webhook channel (#1059) found that its de-duplication - the only replay protection of the `github` and `generic-hmac` schemes, and a second line for `eddi-v1` - was weaker than documented.

- **Dedup cache sizing and admission.** `webhook-event-dedup` had no size entry in `CacheFactory`, so it inherited the 1,000-entry default and was shared by every webhook integration, each delivery storing up to two keys. About 500 deliveries in ten minutes from any one integration evicted another's keys, after which a captured request ran again. The cache now has its own entry and is rate-sized like the A2A nonce cache (100 keys per second over the 10-minute window, factor-two head-room: 120,000 entries), and the handler **refuses instead of evicting** (an evicted key is a replayable request, a refused delivery is only a retry), per integration so that one sender cannot push the others out:
  - Each integration has its own budget, `platformConfig.maxDeliveriesPerWindow` (default 3000 deliveries per 10 minutes, validated 1 to 100000 at save), counted over a rolling window of 11 one-minute buckets (longer than the 10-minute key lifetime, so a delivery is counted as long as its keys exist). A delivery that is not accepted (429, 503, ...) gives its slot back, so a sender looping on a quota refusal keeps seeing the real refusal. The counters are a bounded Caffeine cache that expires idle integrations.
  - From half capacity, an integration above its fair share (half the cache divided by the active integrations, counting only those with 50 or more deliveries in the window, so throwaway integrations cannot shrink anyone's share) is refused even inside its own budget.
  - From 90% of capacity every new delivery is refused, whatever its integration holds - a last resort that keeps the cache clear of eviction.
  - Repeats of remembered deliveries are always answered, and the repeat check runs only when a refusal is pending, so an admitted delivery costs no extra cache read (in a cluster, no extra NATS round trip).
  - Refusals are their own metric outcome, `refused_capacity` (`metrics.md`, dashboard), and the `WARN` is limited to once a minute per integration. `ICache.size()` stays a cheap estimate; the new `ICache.sizeExact()` sweeps expired entries and is read only once the estimate reaches the threshold, so a refusal cannot outlast the data.
  - In a cluster the budgets and the thresholds are per node: the counters are node-local and the cache size read is the node-local view (documented).
- **Cluster.** `webhook-event-dedup` joins `slack-event-dedup` in the shared `DEDUP` NATS KV bucket (same 10-minute TTL), so a replay is caught on whichever node it hits. With NATS unreachable each node falls back to its own cache, as for Slack.
- **Unsigned routing headers.** Binary-mode `ce-type`/`ce-id` and the plain-mode event-type header are outside every scheme's MAC. The replay key is already derived from the MAC alone, so within the window the same signed body is a duplicate whatever header it arrives with (now covered by tests at handler and endpoint level); the page now says plainly that routing headers are unsigned, what that means (tampering in transit can re-route a body without breaking the signature) and what to do (TLS, route on a field of the signed body). No wire-protocol change and no new signing scheme.
- **Orphaned conversations.** A `429` (or any refusal) from the turn after `startConversation` left one empty conversation per retried delivery. The conversation just created is now ended when its first turn is refused; a correlated conversation is kept, since the retry reuses it.
- **Weak or plaintext signing secrets.** Save-time validation already requires a vault reference, but a ZIP import or direct store write bypasses it, and no length was checked anywhere. The router now refuses to hand the verifier a plaintext secret, a reference that did not resolve (left unchanged by resolution, also with surrounding whitespace) or a resolved one shorter than 16 characters; the verifier independently rejects anything still containing a `${vault:` reference (the integration answers `401`, with one `WARN` per integration).
- **Id probing.** An unknown integration id answered `404` before the signature was looked at. It now answers `401` with the same body as a bad signature (the log keeps the distinction). The Slack endpoint likewise answers a uniform `403` for anything it cannot verify.
- **Two meanings of `409`.** The body now carries `reason`: `in_progress` (retry in 5 seconds) or `awaiting_approval` (a human has to decide). The status code is unchanged.
- **Behaviour change for 6.6.0 installs:** a webhook integration whose vault secret is shorter than 16 characters used to work and now answers `401` to every request (as does a plaintext secret that reached the store through import). Find them with the log line "signing secret is shorter than" (one WARN per integration version, repeated after a vault secret change) and rotate to 32 random bytes. Saving such a secret is now refused with 400 when it already exists in the default-tenant vault; references to another tenant are not resolved at save time (that would let any editor probe other tenants' secrets), so the router's runtime check is what covers them.
- The Platform Operator prompt now knows the new answers (unknown id 401, weak secret 401, capacity 503, 409 `reason`), operator revision bumped.
- Group targets still receive only the rendered input, not the event map; documented, not changed.

### Design decisions

- No new property: the capacity is derived from the window like the nonce cache's, and the refusal threshold follows from it. A property would let an operator size the cache below the traffic it must hold, which is the defect being fixed.
- The check for a quota refusal before creating the conversation was rejected: the API-call quota has only an atomic acquire, no read-only peek, and adding one would race. Ending the orphan is the safe equivalent (each attempt still spends a conversation slot).
- The shared bucket is not size-capped and the node-local cache that stands in for it is, so in a cluster the thresholds read each node's own view: a sender spread over N nodes may hold N times its budget in total. Reading the exact cluster-wide size is not possible (the bucket cannot enumerate its keys).
- Per-integration admission rather than a global refusal: a global threshold let one integration with a valid secret push every other integration to 503. The fair share counts only integrations with 50+ deliveries because the roles that can create integrations (`eddi-admin`, `eddi-editor`) could otherwise shrink everyone's share with many one-delivery integrations.

### Tests

- `WebhookEventHandlerTest`: an integration over its budget gets 503 while another still gets 202 (and a remembered repeat is answered); the window rolls over after 11 minutes and a delivery still counts at 10; from half full only the integration above its fair share is refused; the 90% hard stop refuses an idle integration; throwaway one-delivery integrations do not shrink another's share; an admitted delivery performs no extra cache read; refused deliveries do not spend the budget; the WARN is throttled to once a minute; `refused_capacity` is its own outcome; the refused turn ends its new conversation with its own reason; both `409` reasons; the same signed body under another event type is a duplicate.
- `RestWebhookChannelTest`: unknown or malformed id answers identically to a bad signature; rerouted replay is a duplicate; `reason` in the body and no `Retry-After` for `awaiting_approval`.
- `CacheFactoryTest`: explicit, window-derived size; shared through the `DEDUP` bucket with the matching TTL. `CacheImplTest`: `sizeExact()` ignores expired entries.
- `ChannelTargetRouterWebhookTest`: plaintext and 15-character secrets are stripped, a 16-character one is kept; the weak-secret warning is logged once per refresh cycle and again after a vault change.
- `RestChannelIntegrationStoreValidationTest`: a short existing vault secret is refused at save, other-tenant references are never resolved, `maxDeliveriesPerWindow` is validated.
