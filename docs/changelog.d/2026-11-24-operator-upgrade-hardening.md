## 🛠️ fix(operator): upgrading an older operator no longer asks for a grant, keeps a trimmed prompt or shows a stale banner (2026-11-24)

**Repo:** EDDI (`fix/operator-upgrade-hardening`)

### What changed and why

Upgrading a Platform Operator provisioned by an older Manager went wrong in five
ways at once, observed on two 6.7.1 deployments. Both operators had
`promptBodyIsDefault: false` because their instructions had been trimmed to fit
6.7.0's 100k setup-api cap.

1. **The upgrade dialog preselected "Keep the current text" for a body that was
   only a trimmed or older default.** One body differed from the new default by
   removals alone. The other differed by removals plus seven lines of an older
   default's wording. The dialog now reads the stored text line by line
   ([`prompt-lineage.ts`](../../ui/manager/src/lib/operator/prompt-lineage.ts)). A
   line is the default's when it is in the new default or in any default the
   Manager ever shipped. If every line is the default's, "Replace with the new
   default" is preselected and the dialog says why ("only removes lines", "keeps
   wording from an earlier default"). Any other non-blank line, however short,
   counts as the admin's own, and "Keep" stays preselected. The test is set
   membership, not a diff: a diff counts a moved line as added, and `diffLines`
   reports everything as changed past 2,000 lines. The list of shipped lines,
   [`operator-prompt-lineage.json`](../../ui/manager/src/lib/operator/operator-prompt-lineage.json),
   holds FNV-1a hashes of 2,136 lines. It was generated by
   [`gen-operator-prompt-lineage.mjs`](../../ui/manager/scripts/gen-operator-prompt-lineage.mjs),
   which renders both scopes' default body at each of the 149 commits that touched
   an input of it (`system-prompt.ts`, `tool-scopes.ts`, the model suggestions and
   the provider catalogue, old and new paths), loading each historical module graph
   straight from git. 147 of them rendered; two predate the default-body export. The list is not
   part of `operatorProvisioningSource()`, so the revision is not bumped.
2. **The new operator agent did not inherit the old one's vault grants.** The
   upgrade therefore stopped on the grant dialog, which offered "Allow every
   agent". Before the first deploy, activation now carries the grants over
   ([`carry-grants.ts`](../../ui/manager/src/lib/operator/carry-grants.ts)). It
   covers every default-tenant secret whose grant names the predecessor, plus any
   secret the new agent references whose fresh read names it. Each one is the
   backend's one-agent append, never a list replace and never `*`. It runs only for
   a predecessor that passed the trust checks, because `platform.operator` is
   editor-writable. When it cannot run (a non-admin, the vault off), the existing
   dialog asks as before. For the operator, that dialog no longer offers "allow
   every agent" at all: the new `offerAllowAll: false` is passed by activation, by
   Turn back on, and by the operator page's two "Fix grant and deploy" buttons.
3. **A permanently deleted agent stayed on every secret's `allowedAgents`.**
   `RestAgentStore.deleteAgent` with `permanent=true` now calls
   `VaultGrantService.revokeDeletedAgent`. It sweeps every vault tenant
   (`ISecretProvider.listTenants`, which reads the DEK registry), and uses the same
   compare-and-set and retry as the append, with an audit entry
   (`vault.grant.revoke-deleted-agent`). A soft delete keeps the grants, so a
   restored agent is still granted. It never widens a grant: when the deleted
   agent is a grant's only id, the id stays, because an empty list means every
   agent. [`docs/secrets-vault.md`](../secrets-vault.md) describes it.
4. **The operator page showed "switched on, but its agent is not deployed" during
   and after the upgrade.** The upgrade undeploys and deletes the agent the cached
   config still named, and the predecessor's status was refetched in parallel with
   the config. On success, activation now writes the new config into the cache
   before invalidating. While an upgrade runs, the page does not render the health
   banner.
5. **`quarkus.smallrye-openapi.security-scheme-name` was `Keycloak OIDC`.** An
   OpenAPI component key may not contain a space, so swagger-parser warned on every
   boot when `McpApiToolBuilder` parsed the deployment's own spec. The name is now
   `KeycloakOIDC`. Nothing in the repository referenced the old name. An external
   client generated against the old spec that names the scheme would need to
   regenerate.

### Tests

- `OperatorPage — the operator upgrade, end to end against a stateful backend`
  (`operator-upgrade-refresh.test.tsx`) runs the real activation hook. It asserts
  Replace is preselected, the grant is carried with no dialog, and neither health
  banner ever mounts (a `MutationObserver` runs from the first click). Both halves
  of fix 4 and the grant carry-over were mutation-checked against it.
- `prompt-lineage.test.ts` and the new cases in `operator-upgrade.test.tsx` cover
  the preselection, using lines from a real earlier rendered default. The list
  must be regenerated when the revision moves past `throughRevision + 1`.
- `carry-grants.test.ts`, and `use-deploy-with-grants.test.tsx` for
  `offerAllowAll`.
- Backend: `VaultGrantServiceRevokeTest`, four new `RestAgentStoreTest` cases,
  three `VaultSecretProviderTest` cases for `listTenants`, and
  `OpenApiSecuritySchemeNameTest`. All were mutation-checked.
- The real-backend `Operator Activation E2E` job gains the upgrade scenario (the
  second test in `operator-activation.operator.spec.ts`). It rewrites the activated
  operator's config to an older revision with a trimmed prompt and a vault key
  granted only to its agent, then upgrades it in the browser. It asserts all four
  field symptoms, including the deleted agent leaving the grant. Its compose
  overlay now turns the vault on. Run locally against an image built from this
  branch, both tests in the tier pass. Against `labsai/eddi:6.7.1` the upgrade
  test fails and the activation test passes.

### What's next

- Ids that deleted agents already left on grants before this change are not
  backfilled. An admin removes them on the Secrets screen.
- When the operator PR that bumps `operator-revision.json` past `throughRevision + 1`
  lands, it must run `node scripts/gen-operator-prompt-lineage.mjs`.
