## feat(attachments): a streaming store API on the blob backends (2026-11-22)

**Repo:** EDDI (`feat/doc-streaming-store`). This is work package WP-4.1b of the PDF documents plan, the fourth package in the serial chain of attachment-store edits (after WP-2a.3, before WP-5a.1). It depends on WP-4.1a (#1472, the blob backends) and WP-2a.3 (#1511, quota reservations). Nothing user-visible: no code path stores a large file yet. Large uploads (WP-4.5) switch that on; the windowed PDF reader (WP-4.2) and the personal library (WP-5a.1) build on it.

### What changed and why

The attachment stores can now write and read a file without ever holding it in memory whole, while the `byte[]` methods keep working exactly as before for small files.

- **Each store is a metadata layer over a blob backend.** Owner, grants, quotas, lineage and *where the bytes are* stay in the database as before; a file larger than `eddi.attachments.max-size-bytes` keeps its bytes in the blob backend of WP-4.1a (`gridfs` on MongoDB, `pg-chunks` on PostgreSQL). On PostgreSQL the row gains `blob_backend`, `blob_key` and `quota_mode`, and `data` becomes nullable. On MongoDB such a file is an empty GridFS file of the same `attachments` bucket whose metadata names the locator and the size, so every existing query of the bucket finds it unchanged; every place that read the GridFS length (listing, usage, conversion, lineage caps) now reads `sizeOf(file)`.
- **`IAttachmentStore`** gains `store(InputStream, declaredLength, …, reservationId, QuotaMode)`, `open`, `openRange`, `materialize`, `pendingTombstones` and `sweepTombstones`, a mode-aware `reserve(…, QuotaMode)` and `AttachmentTooLargeForMemoryException`. `QuotaMode` is `STANDARD` (today's rules) or `LARGE_PER_USER`.
- **Streamed write.** The quota is held by a reservation from before the first byte — the caller's (checked live, of this conversation, user and mode, and large enough, before a byte is read) or one the store takes (`eddi.attachments.blob.upload-ttl-seconds`, 1 h). `StreamedUpload` reads the first 8 KiB in a loop until full, judges the declared type on them with `MimeValidator`, hands them out again in front of the rest, and computes the SHA-256 as the bytes stream; a stream longer or shorter than declared fails. A small upload is read whole (bounded by the memory guard, as every upload always was) and stored inline; a large one is `put` to the backend holding no lock and no transaction, then recorded and converted — in one transaction on PostgreSQL, blob-visible-then-convert on MongoDB. The reservation is used up either way: converted, or released on failure. Any failure deletes the object and the row.
- **`load()` refuses any file above `eddi.attachments.max-size-bytes`** with `AttachmentTooLargeForMemoryException`, after authorizing and without reading it, so no later code path can pull a large file onto the heap (plan I7). It decides on size, not location: an inline file above a guard lowered later is refused too, and a located one within a guard raised later loads. `open`, `openRange` and `materialize` answer strangers exactly as `load` does.
- **Backend failures are store errors, never "not found":** an unreachable backend, and an object missing under a key a row still names.
- **Deletes and tombstones.** A delete records the bytes of a located file as a tombstone in the same commit as the row delete (MongoDB: before it), then deletes them from the backend; if the backend cannot, the tombstone stays and is retried with a back-off. An upload writes an *intent* tombstone before its first byte, due a minute after its reservation expires, and removes it when it records the file, so the object of a writer that died mid-upload is cleaned up too. The sweep deletes an object no file references and keeps one a file does. It runs a few tombstones at a time after every delete and streamed upload — no scheduler. `pendingTombstones(ownerKey)` lets erasure report what is still waiting (WP-5a.4).
- **`LARGE_PER_USER`** bytes count against the user's byte quota only, never the conversation's — in `usage()` for stored files and for reservations, on both stores — while the file still counts toward the conversation's file count. It needs a known user.
- **`BlobBackendSelector`** resolves `eddi.attachments.blob.backend` (`auto` | `gridfs` | `pg-chunks`; `s3` and `pg-largeobject` refused as not available in this version) and picks a reader by the backend a locator names. `DataStoreProducers` produces it with only the configured database's backend, created on first use; `BlobBackendStartupCheck` fails startup on an impossible combination (`gridfs` on PostgreSQL, `pg-chunks` on MongoDB) with the reason.
- **Meters:** `eddi.attachment.blob.bytes{backend,direction}` and `eddi.attachment.blob.tombstones{backend}`, in `docs/metrics.md` and the full dashboard (its split Kubernetes copy regenerated by `scripts/sync-monitoring-assets.py`).
- **Docs:** `docs/attachments-guide.md` (new "Storage backends" section), `docs/configuration-reference.md` and `application.properties` (`eddi.attachments.blob.backend`, `eddi.attachments.blob.upload-ttl-seconds`; the "not used yet" note on the chunk size is gone).

### Design decisions

- **Tombstones instead of a soft-delete flag.** Marking the row deleted would need a filter in every query of two 1,400-line stores. A tombstone written with (PostgreSQL) or before (MongoDB) the row delete gives the same guarantee — no object outlives its file unnoticed — and leaves every read path as it was.
- **The sweep is opportunistic,** after deletes and streamed uploads, following the reservation sweep's precedent; no schedule and no change to `ScheduleFireExecutor`.
- **The writer and the sweep cannot both act on one object.** PostgreSQL: the sweep locks a tombstone `FOR UPDATE SKIP LOCKED`, and the writer's transaction must remove exactly its intent tombstone or it refuses the upload. MongoDB: the sweep claims a tombstone with a lease by the server's clock, and keeps any object a file references. Both work on database time; an intent is due only after its reservation can no longer be converted.
- **A record whose outcome is unknown keeps its object.** A commit can fail after the server applied it, so a PostgreSQL `SQLException` while recording does not delete the object: it makes its tombstone due, and the sweep keeps the object if a row references it. A refusal (expired reservation, lost tombstone) still deletes at once. On MongoDB the tombstone a delete writes first falls due only after a claim period, so a sweep between the file delete and the object delete cannot drop it.
- **`STANDARD` refuses a file above the memory guard;** only `LARGE_PER_USER` may be larger. A caller's reservation must have the upload's quota mode, so a `LARGE_PER_USER` reservation (whose bytes the conversation never counted) cannot cover a `STANDARD` upload.
- **Platform Operator, MCP, UI: no change.** No endpoint, tool or designer key is added and nothing stores a large file yet. `operator-revision.json` is not bumped.

```decision-log
| 2026-11-22 | Attachments up to `eddi.attachments.max-size-bytes` keep being written inline (GridFS bucket / `BYTEA`); only larger ones go to the blob backend, and existing rows are not migrated | WP-4.1b streaming store (plan P17) | Writing every new file to the backend, or migrating existing rows |
| 2026-11-22 | A blob-backend object is deleted through a tombstone written with the row delete and swept opportunistically after deletes and uploads | WP-4.1b delete protocol | A soft-delete flag on the row (a filter in every query), or a scheduled sweeper |
```

### Tests

New `StreamingAttachmentStoreContract`, run against real databases and real backends by `GridFsAttachmentStoreIT` and `PostgresAttachmentStoreIT`: small streams stored inline and `open` equals `load`; large streams round-trip by hash through `open`, `openRange` (and its clipping) and `materialize`; `load` refuses a large file without reading it, and judges on size whichever way the guard moved; strangers are answered as by `load`; `STANDARD` above the guard, a mismatched type, short and long streams leave nothing; a caller's reservation is converted, one that cannot cover the upload (too small, another user, another mode) or has expired is refused before a byte is read, one that expires mid-stream leaves nothing; large uploads skip the conversation byte quota, count for their user, and count toward the file count; deletes remove objects, a backend that cannot delete leaves a tombstone the sweep retries; erasure removes large objects, and an erasure mid-upload leaves nothing; an upload in flight is not swept; the sweep deletes an orphan and keeps a referenced object; a failed sweep backs off; an unreachable backend and a lost object are store errors, not "not found"; and a 64 MiB upload and read through the real store in a child JVM with `-Xmx128m`. Unit tests: `BlobBackendSelectorTest` (every combination, the startup check), `StreamedUploadTest`, `BlobMetricsTest`, `QuotaModeTest`. The mutants run are listed in the PR.

### What's next

WP-4.2 (windowed PDFBox) reads large files with `materialize`; WP-4.5 accepts large uploads through the streaming `store` with `QuotaMode.LARGE_PER_USER` and must add a large-file maximum (with the user byte quota off, nothing here bounds a `LARGE_PER_USER` file); WP-5a.4 reports `pendingTombstones` in erasure.
