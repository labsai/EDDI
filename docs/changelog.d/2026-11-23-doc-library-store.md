## feat(attachments): library owners in the attachment store — promote, buckets, soft removal, erasure by owner key (2026-11-23)

**Repo:** EDDI (`feat/doc-library-store`). This is work package WP-5a.1 of the PDF documents plan, the fifth package in the serial chain of attachment-store edits (after WP-4.1b, before WP-5b.1). It depends on WP-4.1b (`feat/doc-streaming-store`, the streaming store). Nothing user-visible: no code path puts a file into a library yet. The library service and tools (WP-5a.2), the memory card (WP-5a.3), retention and erasure participants (WP-5a.4) and REST (WP-5a.5) build on it.

### What changed and why

The attachment stores can now hold a file that belongs to a user's personal library instead of a conversation, with every rule of the plan's step 2 enforced in both stores.

- **`IAttachmentStore`** gains `promote`, `moveOwner`, `listByOwner`, `getLibraryEntry`, `touchAccess`, `softRemove`, `restore`, `deleteByOwner`, `deleteLibraryDocument`, `expired` and `removedBefore`, and the quota scope `library`. New types: `LibraryEntry` (the store-level record; never returned by REST or a tool as it is), `LibraryMeta` (title, slug, agent scope, retention — bounded by its constructor) and `LibraryStoreSupport` (the owner check, the bucket lock, the quota rule, slug collisions, grant eviction and paging both stores share).
- **`promote` moves a root and its whole lineage** to an `OwnerScope.USER` owner; nothing is copied. Only the conversation that owns the file may promote it; a grantee, a stranger, a derived blob or a file already in a library is refused, and so is a `TEAM` owner (not available in this version). The promoting conversation keeps a grant (both shapes). `AttachmentOwnerChanged` is fired once, after the change committed — the first code that fires it.
- **Conversation-keyed methods leave a library root alone** (plan step 2). `delete` refuses it for every conversation, the origin included — on PostgreSQL the owner is read again under the root's row lock, on MongoDB under the root's source lock, so a concurrent promote cannot be undone by a delete; `deleteByConversation` skips it and its lineage and removes only that conversation's grant — on PostgreSQL it now locks the conversation's roots (in one order) before its DELETE, so it neither deadlocks with a promote that holds a root and then updates its views nor removes a root a promote moved meanwhile; on MongoDB every file is deleted only while it is still conversation-owned (one condition on the files document), so a promote that committed after the cursor read a root keeps it; `listByConversation` excludes it; `listAccessible` lists it through a grant only, and not while it is soft-removed; reads authorize a library root through a grant only, so the origin conversation's id is origin information, not ownership.
- **Buckets.** A library root and its media views no longer count in the conversation's or the uploading user's upload buckets (`usage()` filters on the owner scope, on both stores) and count in the library's instead: `eddi.documents.library.max-per-user` (50) and `.max-total-bytes-per-user` (2 GiB). A full library refuses with both numbers and never evicts. A media view of a library document is charged to the library under the library's bucket lock.
- **Lock order.** The library's bucket locks in the user place of the fixed order (conversation → user → team → source) under an id of its own (`library:<ownerKey>`); `AttachmentLockOrder.ordered` now breaks ties within one scope by id, so a write that ever needs two user-place locks takes them in one order.
- **In-flight views follow the new owner.** `storeDerived` used to fail with "the owner changed" when its root's owner changed between the read and the lock; it now starts over (up to three times) and stores the view under the owner the root has at write time, with that owner's buckets and locks.
- **Grants on a library root are a ring.** Past `eddi.documents.library.max-grants-per-document` (1,000) the oldest grant (by when it was first given; opening again does not refresh it, as the plan specifies) is evicted — in both shapes, legacy-only grants (of unknown age) first, never the grant just written — on `grantAccess` and `promote`. A conversation's own files are never evicted from.
- **Soft removal, restore, touch** by owner key; **`deleteByOwner` / `deleteLibraryDocument`** delete the library's roots, their lineage, the grants on them and (for the whole library) its reservations, record tombstones for located bytes under the library's owner key (so `pendingTombstones(ownerKey)` reports them) and fire one `AttachmentRootDeleted` per root. Every owner-keyed method matches library roots only: a conversation id passed as an owner key reads and deletes nothing.
- **`expired(now, limit)`** uses a document's own `retentionDays`, else `eddi.documents.library.retention-days` (365), counted from the last access; `0` never expires; `LibraryMeta` bounds a retention at 36,500 days, so the date arithmetic of either database never leaves its range. **`removedBefore(cutoff, limit)`** lists soft-removed documents for the purge.
- **Every owner-keyed query can use an index.** PostgreSQL's library quota count reads the roots by owner key (the partial library index) and their media views by root; MongoDB's owner-keyed filter names the `savedAt` its partial indexes are filtered on. The reaper's `expired` and `removedBefore` name no owner and scan the library roots.
- **Schema.** PostgreSQL: `ADD COLUMN IF NOT EXISTS` `library_title`, `library_slug`, `agent_scope`, `contributed_by`, `saved_at`, `removed_at`, `retention_days`; partial indexes `(owner_key, last_accessed_at)`, `(owner_key, removed_at)` and a unique `(owner_key, library_slug)` backstop, built CONCURRENTLY with the lineage indexes. MongoDB: the same names under `metadata.`, with partial indexes from `GridFsAttachmentStore.ensureLibraryIndexes()` on their own budget. No backfill: every existing row is conversation-owned.
- **Config.** `eddi.documents.library.max-per-user`, `.max-total-bytes-per-user`, `.retention-days`, `.max-grants-per-document` in `application.properties`, [`configuration-reference.md`](../configuration-reference.md) and `DocumentSettings.libraryLimits()`.
- **Docs:** [`attachments-guide.md`](../attachments-guide.md) gains "Library documents".

### Design decisions

- **`LibraryEntry` carries `filename` and `mimeType`** besides the plan's fields, so a library listing needs no per-document metadata read through a conversation that may hold no grant.
- **The store resolves the default retention** (`eddi.documents.library.retention-days`) when the reaper asks, instead of the saver writing it into each document: an operator who changes the default changes it for every document saved without its own. WP-5a.4 adds the save-time rules (`.retention-days.max`, `.retention.allow-unlimited`).
- **Slug uniqueness is the store's,** decided under the library's bucket lock, so two concurrent saves of "Annual report" get `annual-report` and `annual-report-2`, never the same name.
- **A soft-removed document keeps counting toward the library's quota** until it is purged: its bytes are still stored.
- **`moveOwner` shares promote's re-keying** and accepts only `USER` targets until the team library (WP-5b.1) opens `TEAM`.
- **No erasure participant here:** the plan assigns `libraryDocuments` / `libraryPendingBlobDeletes` to WP-5a.4, and nothing can create a library document before WP-5a.2. `deleteByOwner` and `pendingTombstones(ownerKey)` are what those participants call.
- **Platform Operator, MCP, UI: no change.** No endpoint, tool or designer key is added. `operator-revision.json` is not bumped.

```decision-log
| 2026-11-23 | A library document's default retention is resolved by the store when the reaper asks (`eddi.documents.library.retention-days`), not written into each document at save | WP-5a.1 library store | Storing the effective retention at promote, which freezes the default per document |
| 2026-11-23 | Library slugs are made unique by the store under the library's bucket lock (`-2`, `-3`, …) | WP-5a.1 library store | Suffixing in the library service, which is check-then-act across nodes |
```

### Tests

New `LibraryStoreContract`, run against real databases by `GridFsAttachmentStoreIT` and `PostgresAttachmentStoreIT`: promotion moves root and lineage and fires one owner change; the promoting conversation reads through its grant but neither lists nor deletes the document (nor a view of it); deleting the origin conversation keeps the document and removes only its grant while its own files still die; every refusal of `promote` (grantee, stranger, view, unknown, team, conversation owner, twice) moves nothing; the bytes move between buckets exactly (root, media and text views); a full library refuses with the numbers; a media view of a library document is charged to the library; grant eviction (oldest first, legacy-only first, never the newest, never on a conversation's file); listing by agent scope, recency and pages; `getLibraryEntry` per owner; slugs unique per owner; soft removal and restore; `deleteByOwner` and `deleteLibraryDocument` leave nothing and announce each root, and a conversation id as owner key deletes nothing; retention by own value, default and zero; `removedBefore`; `moveOwner`; and a view whose writer read the root as the conversation's and was held on the conversation's quota lock while the root was promoted — it is stored under the library and charged to it (the retry path). Unit tests: `LibraryStoreSupportTest` (eviction, quota, slugs, owners, lock tie-break, paging, `LibraryMeta` bounds), `DocumentSettingsDefaultsTest` (one block). The mutants run are listed in the PR.

### Known limits, stated

- **MongoDB grant eviction is not serialized:** two grants written at the same moment to a library document at its cap may each evict the other's (with the default cap of 1,000 this needs a thousand conversations opening it at once). PostgreSQL serializes eviction on the root's row.
- **A MongoDB promote that stops between re-keying the views and the root** (a node crash, a lost connection) leaves views keyed to the library under a root its conversation still owns; the conversation's cascade still deletes them by root, and promoting again finishes the move.
- **GDPR export** lists a conversation's files through `listByConversation`, so a promoted document drops out of its origin conversation's export; WP-5a.4's library export covers it.
