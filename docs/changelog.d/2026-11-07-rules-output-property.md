## 🐛 fix(rules): refuse unsupported deployment tags, quick-reply templating, property and dependency fixes (2026-11-07)

**Repo:** EDDI (`fix/rules-output-property`)

### What changed and why

- **Templated quick replies are now shown templated.** The output task stores each quick reply twice: in the `quickReplies:<action>` data entry and in the conversation output the client receives. `OutputTemplateTask` rendered only the data entry, so the client showed `Call {properties.agentName}` while the next turn's dictionary, built from the data entry, held `Call Ava`. A click on the button the user saw matched nothing. The rendered quick replies now replace the raw ones in the conversation output too, as rendered output texts already did. Quick replies sent in `context` are still shown as they arrived.
- **`deploymentContext` refuses `tagMatches`.** The condition read agent tags from an `agent:tags` memory key that nothing writes, and `AgentConfiguration` has no tags field, so a rule with `tagMatches` never fired. That included the Javadoc's own example, a safety rule meant to make production agents cautious. A non-blank `tagMatches` is now refused when the ruleset is read, with an error that names the rule and points to `contextmatcher`. The Manager's default for a new `deploymentContext` condition no longer carries the field. **Behaviour change:** a stored ruleset that uses `tagMatches` now fails to save or deploy until the field is removed. Such a rule never matched, so removing the field changes nothing at runtime.
- **A property instruction runs once per turn.** `PropertySetterTask` collected and applied instructions separately for each of the turn's actions. An instruction under `"*"`, or under two of the turn's actions, therefore ran once per action. For `scope: secret`, every run wrote a new vault slot. Only the last reference reached the step history, and conversation deletion sweeps only what the history holds, so the other slots stayed in the vault until a GDPR sweep of the user. Instructions are now collected across all of the turn's actions, without duplicates, and then applied once each.
- **`dependency` survives unnamed rules and requires `reference`.** It called `getName().equals(reference)` on every rule in the set, so a single unnamed rule anywhere caused a NullPointerException, and the turn failed, whenever any dependency was evaluated. `Rule.equals` had the same problem. Both comparisons are now null-safe. A `dependency` without a `reference`, which could only fail, is now refused when the ruleset is read. Rule names stay optional, and duplicate names stay supported.
- **Matcher semantics are pinned.** New `@Nested Semantics` tables in `ActionMatcherTest` and `InputMatcherTest` run the matchers against a real conversation memory. They pin that a comma list is an ordered, adjacent sublist, plus `empty`, `lastStep` on the first step, `anyStep` and `never`. The existing tests stubbed every lookup and asserted SUCCESS only, so they kept passing with `indexOfSubList` replaced by `containsAll`.

### Design decisions

- `tagMatches` is refused rather than implemented. Agent tags would be a new feature with no model field, UI or storage behind them, and a value the client sends can already be matched with `contextmatcher`.
- Instructions are collected first and then applied, instead of being remembered as applied across actions. The order is the turn's actions, then `setOnActions`, the same first-seen order as before.
