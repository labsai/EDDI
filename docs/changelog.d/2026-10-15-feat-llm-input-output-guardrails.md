## ✨ feat(llm): input and output guardrails on LLM tasks (2026-10-15)

**Repo:** EDDI (`feat/llm-input-output-guardrails`) — WS4 Phase 4a, executing the R0 spec of `planning/langchain4j-recommendations.md`.

### What changed and why

Only tool *results* were governed (`ToolResultGuardrail`). Nothing screened the user's message or the model's final answer — the largest governance gap (jailbreaks, PII leaking either way). An LLM task can now carry `inputGuardrails` and `outputGuardrails`: ordered lists of `{type, action, maxRetries, blockMessage, parameters}`. Actions are `block` (default), `redact`, `reprompt` (output: re-ask the same model, `maxRetries` default 2, clamped 0–5, then block) and `warn`. Built-in types: `prompt-injection` (input), `pii-redaction`, `regex-filter`, `max-length` (both), `json-object` (output). Nothing is on by default; a task without the lists never touches the guardrail service.

- **Input** guardrails run after prompt assembly and before the model is built, `preRequest` runs or the circuit breaker is consulted. A block answers the turn with the block message (output item marked as engine text, so later history leaves it out); the model is never called. Redaction rewrites what the model sees; memory keeps the user's text. Earlier user messages of the history window are re-screened silently every turn, so a message blocked/redacted on its own turn is not replayed to the model later (a guardrail can opt out via `screensHistory()`, meant for model-backed types).
- **Output** guardrails run right after `responseValidation`, in every branch — plain, streaming, tool loop, cascade — and on the HITL resume path. A block is served like a fallback (not parsed, not recorded as the model's response). A reprompt runs on the branch that produced the answer: plain chat re-asks the model; the tool loop and a resumed loop re-ask only the final answer over the tool transcript (`reaskFinalAnswer` — no tool runs twice); the cascade re-asks the accepted step. Corrective shape is R5's (`FormatRetryRunner.withCorrective`): request, rejected answer as assistant turn, corrective user message. A reprompt needs `responseValidation.minAttemptMs` of turn time left (#996 deadline), else blocks. Reprompt tokens fold into the turn's token usage and cost (cascade: priced with the accepted step's prices into `cascadeCostUsd`).
- **Streaming:** an output guardrail with `block`/`redact`/`reprompt` forces the task onto the buffered path exactly like a `retry` response-validation policy (`bufferOutput = retryPolicy != null || guardrailBuffering` replaces every streaming decision that used `retryPolicy != null`); `warn` keeps streaming.
- **Evidence:** step key `audit:guardrail:<phase>:<type>` (a list of `{phase,type,action,reason,retryCount,taskId}`), collected by `LifecycleManager.buildAuditEntry` into `AuditEntry.output.guardrails` (LLM task only); SSE `guardrail_triggered` `{type,phase,action,taskId}` via `ConversationEventSink` → `StreamingResponseHandler` (both wrappers in `ConversationService`) → `RestAgentEngineStreaming`; counter `eddi.guardrail.triggered{phase,type,action}`.

### Design decisions

- **EDDI-native SPI instead of `dev.langchain4j.guardrail` types.** R0 chose the lc4j types; against langchain4j 1.22.0 (`javap`-verified) `OutputGuardrailRequest` still demands a `ChatExecutor` that a guardrail may call itself — a second model-call path outside the turn's budget, deadline and cost accounting — `GuardrailRequestParams` still NPEs without `userMessageTemplate`/`variables`, results are sealed, and `JsonExtractorOutputGuardrail` no longer exists. Reprompting is EDDI's loop through a `Reprompter` the branch supplies, so the executor would be dead weight or a hazard. `ContentGuardrail` (`type()`, `phases()`, `evaluate(text, context)` → `GuardrailVerdict` ALLOW/REWRITE/VIOLATION) keeps "a new type is just another bean": `GuardrailService` indexes every `@Any Instance<ContentGuardrail>` by type. `GuardrailVerdict.costUsd` and `GuardrailContext.messages` are the hooks Phase 4b's `classifier` type needs.
- **A block is a value, never an exception** (R0 T1): a guardrail message can quote user text and would otherwise reach the tool loop's retry classifier.
- **Find vs act:** guardrails only report; for `pii-redaction`/`regex-filter`/`max-length` a finding with `block` refuses, with `redact` applies the rewrite.
- **No new loop on top of `FormatRetryRunner`:** its triggers are a fixed enum tied to `responseValidation`; reusing its corrective shape, `Asker`, `turnBudget` and `minAttemptMs` keeps the semantics without entangling the two policies.
- **No `ExtensionDescriptor` entries** (R0 1.3 f): the descriptor describes the workflow step's `uri`, not the LLM resource; guardrails live in the resource.
- **Not extracted into `executeModel`** (T11): hooked at the existing seams instead, so the diff in `LlmTask` is additive plus the `retryPolicy != null` → `bufferOutput` substitutions.

### Known limits / follow-ups

- Retrieval (`httpCallRag`, vector RAG) runs before input guardrails and sees the raw input (documented).
- Manager: only the `LlmTask` type mirror (`inputGuardrails`/`outputGuardrails`, `GuardrailConfig`); a guardrail list editor on the LLM task form is a follow-up. Platform Operator cheatsheet explains configuring guardrails; revision bumped.
- Phase 4b (`classifier` type) builds on this branch.
- SSE acceptance criterion 11 (`guardrail_triggered` before `done` over a real socket) is covered at unit level (handler → `sendJson`) only.
