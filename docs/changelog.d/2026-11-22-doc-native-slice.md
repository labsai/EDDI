## feat(documents): a part of a PDF reaches the model as only those pages — native slice or page text (2026-11-22)

**Repo:** EDDI (`feat/doc-native-slice`). This is work package WP-2a.5b of the PDF documents plan and depends on WP-2a.5a (#1509). A stored PDF attachment that names a page range (`attachment_0: {storageRef, pages: "3-5"}`, or a part shared between agents) now sends only those pages: a PDF of them to a document-capable model, those pages' text to any other. An attachment without a part is sent exactly as before.

### What changed and why

- **`PdfSliceBuilder`** (`modules/ingestion/extract`, new; in that package because the decode budget's charge hook is package-private). `Path slice(byte[] pdf, int firstPage, int lastPage, long maxBytes, Path workDir)` copies the pages with PDFBox's `Splitter`, which wraps `PDDocument.importPage` and also fixes what a bare import gets wrong (resources inherited from the page tree, links to pages outside the range, form-field parents, the structure tree). It runs the `PdfStreamBudget` pre-scan and keeps a `PdfDecodeBudget` armed on the calling thread for the load, copy and save. The output goes through a counting stream that aborts as soon as it passes `maxBytes` (`SliceTooLargeException`). The work file is owner-only where the file system supports POSIX permissions, and is deleted by the builder on any failure and by the caller in a `finally`.
- **`DocumentForwardPlanner`** (`modules/llm/impl`, new, pure) decides `WHOLE_NATIVE | SLICE_NATIVE | RANGE_TEXT | FLAT_TEXT` from the selector, the model's capabilities, the sizes and the effective `documents` config. A whole file (no selector, or no part) keeps today's two forms for every capability and configuration. A part is a slice for a document-capable model while it fits both the per-file limit and what is left of the request budget, and its text otherwise; it is never the whole file. Every PDF, whole or part, goes through it, so the later forms (blocks, card) are one more branch.
- **`AttachmentForwarder`.** `process(…)` returns `List<Content>` (X18): one item as before, two for a slice (`[TextContent header, PdfFileContent]`), none for a dropped attachment. The two callers were adjusted: `forwarded` still counts attachments, not content items, and the earlier-turn image re-inline counts a re-inline only when an image came back. The part branch:
  - checks the file is not withheld in this conversation (I3b: a part of a file an input guardrail refused earlier sends nothing). The withheld set is read only on a turn that carries a part, so other turns do exactly what they did;
  - loads the root without charging it to the forward limits (the slice is charged, not the file, so a 30 MB file can send a 2 MB chapter);
  - reuses a cached slice (`findDerived(root, PDF_SLICE, "p<from>-<to>")`) when it still fits, else builds one with the limit `min(max-forward-bytes, aggregate left)` and stores it through `storeDerived`. A store refusal (a per-source cap, anything else) still sends the slice;
  - falls back to the pages' text (`extractPdfText(bytes, from, to, max)`) when the model reads no PDFs, the slice is too large or cannot be built. The range is checked against the page count first, because the extractor widens an end page past the last page to the rest of the document. A missing or malformed range, an unreadable file or pages beyond the document end in a note naming the part.
  - The header names the file, the unit label if any, and the pages.
- **Constructors and overloads.** The CDI constructor takes the `PdfSliceBuilder`; the seven-argument constructor stays (with a default builder), and a new `forward(…, record, EffectiveDocumentsConfig)` overload carries the config to the planner. `LlmTask` still calls the eight-argument form, which passes no config. No `documents` key changes forwarding yet, and the first one that does (`unitForm`, WP-2b.3) wires it.

### Design decisions

- **`Splitter`, not a hand-written `importPage` loop.** The plan names `importPage`. `Splitter` uses it and adds the page-tree, link, widget and structure-tree repairs that keep a slice from dragging in the rest of the document. On the fixtures a two-page slice of a 40-page document is under a quarter of its size (asserted). A file whose pages share large fonts or images can still produce a slice close to the file's size; the abort and the text fallback cover that.
- **Byte accounting.** The builder's limit is the per-file limit or what is left of the request budget, whichever is less. The slice's size is charged to the request budget. A part sent as text is not charged (the text is capped by `eddi.attachments.extraction.max-chars`). A cached slice is re-checked against both limits.
- **The work directory is the JVM's temporary directory.** A configurable one arrives with WP-4.2; no property is added here.
- **Platform Operator, MCP, UI: no change.** No endpoint, tool, designer key, property or meter is added; the operator learns about documents with WP-2a.7. `operator-revision.json` is not bumped.
- **GDPR.** Slices are derived blobs of conversation-owned roots, deleted with them. No new participant.

### Tests

New `PdfSliceBuilderTest` (exact pages and order, an outlined chapter, one page, a slice smaller than its document, pages beyond the document, bad arguments, the size abort leaving no file, the pre-scan refusing a Flate bomb, an encrypted file, non-PDF bytes, looping and deep page trees under timeouts, the work file's directory and POSIX permissions), `DocumentForwardPlannerTest` (the whole-file matrix over capabilities, configurations and sizes; parts with and without a `documents` block; both limits; a part is never the whole file) and `AttachmentForwarderPartsTest` (header then a PDF of only the pages; the unit in the header; the slice cached as `PDF_SLICE` of the root; a cached slice reused without building; a cap refusal still sends; the work file deleted; a file over the per-file limit still sends a small part; a text model gets only those pages' text; a too-large or unbuildable slice falls back to text; the request budget charged the slice; pages beyond the document and a missing range send nothing of the file; a withheld file sends nothing; a plain PDF is sent byte-for-byte as before). `AttachmentForwarderTest` is unchanged and green.

### Known gaps

- **A group part after a HITL resume is sent as the whole file.** `GroupAttachmentBinder.rehydrateAttachmentsFromStore` rebuilds a resumed discussion's attachments from the store, which holds no selector (WP-2a.5a's known gap). With rendering live, a member whose first turn lands after the resume now receives the whole PDF instead of the part. No access is widened (the grant is on the root either way). The plan's hot-spot table gives `GroupAttachmentBinder` to WP-3.1 next, not to this package, so the fix is left to it.
