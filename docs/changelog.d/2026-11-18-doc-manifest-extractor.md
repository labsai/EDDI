## ✨ feat(documents): content model and `PdfStructureExtractor` — a PDF's units as a manifest (2026-11-18)

**Repo:** EDDI (`feat/doc-manifest-extractor`), work package WP-2a.4 of the PDF documents plan. Pure extraction: no store, no configuration, no wiring, nothing user-visible yet.

### What changed and why

The first step towards handing a chapter of a PDF to a model instead of the whole file: a stateless component that reads a PDF's structure and cuts it into whole-page units, without keeping any of its text.

- **Content model** (`modules/ingestion/extract/document/`): `DocumentManifest` (root ref, SHA-256, page count, strategy used, units, embedded files, warnings), `DocumentUnit` (`u3`, parts `u3.1`, with level, parent, pages and a token estimate), `SplitStrategy` (`AUTO`, `OUTLINE`, `HEADINGS`, `PAGES` — the one definition of the names), `SplitConfig` with a stable `hash()`, `EmbeddedFileInfo`, and the sealed `Block` family (`TextBlock`, `ImageBlock`, `TableBlock`, `AudioBlock`, `Cell`) that ordered extraction will produce later.
- **`PdfStructureExtractor.manifest(pdf, rootRef, split, limits)`** cuts by the outline (top-level entries are units, the level below are their parts) or by fixed page windows. `AUTO` uses the outline when two or more of its top-level entries point to different pages (a front-matter unit before a single chapter does not count) and the pages measured hold text. `HEADINGS` is handled as `AUTO`, with a warning, until heading detection exists. The page estimate is laid-out characters / 4.
- **`UnitBudgetFitter`** (pure) merges units below `minUnitTokens` into the next one, cuts units above `maxUnitTokens` at page boundaries, and merges the last units past `maxUnits`. The leaf units always cover every page exactly once.
- **Bounded like `PdfTextExtractor`**: the `PdfStreamBudget` pre-scan, a `PdfDecodeBudget` armed on the calling thread for the whole read, the parser's scratch space capped, glyphs per page capped, a deadline checked before every page measured and every 64 objects of any walk (pages, outline, names). Encrypted, corrupt, empty or over-budget files throw `UnreadableDocumentException`; the decode budget is checked again after a read that completed, because PDFBox swallows the budget's exception in places (`PDFont.getSpaceWidth`, `LegacyPDFStreamEngine`). `PdfTextExtractor.BoundedTextStripper` went from private to package-private so both extractors measure pages under the same bounds.
- **Fix: page-by-page reading no longer charges every page on every pass.** `PDFTextStripper` calls `processPage` for every page that has content, in or out of the requested range, and `BoundedTextStripper` charged each one's content to the decode budget before the range was checked. Reading one page at a time, as both PDF extractors do, therefore charged roughly the square of the page count: an ordinary 400-page text PDF was refused as expanding past its budget. Pages outside the range are now skipped before anything is decoded. This also lowers what `PdfTextExtractor` spends on long documents.
- **Hostile outlines**: the outline and the named-destination tree are walked here, iteratively, with an identity set and caps (2,000 outline entries, 50,000 named destinations). PDFBox's own helpers recurse into `/Kids` and climb `/Parent` with no memory of where they have been, so a self-referencing tree loops or overflows the stack. Outline titles are data: control and formatting characters are removed and titles are cut to 200 code points. Warnings never quote the document.
- **Page trees**: PDFBox's page iterator, used by text extraction, recurses once per branch it enters, builds every page object up front (a `null` in `/Kids` becomes an empty page: five bytes of input, a dictionary of heap), and yields a page listed twice in `/Kids` twice. The tree is first walked here exactly as the iterator will walk it — kid by kid, with its rule for branches already entered — but with an explicit stack. A tree on which the iterator would recurse more than 256 levels, that holds more than 250,000 pages, or that lists one page twice is refused (a duplicate would make the page numbers here and the text engine's disagree). One recursion stays out of reach: when the cross-reference table is broken, PDFBox's parser rebuilds it and walks the page tree recursively before this code has the document, so a `StackOverflowError` from the read is caught at the boundary and reported as an unreadable file. `PdfTextExtractor` has the same exposure and is not changed here.
- **Test fixtures**: `PdfFixtures` (beside `OfficeFixtures`) builds every PDF in memory: outlined, plain, flat chapters, outline cycle, 10,000-entry outline, Flate bomb, hostile titles, named destinations and their edge cases (page index, names naming names, a looping name tree, 50,000+ names), untidy outline, blank pages, a single chapter after front matter, a page listed twice, a deep page tree, and a Type 3 font whose space glyph is a Flate bomb. Later packages append their fixtures there.

### Design decisions

- **Leaves partition the pages; nothing overlaps.** A chapter that starts mid-page owns that page and the chapter before it ends on the page above (the plan's "on both sides" would contradict its own "exactly once" acceptance). Pages before the first chapter form a "Front matter" unit; below the top level they join the first part. Entries are ordered by page, and one entry per starting page is kept.
- **Two outline levels become units.** Deeper levels do not. An outline with a single top-level entry is replaced by that entry's children.
- **Pages with no text are never merged, nor merged into.** A document with no text in the pages measured is cut into page windows; within any document, a unit whose estimate is zero (a scanned chapter, a window of scanned pages) neither absorbs a tiny neighbour nor is absorbed, because its estimate says nothing about its size and a run of them would otherwise fold into one unit of hundreds of pages. Only the first `maxParts` pages are measured, so the no-text warning says how many pages it is about.
- **`SplitConfig.hash()` includes a rules version**, so manifests cached under 2a rules are not reused once `HEADINGS` stops meaning `AUTO`.
- **For WP-2a.5a: the manifest depends on `ExtractionLimits` as well as the split.** Pages past `maxParts` are estimated from the average, and the no-text decision looks only at the pages measured, so the same file and split under different limits can give different units. `split.hash()` does not cover the limits; a cache keyed on it alone must either fix the limits it extracts with or add them to the key. The estimates may also differ between hosts: `PDFTextStripper` inserts spaces from glyph widths, and for a font that is neither embedded nor given `/Widths` PDFBox falls back to the fonts installed on the machine, so the same file and split can give different unit boundaries on two nodes. A cache that must agree across nodes should store the manifest, not recompute it.
- **For WP-4.2: the work is still in memory.** Measuring calls the text engine once per page, and each call walks the whole page tree (cheap now that out-of-range pages are skipped, but quadratic in page visits); file-backed, windowed reading replaces this pass there.
- **Not yet reconciled with WP-0.1**: `DocumentsConfig` holds the strategy as a string and `EffectiveDocumentsConfig.Split.Strategy` is a nested enum there. A later package maps them onto this `SplitStrategy`.

```decision-log
| 2026-11-18 | PDF manifest leaf units partition the pages exactly once: a chapter starting mid-page owns that page; pages before the first chapter are a "Front matter" unit | WP-2a.4 plan: "includes that page on both sides" contradicted "covering 1..pageCount exactly once at leaf level" | Overlapping units sharing the boundary page (fan-out would process that page twice) |
```
