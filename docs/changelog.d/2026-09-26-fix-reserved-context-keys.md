## 🔒 fix(engine): teardown, cleanup, delegation and recruitment bound to what the caller owns; reserved context keys read exactly (2026-09-26)

**Repo:** EDDI (`fix/reserved-context-keys`, PR #831)

Review findings C3a/C3b/C3c/C6/M-T2/M-A1 on the dynamic-agent tools and the context keys the engine trusts. #859 (C3a) and #860 (C6) fixed them independently on `main` while this branch was open — see the reconciliation entry below for what was kept from each side. What this branch adds on top of `main`:

- **C3b — teardown of any agent.** `teardown_agent(victim, delete=true)` decided from the conversation's created-agents list alone. **Fixed** with a creator marker: new `AgentConfiguration.dynamicOrigin` (`createdByAgentId`, `createdInConversationId`, `createdInGroupConversationId`, `createdForUserId`), stamped on v1 by a new internal overload `AgentSetupService.setupAgent(request, origin)` — not a `SetupAgentRequest` field, which is a REST/MCP body. [`TeardownAgentTool`](../../src/main/java/ai/labs/eddi/modules/llm/tools/TeardownAgentTool.java) refuses, for undeploy as well as delete, unless the agent's current config carries a marker naming this conversation or its discussion; unreadable config fails closed. [`GroupLifecycleOps.cleanupEphemeralAgents`](../../src/main/java/ai/labs/eddi/engine/internal/groups/GroupLifecycleOps.java) applies the same marker: names this discussion → policy in full; names another → left alone; none or unreadable → undeploy only, never delete. The marker is engine-owned on every write path: [`RestAgentStore.updateAgent`](../../src/main/java/ai/labs/eddi/configs/agents/rest/RestAgentStore.java) keeps the stored value whatever the body says (a store failure on that read fails the update), and `duplicateAgent` and a ZIP import that creates a new agent drop it.
- **M-A1 — recruitment and delegation unchecked.** New `ResourceAccessGuard.principalMayUse(resourceId, principal[, principalIsAdmin])`, a request-free USE check (own resources, direct grants, published; team shares refused because the member turn carries no token; admin only via `CallerIdentity.isAdminActingAs`, from the new `CallerIdentity.admin`). `recruit_agent` asks it for the discussion owner **before** the deployment check, so a refusal never reveals whether an off-limits agent is deployed. `converse_with_agent` asks it for the bound user on every delegation, new or continued; agents this conversation or its discussion created are exempt only when tracked **and** carrying a matching `dynamicOrigin`.
- **M-T2 — retain lasted one turn.** The retained set is seeded from the *latest* recorded set (not the union, so `unretain_agent` is not resurrected), narrowed to agents still tracked as created.
- **Reserved keys read exactly (CWE-863, CodeRabbit on this PR).** `IConversationStep.getLatestData` / `IConversationStepStack.getAllLatestData` match by **prefix**, so a client key such as `groupIdSuffix` or `dynamicAgentConfigX` — not reserved by name — was read as the reserved key. Every reserved-key reader now uses `getData` or the new `IConversationStepStack.getExactDataPerStep` (`ConversationGroups`, `DynamicAgentToolsProvider` policy/created-list/delegation-depth, `AgentOrchestrator.groupConversationIdOf`), and [`ClientContextGuard`](../../src/main/java/ai/labs/eddi/engine/security/ClientContextGuard.java) also drops any key that starts with a reserved name (`shadowsReserved`). Keys extending an operator-permitted reserved key stay permitted. Documented in [`passing-context-information.md`](../passing-context-information.md#reserved-context-keys).
- **C3c — an earlier step's `groupId` is verified.** [`ConversationGroups.resolveGroupIds`](../../src/main/java/ai/labs/eddi/engine/memory/ConversationGroups.java) trusts the current step's `groupId`, but an earlier step's only when that step's `groupConversationId` names a running discussion that has this conversation as a member and belongs to that group (`LiveDiscussionRegistry.isLiveMember`). Applied on all three paths — the `usermemory` tool, the `longTerm` write boundary (`IPropertiesHandler.getGroupMembershipCheck`) and undo/redo sync — so a `groupId` forged before the guard existed no longer keeps a client in another team's group memory.

### Design decisions

- Belt and braces for teardown: the context guard closes today's hole; the marker keeps a future leak of any list from reaching an agent a person built.
- Compatibility: `dynamicOrigin` is additive (strict-boundary round-trip test passes). Sub-agents created before this change carry no marker: `teardown_agent` refuses them and end-of-discussion cleanup only undeploys them. `CallerIdentity` gained a trailing `admin` component; the 3- and 4-arg constructors remain (non-admin). A client can no longer use a context key that starts with a reserved name (`groupIdLabel`). A turn the owner sends into a member conversation after its discussion ended — or on another node — persists group-visible properties as `self`.

### Tests

## 🔒 chore(engine): PR #831 reconciled with #859/#860 — main's implementation kept where both fixed the same finding (2026-09-29)

`main` merged an independent fix for the same review (#859: `ClientContextGuard`; #860: converse ownership checks; #871: `ConversationGroups`). Merged `origin/main`, every conflict resolved to `main`'s side, then cut the branch to its delta:

- `main`'s `CreateSubAgentTool` prompt-escaping tests (#858) now stub the origin-stamping `setupAgent` overload.
