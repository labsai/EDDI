## 🔒 fix(gdpr): unverified e-mail matching, Dream under Art. 18, third-party ids in exports, log buffer erasure (2026-11-12)

**Repo:** EDDI (`fix/gdpr-erasure-export-gaps`)

### What changed and why

Gaps from a review of the GDPR erasure and export paths:

- **Unverified directory e-mail.** The email ledger and suppression participants matched a principal's rows through the e-mail the user directory recorded, whether or not the identity provider had verified it. An account holder who typed somebody else's address into an IdP profile that does not verify it got that person's ledger and suppression rows into their own export, and their own erasure deleted them. The directory address is now used only when `email_verified` was true; an unverified one is skipped. The `email:<integrationId>:<address>` expansion was already safe — integrations mint those identities only for DKIM-aligned senders, and it runs only for an id the operator named.
- **Basis in the ledger.** `IGdprParticipant` gains an optional `auditBasis(userId)`; the `GDPR_ERASURE` and `GDPR_EXPORT` compliance entries carry it as `<name>Basis`. The email ledger reports how many addresses it matched, from which source (`userId`, `emailIdentity`, `directoryVerified`) and whether an unverified directory e-mail was skipped — never the addresses. Optional field, absent on older entries. The export entry is now written after the participant sections, so it can carry them — in a `finally`, with `outcome: completed|aborted`, so an export that aborts after it started reading still leaves an entry with what it gathered.
- **The skip is not silent.** Many IdPs never set `email_verified`, so for a genuine user the skip leaves their ledger and suppression rows behind. `IGdprParticipant.notices(userId, operation)` (default empty) feeds a new additive `notices` field on `GdprDeletionResult` and `UserDataExport` (REST and MCP alike, also in the compliance entries): `emailLedger: unverifiedDirectoryEmail: …` names the gap and the remedy — confirm the address out of band, re-run with the address as the user id — without the address. A notice changes neither `complete` nor the status code.
- **Dream ignored Art. 18.** A scheduled Dream cycle pruned, rewrote and sent a restricted user's memories to a model. `DreamService.processScheduledFire` now checks the restriction first and skips the whole cycle as a successful fire (so the schedule is not dead-lettered and resumes when the restriction is lifted). An unreadable flag — or an unresolvable GDPR service — skips the cycle the same way (WARN): as a failed fire it would walk the retry ladder (`eddi.schedule.max-retries`, default 5) and dead-letter the schedule until an operator re-arms it, over a transient outage. The skip is logged at DEBUG without the user id.
- **Other people's ids in an export.** The HITL oversight section exported approvers (`decidedBy`), reviewers (`reviewedBy`) and — for decisions the subject made — the owner of the other conversation; the group section exported the other human members of a discussion. They are now `[other person]` (`ThirdPartyIdentifiers`); the subject's own id and `system:*` principals stay. Transcripts fail closed: an id stays only if the stored discussion recorded it as an agent at the time (it started a member conversation for it, recruited or created it, or persisted it as a non-human dynamic member); everything else is masked. The group's current configuration can only add masks (its HUMAN members), never remove one — an id that was human during the discussion may be listed as an agent today — so an agent nothing records reads `[other person]` too. Human evidence wins in every entry: a configured HUMAN, a pending or recorded human turn (new `GroupConversation.humanMemberIds`, filled whenever the discussion pauses for or skips a human member's turn — transcript entries carry no member type, and a human turn can be written with any entry type), a dynamic HUMAN member, or a `HUMAN_INPUT` / human-turn `SKIPPED` entry masks the id throughout, even after a continuation started a member conversation for it. A discussion stored before `humanMemberIds` existed has no record (the field reads back as null; new discussions start it as an empty list, which the persisted JSON keeps), and for it agent evidence unmasks nothing: every id but the subject's own and the no-person markers is masked, so exports of discussions created before this version show their agents as `[other person]`.
- **In-memory log store.** The erasure pseudonymised the persisted logs, but not the ring buffer the log endpoints serve nor the entries still queued for the database writer — those reached the database behind the sweep with the raw id. `LogBufferErasureParticipant` (step `logBuffer`) rewrites both, and new entries of the user for an hour, on the erasing node with the keyed pseudonym and on other replicas (by hash) with `gdpr-erased`. `flushToDb` is synchronized so the mark waits for a batch already in flight, and `publish` scrubs under the same write lock that adds the entry to the buffer and the DB queue, so an entry published during the mark cannot land raw after the rewrite. Marks are keyed by the hash of the user id (the store never holds the raw id), pruned on publish once due, timed on an injectable clock from the moment the mark holds the flush monitor and the write lock, and the mark rewrites the buffer and the DB queue for its user unconditionally, so an entry that waited behind a flush blocked for longer than the window still leaves pseudonymised. SSE listeners get each entry scrubbed again right before delivery, since they run after the lock is released.
- **Review round 6.** A timed-out human turn's generated skip reason (`No response from <name> within <window>`, now built by `HumanTurnSkipReasons.timedOut`) is masked with its speaker in the export, keeping the window when it is recognisably the writer's. The unverified-address notice no longer simply says "re-run with the address as the user id": there is no address-scoped erase or export of the email ledger, and a request under the address is the whole cascade for whatever principal that string names, so the notice (and the procedure in `gdpr-compliance.md`) first requires checking that no account uses the address as its user id, and points at the per-integration suppression clear that does exist.

Refuted on reading: the pseudonym written into database logs is already keyed (`GdprPseudonymizer`, `gdpr-erased:k1:`/`s1:`); the ledger's v3/v4 fallback stays unkeyed by design, documented there.

Still open: schedules and HITL journal entries remain in `omittedCategories` (the journal has no by-conversation listing; the schedule export would also change the Manager's "always 207" copy); resource descriptors keep their `ownerId`/`ownerName` after the owner's erasure; free text written by other people in a discussion the subject started is exported as is.
