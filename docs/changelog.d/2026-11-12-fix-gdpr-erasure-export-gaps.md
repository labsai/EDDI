## 🔒 fix(gdpr): unverified e-mail matching, Dream under Art. 18, third-party ids in exports, log buffer erasure (2026-11-12)

**Repo:** EDDI (`fix/gdpr-erasure-export-gaps`)

### What changed and why

Gaps from a review of the GDPR erasure and export paths:

- **Unverified directory e-mail.** The email ledger and suppression participants matched a principal's rows through the e-mail the user directory recorded, whether or not the identity provider had verified it. An account holder who typed somebody else's address into an IdP profile that does not verify it got that person's ledger and suppression rows into their own export, and their own erasure deleted them. The directory address is now used only when `email_verified` was true; an unverified one is skipped. The `email:<integrationId>:<address>` expansion was already safe — integrations mint those identities only for DKIM-aligned senders, and it runs only for an id the operator named.
- **Basis in the ledger.** `IGdprParticipant` gains an optional `auditBasis(userId)`; the `GDPR_ERASURE` and `GDPR_EXPORT` compliance entries carry it as `<name>Basis`. The email ledger reports how many addresses it matched, from which source (`userId`, `emailIdentity`, `directoryVerified`) and whether an unverified directory e-mail was skipped — never the addresses. Optional field, absent on older entries. The export entry is now written after the participant sections, so it can carry them.
- **Dream ignored Art. 18.** A scheduled Dream cycle pruned, rewrote and sent a restricted user's memories to a model. `DreamService.processScheduledFire` now checks the restriction first and skips the whole cycle as a successful fire (so the schedule is not dead-lettered and resumes when the restriction is lifted); an unreadable flag fails the fire. The skip is logged at DEBUG without the user id.
- **Other people's ids in an export.** The HITL oversight section exported approvers (`decidedBy`), reviewers (`reviewedBy`) and — for decisions the subject made — the owner of the other conversation; the group section exported the other human members of a discussion. They are now `[other person]` (`ThirdPartyIdentifiers`); the subject's own id, agent ids and `system:*` principals stay.
- **In-memory log store.** The erasure pseudonymised the persisted logs, but not the ring buffer the log endpoints serve nor the entries still queued for the database writer — those reached the database behind the sweep with the raw id. `LogBufferErasureParticipant` (step `logBuffer`) rewrites both, and new entries of the user for an hour, on the erasing node with the keyed pseudonym and on other replicas (by hash) with `gdpr-erased`. `flushToDb` is synchronized so the mark waits for a batch already in flight.

Refuted on reading: the pseudonym written into database logs is already keyed (`GdprPseudonymizer`, `gdpr-erased:k1:`/`s1:`); the ledger's v3/v4 fallback stays unkeyed by design, documented there.

Still open: schedules and HITL journal entries remain in `omittedCategories` (the journal has no by-conversation listing; the schedule export would also change the Manager's "always 207" copy); resource descriptors keep their `ownerId`/`ownerName` after the owner's erasure; free text written by other people in a discussion the subject started is exported as is.
