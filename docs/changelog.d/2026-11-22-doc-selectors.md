## feat(documents): pages-authoritative selectors, the document structure service, and parts through sharing (2026-11-22)

**Repo:** EDDI (`feat/doc-selectors`). This is work package WP-2a.5a of the PDF documents plan. It depends on WP-1.1 (#1469), WP-2a.2 (#1502) and WP-2a.4 (#1475). "Chapter 3 of this file" now becomes a selector that means the same pages for every agent that receives it. Rendering by pages is the next package (WP-2a.5b): until then the model still receives the whole PDF, as before.

### What changed and why

- **`DocumentStructureService`** (`engine/documents`, new). `manifest(storageRef, conversationId, split)` returns a PDF's `DocumentManifest`. It reads it from a node-local Caffeine cache keyed `(ownerKey, rootRef, split hash)` (30 min access expiry, bounded, values hold no storage reference), else from the stored `MANIFEST` derived blob (`unitId = "manifest:" + split.hash()`), else it extracts the manifest with `PdfStructureExtractor`, stores it through `storeDerived` with the *requesting* conversation (so the root's owner owns it, I3) and records the root's page count. The store authorizes every call before the cache is consulted, so a warm cache never answers a stranger. The persisted JSON wraps the manifest with its split hash, so two splits that cut a file identically still store distinct, findable blobs despite the store's content dedup. A store refusal (cap, race) still answers the call. The cache is evicted per root on `AttachmentRootDeleted` / `AttachmentOwnerChanged` and per owner by `evictOwner`.
- **`resolve(storageRef, conversationId, unit, pages, split)`** is the only place a unit label becomes pages (`SelectorResolver`, pure). Pages given are checked against the page count and kept, and never re-derived from the label. A unit alone becomes its pages under the given split, with unit and split hash kept as labels. A unit with another split's hash and no pages is an error, and so are an unknown unit, an out-of-range or malformed range, a non-PDF, or a part of a view. Errors are model-safe `SelectorException`s that never name a reference. An overload takes the carried split hash.
- **Turn intake** (`AttachmentContextExtractor`). The stored-reference path reads `pages`, `unit` and `split` into `Attachment.metadata` (`doc.pages` / `doc.unit` / `doc.split`) and nothing else, so a client cannot mark an attachment derived. A new `resolveAndGuard(…, PartResolver)` overload resolves a part after the owner-or-grant check. An unresolvable part goes to `attachments:errors` and the attachment is dropped, never sent whole. The old four-argument form refuses every part. A part counts as one attachment against `max-per-turn`. The map form read back from the conversation store now round-trips `metadata`. De-duplication identity includes the pages, so two parts of one file stay two. `withheldStorageRefs` is root-based (a recorded view on a withheld turn withholds its root, I3b). New `recordedDerived(memory)` collects the `doc.derived` entries of every non-withheld step.
- **Wiring.** `IPropertiesHandler.getAttachmentPartResolver()` (default `null`), implemented by `ConversationService` with the injected `DocumentStructureService`, and passed by `Conversation.prepareLifecycleData`.
- **Listing.** `ConversationListing.of` now lists the recorded derived selectors whose root is listed and not withheld. The store decides the root (`rootOf`), never the recorded `doc.root`. Their display name is `"<file> — u3, p.12–19"` or the view's own file name. `Entry` gains a `rootRef` component (the five-argument constructor stays), `entryForRoot` returns roots only, and `partName` is public.
- **Sharing.** `resolveNames` turns `report.pdf#u3` / `#p4-9` on a listed PDF into a part entry. `share` resolves every part through `DocumentStructureService.resolve` under the new `SharePolicy.split` (the six-argument constructor stays and uses the default split), then grants the **root** (P9), so the receiver gets the sender's pages and can read the whole file through `readAttachment`. A part that does not resolve, a resolve that fails for any other reason (the other files of the call are still shared and reported), or a part that would come back as the whole file is refused, counted as `part_invalid`, and grants nothing. A recorded view without part fields (a derived blob such as an image) is shared as itself with a grant on its root. A service built without the structure service (the binder's two-argument path) still refuses parts as `part`, whose text loses "yet".
- **Delegation (after merging `integration/pdf-documents-wave1`, which brought WP-1.2).** `converse_with_agent(…, attachments)` now accepts `book.pdf#u3` / `#p4-9`, because its share service resolves parts. `ConverseWithAgentTool` writes the shared selector's `pages`, `unit` and `split` into the delegate's `attachment_N`; without that the delegate would have received the whole file while the result told the model a chapter was shared. `langchain.md` and `attachments-guide.md` no longer say parts cannot be handed on.
- **Groups.** `GroupAttachmentBinder.grantAndInjectAttachments` writes `pages`, `unit` and `split` into the member's `attachment_N` when the group attachment carries them.

### Design decisions

- **The receiving split at turn intake is the deployment's.** The plan resolves a unit-only REST selector "with the receiving task's split config", but turn intake runs before any task, so no task is known there. No `split.*` key is live yet, so every task's effective split is the built-in default today, and that is what intake uses (`DocumentStructureService.deploymentSplit()`). WP-2a.6, which makes `split.*` live, must revisit this, either by resolving per task or by documenting the agent-level choice.
- **Files outside the plan's list:** `IPropertiesHandler`, `ConversationService` and `Conversation` (the intake wiring), and `SelectorException`. The plan's two `resolve`/`manifest` signatures are kept exactly; the carried split is an extra overload.
- **Platform Operator, MCP, UI: no change.** No endpoint, tool, designer key or property is added; the operator learns about documents with WP-2a.7. `operator-revision.json` is not bumped. No new meter, no new property.
- **GDPR.** Manifests are derived blobs of conversation-owned roots and are deleted with them; the cache is evicted on the root-deleted event. No new participant.

### Tests

New `SelectorResolverTest`, `DocumentStructureServiceTest`, `AttachmentContextExtractorPartsTest`, `ConversationListingRecordedTest`, `AttachmentSharePartsTest` and `GroupAttachmentBinderPartsTest`, with the real extractor and fixtures over an in-memory store that applies the real ownership rules. They cover: the wrong-chapter case (A's `u3` under split X reaches B, whose split Y numbers the file differently, as A's pages); a unit with a mismatching split and no pages gives an error and no grant; a grantee-triggered manifest is owned by the root owner; two owners of the same bytes get two extractions; a stranger is refused with a warm cache; a cold cache reads the stored manifest without extracting; and a part survives the conversation store round trip. `AttachmentShareServiceTest.partSuffix_isRefused` changes by design: its service has no structure service and the `PART` text no longer says "yet".

### Known gaps

- **A group part after a HITL resume.** `GroupAttachmentBinder.rehydrateAttachmentsFromStore` rebuilds a resumed discussion's attachments from the store, which holds no selector, so a member whose first turn lands after the resume receives the whole file instead of the part (no access is widened: the grant is on the root either way). It becomes visible with rendering in WP-2a.5b, which owns persisting the selector on the group conversation.
- **The "files from earlier turns" note** of the forwarder and `readAttachment`'s turn count list one entry per part of a file, without the pages. Only part flows are affected; WP-2a.6 renders the listing in `listAttachments`.

### What's next

WP-2a.5b renders selectors by pages (slice or page text). WP-2a.6 adds the document tools and makes `structure` and `split.*` live.

```decision-log
| 2026-11-22 | A document selector's `pages` are authoritative; `unit` and `split` are labels. Server code resolves a unit to pages once, when a selector is created, shared or arrives without pages, and a receiver never re-resolves it with its own split | Unit ids are stable only for one (file, split config); re-resolving on the receiver would hand a delegate a different chapter | Treating the unit id as the address and re-resolving on each receiver; resolving a unit-only REST selector at the forwarder per task (intake has no task, so the deployment split is used until split settings are live) |
```
