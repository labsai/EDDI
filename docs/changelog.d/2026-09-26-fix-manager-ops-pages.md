## 🐛 fix(manager): operations pages that misreported or acted on stale state (2026-09-26)

**Repo:** EDDI (`fix/manager-ops-pages`), Manager UI only. There are no backend, REST-shape or stored-config changes.

### What changed and why

The UI review of 2026-09-25 found that several operations pages showed the wrong thing, or acted on data the operator had not seen. Each fix below has a regression test, and each of those tests was mutation-checked: with the fix reverted, the test fails.

**Schedules ([`schedules.tsx`](../../ui/manager/src/pages/schedules.tsx), [`schedules.ts`](../../ui/manager/src/lib/api/schedules.ts))**
- *UI High 5, frontend half.* The edit form can only describe a chat schedule, and a PUT replaces the whole document. Saving a RAG-ingestion, dream or team-cadence schedule therefore dropped its metadata marker, and from then on the schedule messaged an agent instead of crawling or consolidating. Every schedule the backend treats as system-managed now has no Edit action. The markers are checked the way the backend checks them: `hitlType=hitl_timeout`, `ragIngestion=true`, or a non-empty `dreamType` or `teamCadenceType`. Such a schedule carries a "System" badge. An ordinary edit now also echoes `tenantId`, `allowSelfScheduling` and any free-form `metadata`; before, a PUT without them reset each one to its Java default. The backend carry-over for the same fields belongs to `fix/pipeline-scheduling`.
- `enabled` was read from the row as it stood when the dialog opened. A disable made meanwhile was undone by the save. The value now comes from the freshest copy in the polled list. **This narrows the problem but does not close it.** A disable made within the last poll interval (about 10 s) is still overwritten, because a configuration PUT carries `enabled` at all. The real fix is for the backend to stop taking `enabled` from a PUT, as it already does for `fireStatus`. That belongs to `fix/pipeline-scheduling`.
- `persistentConversationId` is carried over from the stored row on every update, so an edit to it was silently discarded. The field is now read-only when editing, with a hint explaining why.
- **Dead-letter panel.** The panel lists *fire logs*, but Retry and Dismiss act on the *schedule*. A failed log whose schedule is not on the listed page is looked up by id. The list is one page, and it hides HITL timeouts from non-admins. Such a schedule is reported as gone only on a 404, and it keeps its actions if it is dead-lettered. Row keys are `id:<id>` or `idx:<n>`, so a numeric id cannot collide with an index. A FAILED schedule still in its backoff answered Retry with a 404. Dismiss is a `markCompleted`, and on a claimed schedule it could clear a live claim and cause a double fire. Both actions are now offered once per schedule, on its newest log, and only while that schedule is `DEAD_LETTERED`. Every other row shows the schedule's current status, or says the schedule no longer exists. Fencing `markCompleted` on the server is `fix/pipeline-scheduling`'s work.
- **Cron preview.** A day field that begins with `*` counts as starred even when it has a step, and the two day fields are then ANDed. That is what `CronParser` does. The preview had treated `*/2` as restricted and ORed the fields, so `0 9 */2 * MON` previewed every Monday while the server fires only on odd-numbered Mondays.

**Logs ([`session-log-store.ts`](../../ui/manager/src/hooks/session-log-store.ts), [`use-logs.ts`](../../ui/manager/src/hooks/use-logs.ts), [`logs.tsx`](../../ui/manager/src/pages/logs.tsx), new [`log-entries.ts`](../../ui/manager/src/lib/log-entries.ts))**
- *P1.* The ring buffer was reseeded only when the view was empty. After a reconnect, or after the last viewer left and came back, the lines logged in between never appeared, and nothing showed that they were missing. Both the session store and the filtered stream now reseed on every open.
- `RestLogAdmin.streamLogs` replays up to 50 lines on each connect, and these were prepended blindly. They were duplicated, and they landed above newer lines. Incoming lines are now merged in timestamp order (`mergeNewestFirst`). De-duplication counts copies (`newByMultiplicity`): an incoming line is admitted only once the batch holds more copies of it than are already shown. Repeated lines, such as a retry loop logging in one millisecond, are real, and the first version of this fix collapsed them. One case still cannot be told apart without a sequence id from the backend: a single live line that is an exact twin of one already shown.
- Pause worked only on the filtered path, and there it dropped lines. It now freezes the displayed list in both modes. Lines keep being collected, so Resume shows what arrived during the pause.
- Rows were keyed by list index. Each new line therefore remounted the whole list and collapsed any open stack trace. Rows are now keyed by line identity plus an occurrence number (`keyedOldestFirst`). Repeated lines get distinct keys, and a new line never changes an older line's key.
- History showed only the newest 100 rows. `useHistoryLogs` now pages by row offset (`useInfiniteQuery`), shows a "Load older entries" button, and removes rows that shifted from one page into the next, counting copies so that repeated rows within a page survive.

**Debugger ([`live-log-viewer.tsx`](../../ui/manager/src/components/debugger/live-log-viewer.tsx), [`pipeline-trace.tsx`](../../ui/manager/src/components/debugger/pipeline-trace.tsx), [`cost-dashboard.tsx`](../../ui/manager/src/components/debugger/cost-dashboard.tsx), [`use-debug-events.ts`](../../ui/manager/src/hooks/use-debug-events.ts), new [`audit-pages.ts`](../../ui/manager/src/lib/audit-pages.ts))**
- The live log's initial fetch replaced the lines that had already streamed in, and showed the newest-first REST result upside down. It now merges, renders oldest-first, reseeds on reconnect, and pauses the same way as the Logs page.
- The debug store is global, and nothing cleared it (`reset` had no caller). After a switch of conversation or agent, the previous conversation's turns stayed on screen and new ones were added to them. `bindConversation` is called from the drawer. On a change from one conversation to another, it clears everything, the running turn included. On the first binding (null to X), it keeps the turn already recording, because that turn is for X.
- Live turns were matched to audit entries by `turnIndex`, which counts turns seen in this session, against `stepIndex`, the conversation's own step number. So costs and models were attached to the wrong turn. `resolveLiveTurnSteps` now matches finished turns to steps in order, and it refuses to guess:
  - A step matches only if its (taskType, durationMs) pairs are exactly the turn's completed tasks. The backend sends the same measured duration to both the stream and the ledger.
  - When more than one unclaimed step fits, the result is ambiguous. On a rule-based agent, where every task takes 0 ms, that is the common case, and no audit data is shown.
  - Each step can be claimed only once. A later turn only considers steps after the last one claimed.
  - An in-flight turn is never matched.
  - When no step fits yet, the ledger is re-read every 4 s for up to a minute. The ledger flushes a few seconds after the turn, so an immediate read would miss it.
- The cost dashboard and the pipeline trace read a single page of 200 audit entries. Entries come newest-first, so on longer conversations "Total cost" covered only the most recent turns. Now one shared, per-conversation query (`useDebuggerAudit`) serves both. It walks the whole trail once (`getWholeAuditTrail`: pages of 500, at most 20), and after that re-reads only the newest page and merges it (`refreshAuditTrail`). It walks the full trail again only when that newest page does not overlap what is already loaded. Entries are de-duplicated by `id`, because the ledger sorts by timestamp alone and offset paging can return the same entry on both sides of a page boundary. The dashboard says when the page cap cut the total short.

**Other pages**
- *Coordinator ([`coordinator.tsx`](../../ui/manager/src/pages/coordinator.tsx)).* Once the first SSE snapshot arrived, it overrode the polled status permanently, so after a disconnect the page stayed frozen. The page now shows the SSE status only while the stream is up, and the polled status otherwise. A failed dead-letter read used to show a green "No dead-letter entries". It now shows an error state with a retry.
- *Conversations ([`conversations.tsx`](../../ui/manager/src/pages/conversations.tsx)).* The step count on each row came from a full conversation-log request per row, up to 100 per page. The listing already carries it as `conversationStepSize`, so that value is used. The server-side search is now debounced (300 ms).
- *Conversation monitoring ([`conversation-monitoring.tsx`](../../ui/manager/src/pages/conversation-monitoring.tsx)).* "End selected" sent the state from the last poll, which could be up to 10 s old, and the backend acts on that state. A conversation that had paused for approval meanwhile was ended as if it were still running, and its approval was never cleaned up. This is the UI side of C1b. The list is now re-read on confirm, and the fresh state is what gets sent. If a paused conversation appears that the dialog did not warn about, nothing is ended and the dialog stays open so the operator can check again. Paused conversations are compared by id, not by count. A pause that lands between the re-read and the POST can still slip through; closing that needs the backend to read the state itself (C1b). If the re-read fails, nothing is ended.
- *Workflow editor ([`workflow-detail.tsx`](../../ui/manager/src/pages/workflow-detail.tsx), new [`workflow-steps.ts`](../../ui/manager/src/lib/workflow-steps.ts)).* "Add Task" appended new steps after `ai.labs.templating`. A new output or LLM step therefore ran after templating, and its placeholders reached the user unresolved. New steps are now inserted in front of the trailing templating steps.
- *Orphans ([`orphans.tsx`](../../ui/manager/src/pages/orphans.tsx)).* `DELETE /administration/orphans` has no selection parameter. It purges every orphan, re-checking each one just before deleting it. The per-row checkboxes and "Delete N selected" opened the purge-ALL confirmation, which offered a selection the server cannot honour. A client-side delete per resource would skip that re-check, so the selection UI has been removed and "Purge All" is the only action. "Last scanned" now shows when the scan actually ran (`dataUpdatedAt`), not the time of the last render.
- *Sync ([`sync-page.tsx`](../../ui/manager/src/pages/sync-page.tsx)).* A preview that failed outright left the page silent. It now shows the error. Before, a failed re-preview left the previous previews in place, as did a response that did not cover a mapping, and "Sync Selected" stayed enabled on those old diffs. Previews are now cleared when a new preview starts, and a missing row is marked as failed. Changing the source URL or token drops the agent list and every preview, because those belonged to the previous source. Errors now go through `getErrorMessage`, which includes the HTTP status.

### i18n
New keys, in all 11 locales: `schedules.systemManaged`, `schedules.systemManagedHint`, `schedules.persistentConversationIdLocked`, `schedules.failedScheduleGone`, `logs.loadOlder`, `costDashboard.partial`, `orphans.confirmPurge`, `conversations.endStateUnavailable`, `conversations.endStateChanged` and `syncPage.noPreviewReturned`. Removed, because nothing uses them any more: `orphans.confirmPurgeAll`, `orphans.deleteSelected`, `orphans.selectAll` and `orphans.deselectAll`.

### Overlap with sibling branches
- `src/lib/api/schedules.ts` is also in the API layer that `fix/manager-api-contract` edits. This branch touches only the two cron helpers, `parseCron` and `dayMatches`.
- The locale files will conflict textually with every other Manager branch. The keys are appended at the ends of their namespaces.
- `fix/pipeline-scheduling` owns the backend halves of the schedule fixes: carrying over metadata, `tenantId` and `allowSelfScheduling` on PUT, and fencing dismiss.

### Not done here
- The audit ledger has no tie-breaker in its sort (timestamp only on Mongo, `created_at` on Postgres). The client de-duplicates by id, but a secondary sort on `sequence` or `_id` belongs to the audit store owners.
- The sync page still auto-matches only against the first page of local agents. That follows from High 2, the pagination bug, which is `fix/manager-api-contract`'s work.
