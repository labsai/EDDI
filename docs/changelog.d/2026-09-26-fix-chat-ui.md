## 🐛 fix(chat-ui): streaming contract, environment, secret input, rendering and a flaky focus test (2026-09-26)

**Repo:** EDDI (`fix/chat-ui`) — UI review 2026-09-25 items High 6 (Chat UI side), High 12, High 13 and the Chat UI Medium/Low items; fix-plan item 26.

### What changed and why

**Streaming and the backend contract**
- **High 12, extra space per token.** `RestAgentEngineStreaming.padDataLines` prefixes every `data:` line with one space, and the parser kept it, so every token gained a space ("quota tion"). The parser in [`chat-api.ts`](../../ui/chat/src/api/chat-api.ts) now strips exactly one; a token's own leading space follows it. The test that enshrined the old behaviour is rewritten.
- **High 13, environment ignored.** `startConversation` now sends the route's environment as `?environment=`; the backend defaulted a missing one to production, so `/chat/test/{id}` returned 404 for a test-only agent and silently used production for an agent deployed in both. A failed start now says why in the transcript instead of staying on "Starting conversation…".
- **Streamed refusals.** An `error` frame carrying a pre-turn refusal `code` (`awaiting_approval`, `conversation_ended`, `agent_not_ready`, …) is handled like a 409: the optimistic bubble is withdrawn and the draft handed back. The code list is pinned against the Java source by `sse-events.review.test.ts`. A mid-turn failure (no code) still stays as an error on the sent message.
- **`rerunLastStep` no longer sends `language=en`.** The backend already treats it as optional; the hard-coded value became the conversation's `lang` property.

**Secret input (High 6, Chat UI side)**
- A requested `inputField` is read from the streaming `done` frame too, not only the non-streaming snapshot, so the password field appears on the default transport and the key is sent with `secretInput`.
- Only `subType: "password"` is masked and flagged secret; `text` and `email` are ordinary fields (`SecretInput` used to mask every subType).
- A refused secret goes back into the composer **masked, with secret mode on** instead of being dropped.
- Rebuilt transcripts (undo, redo, reload) mask a secret turn from the turn output's `input` (`<secret input>`). That only works because of the engine fix below.

**Backend changes the Chat UI findings required**
- **A client-flagged secret input leaked for any agent with a parser.** `Conversation.storeUserInputInMemory` wrote `<secret input>` as the displayed `input`, but `InputParserTask` — the first task of practically every workflow — overwrote it with the normalized plaintext, and `input:initial` was never masked. Only a `scope:"secret"` property scrubbed them. So a key sent with `secretInput` stayed in the stored step, in every snapshot, in the audit ledger (`TurnAuditBuffer` redacts only when `input:initial` reads as the placeholder), and in the streaming `done` frame once the `input` key was exposed. [`Conversation.scrubSecretClientInput`](../../src/main/java/ai/labs/eddi/engine/runtime/internal/Conversation.java) now runs when the turn stops (completed, stopped, paused or failed), before the audit flush:
  - it sets `input:initial` and `input:normalized` to the placeholder;
  - it clears the parsed expressions and intents derived from the secret;
  - it re-asserts `<secret input>` as the displayed `input`;
  - it removes the raw and normalized text (4+ characters) from every other datum and output of the step, and from the pending tool-call batch of a tool-call pause (the transcript the model saw, the gated arguments and the redacted arguments an approver is shown), so a resume replays and executes with the placeholder;
  - the audit ledger records the placeholder and redacts both forms (`TurnAuditBuffer.addSecretInputForms`, same 4-character floor).

  Tasks still see the plaintext while the turn runs. A conversation property the designer captured the input into is deliberately kept (the wizard pattern; the `secret` scope vaults it instead). A task that runs after a HITL resume of the turn sees the placeholder. Tests: `ConversationSecretClientInputTest`, with the real `InputParserTask` in the workflow, including a tool-call pause and its resume (batch, resumed step and audit ledger).
- **Read-time masking of older stored secret turns.** [`ConversationMemoryUtilities.convertSimpleConversationMemory`](../../src/main/java/ai/labs/eddi/engine/memory/ConversationMemoryUtilities.java) masks `input` in the outputs and `input:initial`, `input:normalized` and `expressions:parsed` in the steps of any turn flagged `secretInput` (the output's `context.secretInput` / the step's own `context:secretInput` datum, so drifted documents cannot mis-pair), in both detail levels, and removes the raw and normalized text (4+ characters) from every other step result and output value it returns for such a turn — an output item that echoed the input included; conversation properties and their step mirrors are returned as captured. That covers turns stored before the turn-end scrub, which on main already returned the raw `input:initial`, without a migration. The stored document is not rewritten. Tests: `ConversationMemoryUtilitiesTest.oldStoredSecretTurnIsMaskedOnRead`, `oldStoredSecretTurnEchoesAreScrubbedOnRead`.
- **`PropertySetterTask` no longer stores or vaults the `<secret input>` placeholder.** A capture that runs after a HITL resume of a secret turn reads the already-scrubbed input; `scope:"secret"` used to vault the literal placeholder as the secret. It now logs a warning and leaves the property unset. Tests: `PropertySetterTaskSecretScrubTest.placeholderIsNeverVaulted` (main's, which covered the same case), `placeholderIsNotStoredAsConversationValue`.
- [`ConversationMemoryUtilities.convertSimpleConversationMemory`](../../src/main/java/ai/labs/eddi/engine/memory/ConversationMemoryUtilities.java) now keeps the exact `input` key in non-detailed `conversationOutputs`. Its contract is "the masked display copy": `<secret input>` for a turn flagged `secretInput`, the normalized text otherwise. It is additive; readers look up specific keys. The Manager's `snapshotToMessages` (from `fix/manager-chat`) reads this key, and the engine fix above is what makes that correct too.
- [`RestAgentManagement.loadConversationMemory`](../../src/main/java/ai/labs/eddi/engine/internal/RestAgentManagement.java) re-runs the last step only when the caller asked for a language. A load without `?language=` compared the stored `lang` against null and re-ran the step on every widget load.

**Conversation lifecycle**
- Managed **New conversation** ends the current managed conversation (`POST /agents/managed/{intent}/{userId}/endConversation`) before loading. Before, the load returned the same conversation.
- Start and restart share one `openConversation`, which re-checks the conversation generation after every await. The first load had no such check, so a restart during its welcome read could get the old greeting and id.

**Rendering**
- Links open in a new tab (`rel="noopener noreferrer"`). A link used to navigate the widget, or the whole iframe, away. Same-page anchors and GFM footnote references stay in the page.
- A model-chosen image (markdown or raw `<img>`) is never fetched: it is a beacon, and only EDDI's own CSP blocked it; an embedding page's CSP might not. After the merge with main it renders as a click-to-open link (main's override) rather than being stripped by the schema.
- `image` output items are rendered by the widget, http(s) or same-origin only. `applicationLink` becomes a link (label escaped, destination wrapped in `<…>`) and `button` shows its label. All three used to be dropped silently.
- KaTeX and syntax highlighting (advertised in the README, never wired) now work. Math is `$$…$$` only (`singleDollarTextMath: false`): with single-dollar math, a reply quoting "$5 and $10" rendered the span between the prices as a formula. Both are **loaded on first use** from their own chunks (`markdown-plugins.ts`), so the main bundle stays about the same (645 → 652 kB). The KaTeX fonts go to `fonts/`, which the Maven build already copies and prunes.
- `MessageBubble` takes its flags as props instead of subscribing to the store, so a streamed token no longer re-renders and re-parses every bubble.

**Smaller items**
- The transcript is `role="log"` with `aria-live="polite"` and `aria-busy` while a reply streams.
- `useTheme` guards every storage access. Blocked storage used to throw and blank the widget.
- `?token=` is read once and removed from the address bar.
- The agent name comes from `/descriptorstore/descriptors/{id}/simple?version=N` with the bearer token. The old call went to `/agentstore/agents/{id}` without auth or version, and that response has no name.
- ESLint (the same base as the Manager) with a zero-warning `lint` script and a `Lint` step in the `UI Chat` CI job.

**Flaky test: "moves focus to the attach button when the last chip is removed"**
- Root cause: the focus intent was consumed by the first `pendingAttachments` effect to run. The upload resolves outside `act`, so React commits the new chip but defers that commit's passive effect to a scheduler task. When the remove click landed before that task ran, React flushed the stale effect first. That effect took the intent while the chip was still mounted and focused the remove button that was about to unmount, so focus fell to `<body>`. Whether the task ran first depends on Node's `setImmediate` vs `setTimeout(0)` ordering, which changes under CPU load.
- Fix: the intent now carries the removed `storageRef` and is only acted on once that chip is gone. A new test forces the race deterministically by clicking natively the moment the chip appears. It failed 5/5 before the fix.

**Review follow-up (CodeRabbit, 2026-09-27)**
- **Short client-flagged secrets were not searched for.** The echo search used the 8-character floor of secret *context* values, so a 5-character PIN a template echoed stayed in the stored step and the reply, while `TurnAuditBuffer` (floor 4) already redacted it from the ledger. Client-flagged input now uses its own floor, `SecretValueScrubber.MIN_SEARCHED_SECRET_INPUT_LENGTH = 4`, shared by the turn-end scrub, the read-time masking and the audit buffer. Not every nonempty form, as suggested: the search replaces every occurrence in every value **and map key** of the turn, so a one- to three-character "secret" would shred the reply and rename the fields of its stored API responses and output items; such a form is still replaced wherever it *is* the input. Test: `ConversationSecretClientInputTest.shortSecretIsScrubbedFromEchoes`.
- **Read-time masking now scrubs echoes** in older stored secret turns (above).
- **Read-time masking now clears the parser's results** for an older stored secret turn, as the turn-end scrub does: `expressions:matches`, `intents` and `properties:extracted` read as empty lists, and the output's `expressions` and `intents` entries are dropped. Only `expressions:parsed` was cleared before; the rest were only searched for the input, and the parser can split a secret into tokens that no search for the whole value matches. Test: `ConversationMemoryUtilitiesTest.oldStoredSecretTurnParserResultsAreClearedOnRead` (it fails with the change reverted).
- **The `CATCH_ANY_INPUT_AS_PROPERTY` capture skips the placeholder too.** It reads `input:initial` directly and stored `user_input`, so after a RULE-pause resume of a secret turn it saved the literal `<secret input>`. It now goes through the placeholder guard (`isScrubbedPlaceholder` since the merge with main) like the `valueString` and `fromObjectPath` captures. Tests: `PropertySetterTaskSecretScrubTest.catchAnyInputSkipsThePlaceholder` (fails with the guard removed) and `catchAnyInputStoresOrdinaryInput`. The helper's Javadoc no longer sits between `autoVaultSecret` and its own doc comment.
- **A resume cannot redact what it reintroduces — documented, not "fixed".** The resume is a later request and the plaintext is never kept past the pause. Restoring it would mean persisting it (defeats the scrub) or a hash (a PIN's hash is reversed offline, and a hash cannot be searched for inside text). [`docs/secrets-vault.md`](../secrets-vault.md) no longer claims the ledger redacts both forms "for a resume"; it says what a resumed task reintroduces — from a captured property or a tool result — is not redacted.
- **Chat UI `isSafeUri`** resolves a slash-prefixed value against the page before calling it same-origin: `/\evil.example` is a path to another host in an http(s) URL. **`useTheme`** keeps the mode in force in a ref, so with blocked storage `setTheme("system")` keeps following OS changes instead of falling back to `initial`.
- **Chat UI `stepsToMessages`** trusts a turn output's `<secret input>` marker only when steps and outputs have the same length, as the backend does. A drifted snapshot used to pair an index with another turn's output and mask an ordinary message on undo/redo (a display error, not a disclosure). A step whose own `input:initial` reads `<secret input>` is still masked. Test: `snapshot.test.ts` "does not pair steps with outputs when a drifted snapshot's lists differ in length".

**Merge with main (2026-09-29)**

Main fixed the same problems independently while this branch was open (`fix/security-frontend`, `fix/security-access-control`). The merge keeps one implementation of each:
- **Turn-end scrub.** One pass, `Conversation.scrubSecretClientInput`; main's `scrubSecretUserInput` and its helpers are gone. Main's guarantees are kept: the raw input is remembered from the start of the turn, so its copies are still found after a `scope:"secret"` property has already replaced `input:initial`.
- **Decision: captured conversation properties are kept** (this branch's policy). Main scrubbed every conversation property of the input; that would turn the reference wizard's `apiKey`, captured from a password field with `{memory.current.input}` and sent to `create_agent` on a later turn, into the literal `<secret input>`. `ConversationSecretInputTest.secretInput_renderedCopiesScrubbed` now asserts the property is kept; the `secret` scope vaults it.
- **Decision: secrets shorter than 4 characters are removed as whole tokens** (main's policy). They are removed only where no letter or digit directly precedes or follows them, in step data other than properties, in outputs other than `input` and `properties`, and in the pending tool-call batch (new `SecretValueScrubber.scrubTypedTokens`). From 4 characters the substring search is unchanged. `ConversationSecretClientInputTest.shortSecretIsScrubbedFromEchoes` now expects "ok abc" to become "ok <secret input>". The audit ledger and the read-time masking keep the 4-character substring search only.
- **`SecretValueScrubber.scrubDeepTokens` no longer renames map keys.** It replaced a short secret in keys as well, so a PIN "id" would have renamed every `id` field of the turn's stored API responses. Only values change in token mode now; substring mode (4+ characters) is unchanged. Test: `SecretValueScrubberTest.wholeTokensLeaveMapKeysAlone` (fails with the change reverted).
- **Detailed reads now redact credential-named properties.** Main's `returnDetailed` redaction (denylisted keys, the secret redaction filter, everything under a credential-named key) applies on top of the secret-turn masking. A secret turn is masked first, then redacted, so a detailed read shows `properties.apiKey` and `properties:apiKey` as `<REDACTED>`; the non-detailed read and `conversationProperties` are unchanged.
- **`PropertySetterTask`.** One guard, `isScrubbedPlaceholder(name, value, scope)`: a value that is exactly `<secret input>` is not stored, in any scope, and for `scope:"secret"` a value that contains either placeholder is not vaulted (main's rule). The property is left unset.
- **Second merge (after `fix/memory-audit-findings`).** Main now wraps every stored property in `withInstructionVisibility`; the `fromObjectPath` string capture keeps that and this branch's placeholder guard. Main's new `properties:changes` undo log is a `properties:*` datum, so, like the property mirrors, it keeps a captured input — undo restores the value the designer captured. `ConversationSecretInputTest.secretInput_renderedCopiesScrubbed` skips `properties:*` data accordingly.
- **Chat UI.** `?token=` is stripped once through the router (this branch); main's `replaceState` helper `stripTokenFromUrl` is removed, because it re-ran on the stripped URL and reset the token. Main's allow-list `apiServer` sanitizer and postMessage token handshake are kept; its control-character regex carries an ESLint exemption. `snapshot.ts` keeps one `SECRET_INPUT_PLACEHOLDER`.

### Refuted / not changed
- **"A double-clicked restart starts two conversations."** Refuted as stated. Every restart control unmounts synchronously on the first click (`CLEAR_MESSAGES` clears the `conversationId` the action bar and banners depend on), so no second click can reach one. The related real race, a restart during the first load's in-flight read, is fixed by the generation checks above.
- **Managed restart racing the first load (review).** Not reachable from the UI: every restart control needs the `conversationId` or state that the first managed load sets only when it completes, so no restart can start while it is in flight.
- Designer-configured images from external hosts are still blocked by EDDI's own `img-src 'self' data:` CSP when EDDI serves the widget. That is a deployment choice and is left alone.
- The descriptor endpoint is editor-only, so an end user with only `eddi-user` still sees the configured `title` instead of the agent name. A user-readable name endpoint would be a backend feature and is a follow-up.
