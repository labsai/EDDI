## Email channel: replies to the thread (2026-11-22)

**Repo:** EDDI · **Branch:** `feat/email-thread-replies` (stacked on `feat/email-addressing`, #1496) · **Plan:** `planning/email-channel-v2-plan.md` §9 (Phase 5, on `docs/email-channel-v3-control-plan`)

**What changed:**

- **New conversation-mode keys**: `replyAudience` (`sender` | `thread`, default `sender`), `replyAllowedRecipients` (sender patterns, required with `thread`, max 50, `*@*` refused), `listAddresses` (patterns never copied) and `maxReplyRecipients` (10, 1–50). `thread` needs `actWhen: addressed` and the default `identityMode`; the three audience keys are refused without it. Save warning `email.reply-audience-thread`. An unknown stored audience reads as `sender`.
- **Audience** — one pure function, `integrations/email/reply/EmailReplyAudience`: the answered mail's signed `To`/`Cc` (the step's `mail` map, built from #1394's signed view), normalised, minus the mailbox, its aliases and their plus-addresses, minus the `To`, minus `listAddresses`, only matches of `replyAllowedRecipients`, in header order; more than `maxReplyRecipients` → no copies (`CC_CAPPED`). Copies exist only when the conversation runs as this integration's `email-thread:` identity, so a conversation started under `sender` (with the sender's memory) is never copied after the setting changes. `EmailReplyRecipients.decide` carries it in its `Decision`; the inbound processor puts it into the turn as `mail.audience` before the turn runs.
- **Identity** `email-thread:<integrationId>:<sha256(threadRoot)>` (a non-participant: `…:<sha256(threadRoot + "\n" + sender)>`), in `ReservedPrincipals.PREFIXES` and `hasNoPersistentMemory` — no long-term properties, no memory tools — and in `EmailUserIdentity.isEmailIdentity`.
- **Participant guard on every lookup path** under a thread audience: the continuation through EDDI's own Message-IDs, the new thread key `email:<id>:<agentId>:sha256(threadRoot + "\nthread")`, and the start race (a mail that loses the race for a thread's mapping to a non-shared sender ends its own conversation and waits, `conversation_busy`). A participant is the first sender or an address a SENT reply in the conversation went to, `Cc` included.
- **Child store `email_reply_recipients`** on `IEmailMessageLedger` (MongoDB collection with TTL, PostgreSQL table keyed `(row_id, address)`, in-memory fake, contract): `addReplyRecipients`, `findReplyRecipients`, `removeReplyRecipients`, `findReplyRecipientsByAddress`. `hasSentReply` now also matches a `Cc` of a SENT row; `deleteByRecipient` removes the children of the rows it deletes and the address's own entries; `deleteExpired` covers them.
- **Sending**: `MailTransport.send(…, List<String> envelopeRecipients)` (one SMTP submission; the single-recipient form stays), `EmailReplyComposer.render(…, cc, …)` sets the `Cc` header (`OutboundMail.withCc`). A suppressed `Cc` is dropped, a suppressed `To` still suppresses the reply. A retry sends to the stored copies intersected with what the current settings allow — never widened — and removes dropped copies from the record, so only someone who was really sent the reply counts as a participant. A permanent bounce for a `Cc` suppresses that address only; the row stays `SENT`.
- **Audit / metrics**: `email.reply` entries add `ccCount` and up to ten `ccDomains`; `eddi_email_outbound_recipients` (distribution summary), `eddi_email_outbound_cc_capped_total`, outcome `cc_bounced`.
- **GDPR**: the ledger participant exports a reply the address was copied on (`role: CC`) and erases its entries; the identity participant also reaches `email-thread:` conversations named by the address's inbound rows and copy entries, but only where the conversation's user id is that integration's thread identity.
- Docs: [`email-integration.md`](../email-integration.md) (Replying to the thread, keys, Who gets a reply, Identity, What the agent sees, Bounces, Personal data, Audit, Metrics), [`gdpr-compliance.md`](../gdpr-compliance.md), [`metrics.md`](../metrics.md). MCP `create_channel_integration` description, Manager (reply-audience block in the Replies section, 18 new strings in all 11 locales, `mail.audience` in the template variables), Platform Operator prompt (revision 84).

- **Review fixes** (same day): a Cc the relay refuses at `RCPT TO` (5xx, no `sendpartial`, so nothing was sent) is dropped from the reply — header, envelope, record — and the rest is submitted once more; a refused `To` still fails it (`MailSendException.getRejectedRecipients`). Continuing a thread conversation now needs the first sender (`originalSenderOnly`, honoured under `thread`) or, with `anyAuthenticatedParticipant`, having been sent **every** reply so far (`countSentReplies` / `countSentRepliesTo` on the ledger, all three stores); the shared-key check also covers an ended conversation. GDPR works per conversation id (`EmailThreadConversations`): export gives only the address's own mails and replies, erasure purges each conversation (`ConversationPurgeService`, audited `email.gdpr`) and never touches the shared identity; the ledger step keeps its rows while such a conversation remains, so a failed erasure can be retried. `from()` applies the thread audience only when its preconditions hold and clamps `maxReplyRecipients`; copies whose local part routes onward (`%`, `!`) are dropped; `hasSentReply` on MongoDB queries exactly.
- *Follow-ups:* the per-reply audience in the Manager's conversation view (plan §9.7) and a Cc case in `EmailConversationModeIT`.

**Design decisions:**

- **GDPR in thread mode (plan §13 Q4, provisional):** erasing an address erases each thread conversation it took part in **whole**, following the v3 plan's §13 rule of cascading over the conversations the address's ledger rows name, guarded so only that integration's `email-thread:` conversations are reached. The owner has not decided between deleting and redacting; redaction would need per-turn removal the conversation store does not offer.
- With copies, a reply's Message-ID is known to all its recipients, so a recipient can forge a DSN that suppresses another recipient. Accepted (a denial of replies to one colleague, cleared by an admin, never an added recipient) and documented.
- No new REST or MCP endpoint: the keys are `platformConfig` keys of the existing channel CRUD, so tool counts, the OpenAPI document and the `origin=email` guards are unchanged.
- Not done: the Manager's conversation view does not yet show each reply's audience (no reply-row view exists on this base); live mailbox verification of DKIM `h=` coverage of `Cc` at Gmail/M365 (plan §13 item 8) is still open — if a provider does not sign `Cc`, its senders' copies are silently empty.
