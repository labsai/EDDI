## ✨ feat(workforce): search my conversations, tool cards, and the tool notice before Edit and Regenerate (2026-11-06)

**Repo:** EDDI · **Branch:** `feat/conversation-search-tool-ui` (`feat/workforce-tier1-ux` with `feat/conversation-search-tool-events` merged in)

The rest of phase 7 of the frontend unification plan (`planning/frontend-unification-plan.md` §5, T1.3, T1.6 and T1.9), on the backend's B3 (`GET /conversationstore/conversations/search`) and B6 (the `tool_result` stream event). Frontend only.

### What changed and why

- **Search my conversations (T1.3).** A search box at the top of the Workforce sidebar's conversations ([`conversation-search.tsx`](../../ui/workforce/src/components/workforce/conversation-search.tsx)): a combobox whose results replace the date-grouped list while it holds text, **↑ ↓** and **Enter** to open, **Esc** to clear. A line under it says it searches **titles only** (tied to the box with `aria-describedby`), and a polite status says how many it found once a search settles, or that none matched, or that it failed (with Retry). [`use-conversation-search.ts`](../../ui/workforce/src/hooks/use-conversation-search.ts) holds the request discipline: the text normalized as the backend stores titles and capped at `MAX_CONVERSATION_SEARCH_LENGTH` (also the box's `maxLength`), a 300 ms debounce, one `AbortController` per request (a new text aborts the old request, and a late answer is dropped), and **More results** while pages come back full. `searchConversations` takes an `AbortSignal` now (it uses the client's authenticated fetch; `api.get` takes no signal). Member conversations of a team session are left out, as in the list. The **⌘K quick switcher** adds the title matches it has not already shown, below the local ones, with the same "titles only" line.
- **No Manager surface.** The Manager's conversation pages list every user's conversations for an administrator, and its chat history one agent's; an owner-only title search fits neither, so search is Workforce only.
- **Tool activity as cards (T1.9).** A new entry, [`@eddi/conversation/tool-activity`](../../ui/packages/conversation/src/tool-activity/index.ts): `ToolActivityLog` files each `tool_result` under its conversation and step (`beginTurn` from `onTurnStarting` empties the turn's step and every later, undone one; `clearStep` after a rerun, which has no stream; at most 50 calls per turn, the rest counted; 20 conversations). `ToolActivityCards` shows a turn's calls as one disclosure under its **question** — collapsed, "Tools used: 2 · 1 failed"; open, a card per call with the tool, whether it worked, and the summary. **The summary is a React text child, never markdown or HTML**: a test feeds it `<img onerror>`, `<b>`, `**…**` and a link and finds no element. The Manager/Workforce chat (`ChatPanel`, through `chatToolActivity` in `use-chat.ts`) and the member thread wire `@eddi/core/tool-events` into their controllers.
- **Live only.** The detailed snapshot holds the raw tool trace under `langchain:trace:*`, which the server redacts (`ToolTraceRedaction`) only on the way out through the stream and `task_complete`. Restoring cards from it would show unredacted tool results, so nothing is restored: a reload, a conversation opened later, or a turn answered without streaming shows no cards. A rerun (REST, no stream) clears its step's cards rather than leave the first run's.
- **The tool notice (T1.6).** `ChatPanel`'s `renderTurnNotice` now defaults to `ToolTurnNotice`: beside **Edit** and **Regenerate** of a last turn that ran tools, an inline warning names them ("Ran send_email. Editing takes back the reply, not what the tools did." / "… What they did stays, and a new reply may run them again."), tied to the button with `aria-describedby`. A host's own `renderTurnNotice` still replaces it. After an Edit of such a turn, the same point is made once more as a toast, since the undo takes the warning off the screen with the turn. **An inline warning, not a confirm step:** the effects already happened, so a dialog cannot prevent anything; an Edit only puts the text back in the composer, and nothing runs again until the user sends; the warning is visible before the click (and before **↑**), where a confirm on every edit of every tool turn would train people to click through it.
- **The widget does not grow.** It is at 169.4 of 170 KB gz and shows no tool activity, so it imports neither the new entry nor `@eddi/core/tool-events`; a test reads `ui/chat/src` and fails if it ever does. Lazy-loading the cards into the widget was rejected: even the loader and the listener would cost bytes it does not have, for a surface the embedding contract never promised. `docs/chat-ui-embedding.md` is unchanged.
- **Strings.** `toolActivity.*` (10 keys) in the package's own locale files (`withToolActivityLocales`, merged by `setupAppI18n`), `Workforce.search.*` (12) and `Workforce.switcher.searchFailed` in Workforce's, all in the eleven locales. The tool strings are their own bundle rather than `conversation.*`: that namespace's English is bundled into the widget.
- **Platform Operator.** The prompt now says how Workforce and the Manager's chat show `tool_result` (cards, the notice, live only, none in the widget), which an admin asked about a missing card would need. No allow-list change. `operator-revision.json` stays at **56** (set by the merge, unreleased) with the new fingerprint.
- **Docs.** [`workforce-guide.md`](../workforce-guide.md) (searching, what the agent's tools did, the warning on Edit and Regenerate, the keyboard table, two administrator notes), `ui/manager/AGENTS.md`, `ui/workforce/AGENTS.md`, the `@eddi/conversation` README.
- **Test fix.** The quick switcher's "filters … opens a chat with an agent" test read an agent row before the sessions loaded and filled the 30 rows; it now reaches the agent by name.

### Design decisions

- Titles only, as the backend decided (B3); the UI says so at every place it offers the search.
- A full page means "maybe more"; a short page ends the list. The backend can return a short page when a match's memory is gone, which can hide later matches; that is rare (orphaned descriptors) and a narrower text finds them.
- Cards go under the turn's question, so they read in the order things happened: the question, the tools it set off, the reply.

### Not done

- Restoring cards after a reload: needs a client-readable, redacted trace on the snapshot (a backend item).
- Tool cards for group discussions: the backend sends no `member_tool_result` yet.
- Searching outputs: the backend's follow-up (privacy review first).
