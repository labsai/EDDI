## 🐛 fix(audit): agent signatures on audit entries honour revocation, and an unprovable one is no tampering alarm (2026-11-08)

**Repo:** EDDI (`fix/audit-agent-signature`, review round on the same branch, now merged with the review round of `feat/agent-signing-key-provisioning`)

### What changed and why

A whole-feature review of agent signing found that the audit half signed with keys it should not have used, reported a routine agent delete as tampering, and could not see a stripped signature.

- **Signing only with a key that is usable and matches.** `AuditAgentSigner` signs with the producing agent version's newest key only while that key is not revoked and is inside its `validFromMs`/`validUntilMs` window at the entry's own timestamp (the ledger's, covered by the HMAC). Each new signature is checked against the public key that version declares before it is stored: a version saved before keys were engine-owned can declare a hand-typed key that a later "Generate signing key" filled in the vault with a different key, and every entry it signed then read as forged. Such an entry is left unsigned and an ERROR is logged.
- **Nothing escapes signing.** An unchecked store failure (a driver timeout) while reading the agent version escaped `AuditLedgerService.submit` after the entry's chain position was taken: the entry was lost and the gap was reported as a deletion (`ChainStatus.BROKEN`). Every failure now leaves the entry unsigned, with a WARN.
- **A GDPR erasure no longer launders a forged row.** The reseal re-made the agent signature of every row whose HMAC verified. A row whose agent signature is the finding — `AGENT_SIGNATURE_INVALID`, or `AGENT_SIGNATURE_MISSING` (a row forged by someone holding the audit HMAC key) — came out of the erasure carrying a genuine signature by the agent, and verified `VALID`. Such a row now keeps what it carried and reports the same verdict after the erasure; if the agent store cannot be read, the resealed row is left unsigned rather than signed on trust.
- **Verification accepts exactly what the ledger writes.** A signature by another key than the version's newest, outside that key's window, or on a version with signing off, is `AGENT_SIGNATURE_INVALID`. The stored form `v<n>:` takes every version up to `AgentPublicKey.MAX_VERSION` and no leading zero.
- **Three new verdicts, none of them tampering.** The HMAC proves the entry's content; these say only that the agent's signature cannot vouch for it. They count in a new report field, `agentSignatureUnproven`, not in `invalid`: the sweep is not `intact`, and `tamperingSuspected` stays false.
  - `AGENT_KEY_REVOKED`: the agent revoked the key since, or its newest version no longer declares it. A revoked key is trusted for nothing, whenever it signed, as for group messages.
  - `AGENT_SIGNATURE_MISSING`: no signature on an entry its agent version would have signed (a stripped signature used to verify `VALID`). Reported only while `eddi.audit.agent-signing-enabled` is on.
  - `AGENT_KEY_UNAVAILABLE`: the agent was deleted permanently. This used to be `UNKNOWN_KEY`, counted in `invalid`, so an owner deleting their own signing agent raised `tamperingSuspected` for every entry it had signed. `UNKNOWN_KEY` is again only an HMAC key the deployment no longer holds.
- **A soft delete no longer takes a revocation back.** Verification read the revocation from the agent's *current* version, and a soft delete leaves none on either backend (MongoDB moves the row out of the current collection, PostgreSQL out of `resources`). Revoking a leaked key and then deleting the agent — the ordinary response to a compromise — turned every `AGENT_KEY_REVOKED` entry back into `VALID`, and a stripped one into `AGENT_SIGNATURE_MISSING`. It now reads the agent's newest version, soft-deleted or not, through a new `IAgentStore.getNewestVersionIncludingDeleted` (`HistorizedResourceStore`: the current version, otherwise the newest history row, which after a soft delete is the deleted version). Only a permanently deleted agent has nothing newer, and its signed entries are `AGENT_KEY_UNAVAILABLE` already.
- **One WARN after a revoke, not one per entry.** Revoking the newest key deletes it from the vault while the deployed version still names it, so every audit entry of that version went unsigned with its own WARN until a redeploy — about a thousand lines a minute on a busy agent, during the incident. `AuditAgentSigner` now logs one WARN per agent version and key that says a redeploy is what fixes it, and the repeats within ten minutes at DEBUG.
- **A signature in the form 6.7.0 and earlier wrote is checked, instead of read as forged.** Those releases signed every audit entry of an agent whose vault held its unversioned key `agent-signing-key:{agentId}`, whatever the agent's settings, over the bare HMAC, as plain Base64 with no `v<n>:`. No release could put that key there: the secrets API's key names allow no `:`, and the key generators had no caller (the old `signInterAgentMessages` validator asked operators to store it, which no API allowed). Such rows exist only where the key was written into the vault outside EDDI's API, and the check is for them. Verification accepted only the new form, so each such authentic row reported `AGENT_SIGNATURE_INVALID`, counted in `invalid`: `tamperingSuspected` for the whole history, also with `eddi.audit.agent-signing-enabled` off, and a GDPR erasure kept the rows as evidence, so they never recovered. `AuditAgentSigner` now checks a plain-Base64 signature against the legacy key the entry's own agent version declares (`identity.publicKey`), over the bare HMAC and whatever the agent's flags: `VALID`, `AGENT_KEY_REVOKED` when that key was revoked since, `AGENT_SIGNATURE_INVALID` when it does not verify. With no declared legacy key, or no agent version on the entry, it is `AGENT_KEY_UNAVAILABLE` (unproven, not tampering). An erasure re-signs a verified legacy row in the current form, and no longer signs afresh a row whose signature nothing could check (`AGENT_KEY_UNAVAILABLE`): any Base64 written by someone holding the audit HMAC key would otherwise have become a genuine agent signature at the next erasure.
- **Architecture page.** [Cryptographic agent identity](../architecture.md#cryptographic-agent-identity), key rotation and revocation, no longer says audit entries carry no agent signature: they are signed as `v<n>:<signature>`, checked by `/auditstore/verify`, revocation applies, and signatures written by 6.7.0 and earlier are checked against the legacy key.
- **What `AGENT_SIGNATURE_MISSING` detects, stated correctly.** The docs said it protects against a forger holding a separate `eddi.audit.hmac-key`. It does not: whether a row should carry a signature is decided by its `agentVersion` and `timestamp`, which that forger writes and HMACs, so naming a version with signing off (every signing agent has a version 1 created with signing off) or a time before the key's `validFromMs` makes an unsigned forged row verify `VALID`. `MISSING` shows a signature stripped by someone who can edit rows but lacks the HMAC key; a `VALID` agent signature is what an HMAC-key holder without the vault cannot fake. [Audit ledger](../audit-ledger.md#agent-signatures) and the `AuditAgentSigner` Javadoc now say so; the verification logic is unchanged.
- **The verify endpoints' Javadoc** in `IRestAuditStore` no longer calls the check HMAC-only: both verify agent signatures and count the unprovable ones in `agentSignatureUnproven`.
- **Docs and API text.** [Audit ledger](../audit-ledger.md#agent-signatures): audit entries are signed by the agent version a conversation runs, so they need a deployed version with the key and the flag (group messages are signed from the newest stored version at once); the verdicts; and that the agent signature adds protection only where `eddi.audit.hmac-key` is separate from the vault master key. The OpenAPI text of `POST /agentstore/agents/{id}/signing-keys` scopes "no redeploy needed" to group messages. [Cryptography](../cryptography.md) mentions revocation.
- **Manager.** The audit page no longer says an entry with a forged agent signature had its content changed: it shows "N agent signature(s) do not verify — the content is intact" next to the content line, and the row chip reads "Agent signature does not match". `agentSignatureUnproven` makes the verdict "Not fully verified" with its own reason. Three keys in all 11 locales.
- **Operator.** The prompt says audit entries need a deployed version, how the new verdicts are counted, and that a plain-Base64 signature written by 6.7.0 or earlier is checked against the legacy `identity.publicKey` (revision 68).

### Design decisions

- **Revocation is absolute for audit entries too.** The plan preferred keeping entries signed before the revocation valid, judged by the ledger's timestamp. Rejected: the revocation records no time, and anyone able to forge an audit row holds the HMAC key and so writes the timestamp too; a "signed before" rule cannot tell their back-dated rows from honest ones. The entry "identity is engine-owned, keys can be revoked, and generating one no longer breaks the agent's descriptor" already makes a revoked key valid at no time, whenever an entry claims it signed. The cost is that honest older entries lose their agent signature's vouching (`AGENT_KEY_REVOKED`), never their HMAC proof.
- **Revocation is read from the agent's newest version, soft-deleted ones included.** Revoking writes a new version, so the entry's own immutable version never shows it. One version lookup per checked entry of a signing agent (a second, indexed history read only for a soft-deleted agent); the version itself comes from `AgentConfigurationCache`. Rejected: a time-based cache of the newest version (revocation would show late, and tests could not see it without a clock seam); probing `readIncludingDeleted` upward from the entry's version (one read per version, per entry, and it relies on versions being contiguous); and treating every soft-deleted agent's entries as unproven (honest entries of a deleted agent would lose their vouching).
- **The new store method sits on `HistorizedResourceStore`, `AbstractResourceStore` and `IAgentStore`, not on `IResourceStore`.** Every configuration store inherits it, but only the agent store declares it: the conversation-memory stores that also implement `IResourceStore` have no version history to answer from, and only audit verification needs it.
- **A signature in the old form is checked with the legacy key alone, outside the new rules.** The old ledger ignored `signInterAgentMessages` and key windows, so judging its rows by `signingIdentity` would still call them forged. Rejected: mapping every unversioned signature to unproven without checking it (honest rows would lose their proof); trying every key the version declares (the old vault key's public half was documented as `identity.publicKey`; an undeclared pairing is reported unproven instead).
- **Unprovable is its own count.** Rejected: mapping them to the HMAC status (a stripped signature would stay `VALID`), and counting them in `invalid` (a routine delete becomes a tampering alarm).
- **Self-check by verifying the fresh signature**, as `GroupSigningGuard` does, rather than a cached `checkSigningKey` per (agent, version, key): no state, and the cost is one Ed25519 verify per signed entry.
