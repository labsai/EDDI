## 🎨 feat(manager): Settings → Branding page with live preview and live update — white-label phase 4 (2026-10-25)

**Repo:** EDDI (`feat/white-label-5-branding-page`)

### What changed and why

Phase 4 of the [white-labeling plan](../../planning/white-label-ui-plan.md): an admin edits the brand in the Manager instead of with `curl`. [`docs/white-labeling.md`](../white-labeling.md) has a new "The Branding page" section.

- **Backend tweak.** `__brand__.js` now carries `assets: {logo, logoDark, icon, favicon, ogImage}`, booleans saying which slots have an image of their own (uploaded or from `assets-dir`); the hashes stay on the admin API. `/branding/logo` always answers an image, the bundled EDDI one when nothing is uploaded, so without this a brand that set only a name kept the EDDI wordmark (the Phase 3 gap). Both Vite plugins' `DEFAULT_BRAND_SCRIPT` and `brand.ts`'s `DEFAULT_BRAND` follow; `BrandDeliveryTest` gains a test for the flags and one that `ui/manager/src/lib/brand-css.ts` carries `BRAND_SCALE` verbatim.
- **Logos close the Phase 3 gap.** `BrandWordmark` shows the product name as a text wordmark when the brand has no logo (per mode: only a dark logo means text in light mode). `BrandIcon` draws the short name's initial on the primary colour when the brand has no icon. Branded image URLs carry `?r=<revision>` (`brandAssetUrl`), so a replaced logo shows at once despite `max-age=300`.
- **The page** (`src/pages/branding.tsx`, route `/manage/branding`, Admin section, `nav.branding`): names with character counts; five colours with a picker and a text field; the two toggles; a light and a dark preview (`components/branding/brand-preview.tsx`); five image drop zones (`components/branding/brand-asset-slot.tsx`); Save; Reset behind a confirmation; the source badge and last-saved line; a locked notice naming `eddi.branding.locked` and the source.
- **Validation** mirrors `BrandValidator` in `src/lib/brand-validation.ts` (caps 40/12/120, `<`/`>`, control and bidi characters, the colour grammar, WCAG contrast). Save is disabled while any field fails; server `violations` are shown on the field they name, and server `warnings` after an accepted save. A per-pair contrast badge updates as you type.
- **Preview** uses the brand's tokens on the preview container: `brand-css.ts` builds the same declarations `BrandDelivery.stylesheet` writes, and `index.css` gains `.brand-preview-light` / `.brand-preview-dark`, which restate each mode's surfaces and the EDDI defaults (token-definition lines, so the no-amber guard allows them). So the light panel is light on a dark page, and a cleared colour previews as the default instead of the brand still in effect.
- **Concurrency.** The PUT carries the revision the form was based on. A 409 with `currentRevision` shows a conflict notice and disables Save until **Reload latest** rebases the form. An image upload or removal moves the base revision without touching the text fields, so unsaved edits survive it and the next save does not conflict with the admin's own upload.
- **Live update** (`src/lib/brand-live.ts`): after every successful write, swap the shell's `brand.css` and favicon `<link>`s to `?r=<revision>` in place, inject a fresh `<script src="/branding/__brand__.js?r=…">` (no `eval`, CSP unchanged), and `setBrand(window.__EDDI_BRAND__)` on load. A failed reload leaves the brand in effect and shows a "reload the page" toast; the write itself is not failed.
- **API and hooks.** `src/lib/api/branding.ts` (typed `BrandingView`, `BrandUpdate`, `brandingErrorInfo`), `src/hooks/use-branding.ts` (query plus four mutations with `meta.silent`, since the page renders every refusal in place). `ApiClientError` gains an optional parsed `body`, and `ApiClient` passes `Blob`/`ArrayBuffer` bodies through unchanged, so the upload keeps the token-refresh path instead of a raw `fetch`.
- **Roles.** `/manage/branding` is `eddi-admin` in `lib/roles.ts`, so the sidebar and command palette hide it from everyone else (the page explains a 403 too).
- **MSW.** `src/test/mocks/branding-handlers.ts` is a stateful stand-in for the admin API (revision checks, validation, magic-byte type check, unsafe-SVG 400, 413, 415, locked 409) and, in the browser worker, answers `__brand__.js`, `brand.css` and uploaded images from the mock's state so the live update can be seen without a backend. Variants: `sessionStorage["eddi-mock-branding-locked"]="true"`, and the tagline `trigger a conflict`. `resetBrandingMockState` runs after every test.
- **i18n.** 88 `branding.*` keys plus `nav.branding`, translated in all 11 locales; the subtitle uses `{{productName}}`.
- **Fix found on the way:** `route-integrity.test.ts` was red since Phase 3, because the Updates route was declared as `path={UPDATES_PATH}` and the test reads the route table as text. The route is literal again; `brand.test.ts` pins `UPDATES_PATH` to it.

### Design decisions

- **The route is `/manage/branding` in the Admin section**, not a new Settings section: the Manager has no settings area, and the Admin section is where the other deployment-wide admin screens are. The page title says "Branding". The plan's "Settings → Branding" wording is for Phase 6 to align (the operator prompt names the page).
- **Hidden, not just refused, for non-admins.** The neighbouring admin entries are role-gated the same way through `SCREEN_ROLES`; this page has nothing to show a non-admin.
- **Images apply on upload, text on Save.** An image is one atomic request with its own errors; holding it until Save would mean staging binary data in the form. The page says so.
- **Mock delivery, not a second dev plugin.** The dev plugin keeps answering the defaults on load (as Phase 1 decided); the mock answers only what it owns. Its `/branding/*` handler had to be anchored at the origin: the leading-wildcard mask `*/branding/*` also matched `/administration/branding/assets/…` and sent uploads past MSW to the absent backend. `browser-handlers.test.ts` pins it.
