## feat(attachments): derived blobs owned by their root, per-source caps, lineage cascade and lifecycle events (2026-11-21)

**Repo:** EDDI (`feat/doc-derived-blobs`). This is work package WP-2a.2 of the PDF documents plan, the second package in the serial chain of attachment-store edits (after WP-2a.1, before WP-2a.3). It depends on WP-0.1 (#1461) and WP-2a.1 (#1471). Nothing user-visible: no code path stores a derived blob yet.

### What changed and why

The store can now hold **views of an uploaded file** (its manifest, page-window text, images, slices, summaries) that belong to the file's owner and die with it, and it announces when an uploaded file is deleted.

- **New types** in `engine/attachments`: `Derivation` (record + `Kind`: `MANIFEST`, `MANIFEST_PART`, `TEXT_PART`, `IMAGE`, `TABLE`, `AUDIO`, `PDF_SLICE`, `SUMMARY`, `DESCRIPTION`, `EMBEDDED`), `OwnerScope` (`CONVERSATION`; `USER` and `TEAM` declared for the libraries), `DerivedCaps` (pure cap arithmetic, like `AttachmentQuotas`), `DerivedBlobs` (hash, metrics, event firing), and the CDI events `AttachmentRootDeleted` and `AttachmentOwnerChanged`. `IAttachmentStore` gains `storeDerived`, `getDerivation`, `listDerived`, `findDerived`, `rootOf`, `ownerOf`, `pageCount`, `setPageCount`, the `OwnerRef` record and `AttachmentDerivedCapException`.
- **Owner = the root's (invariant I3).** A derived blob is a row (PostgreSQL) or GridFS file (MongoDB) of the same store with `root_ref` / `metadata.rootRef` set. Its conversation, user, tenant, owner scope and owner key are copied from the root inside the source lock, never taken from the caller. A view a grantee produces belongs to the root's owner, is readable by every reader of the root and survives the grantee's deletion. A view of a view keeps the original root and records its direct parent. The store computes the SHA-256 itself.
- **Access is decided on the root (X13, P9).** Every read joins the blob to its root and authorizes owner-or-grant there. A non-reader of a derived ref, and of any ref through the new methods, gets "not found" (no oracle); a stranger asking for a root still gets the existing "access denied". `grantAccess` given a derived ref grants its root.
- **Roots only in listings and file counts.** `listByConversation` and `listAccessible` filter derived blobs out, and the quota usage queries count roots only for file counts.
- **Quotas (P10).** Only `IMAGE`/`TABLE`/`AUDIO`/`EMBEDDED` bytes count toward the owner's byte quotas (conversation and user); text kinds and slices are exempt and bounded per root, so a grantee reading a file cannot use up its owner's upload quota. No derived blob counts toward a file-count quota.
- **Per-source caps.** Media share `eddi.attachments.derived.max-per-source` (200) and `.max-total-bytes-per-source` (50 MB); text kinds share `.max-text-bytes-per-source` (200 MB); `PDF_SLICE` is bounded by `.max-slices-per-source` (20) and the new `.max-slice-bytes-per-source` (50 MB), evicting the least recently loaded slice instead of refusing. Only a slice load touches `last_accessed_at`, so ordinary loads stay reads.
- **Write path.** `storeDerived`: read the source and its root (the caller must be able to read it) → take the locks in the fixed order conversation → user (media kinds only, when a byte quota is on) → `source:<rootRef>` (P8) → re-read the root (PostgreSQL: `FOR SHARE` in the same transaction; MongoDB: from the primary, and once more after the upload, deleting an orphan view if the root went meanwhile) → dedup → caps → quotas → insert.
- **No view outlives a delete that races it.** On PostgreSQL a `DELETE` that waited on a root held `FOR SHARE` works from its old snapshot and would miss the view committed meanwhile. So `delete(root)` locks the root `FOR UPDATE` before deleting, and `deleteByConversation` deletes the lineage of its roots once more in a statement after the wait. On MongoDB `deleteByConversation` sweeps the lineage of its roots after its cursor, and `storeDerived` re-checks the root after uploading, so a view is either swept or removed by its own writer.
- **Dedup** on `(ownerKey, rootRef, sha256)`, under the source lock; a unique partial index is a backstop. Two owners with the same file share nothing.
- **Cascade and events (P11).** `delete(root)` deletes the lineage and the grants, then fires `AttachmentRootDeleted` once; deleting a derived blob deletes it only and fires nothing. `deleteByConversation` deletes the lineage with its roots (they are stored under the owner's conversation) and fires once per root after the delete. It now returns the number of **roots**. An observer that throws is logged and undoes nothing. `AttachmentOwnerChanged` is declared and not fired yet (WP-5a.1).
- **Schema.** PostgreSQL: `ADD COLUMN IF NOT EXISTS owner_scope` (default `CONVERSATION`), `owner_key`, `root_ref`, `parent_ref`, `kind`, `unit_id`, `page`, `sha256`, `page_count`, `last_accessed_at`; partial indexes `idx_attach_lineage (root_ref, kind, unit_id)` and unique `idx_attach_dedup (owner_key, root_ref, sha256)`, both `WHERE root_ref IS NOT NULL` and built `CONCURRENTLY` on the backfill's thread with the legacy-grant index. MongoDB: the same names under `metadata.`, with the two indexes built at startup by `GridFsIndexInitializer` in their own time budget. New roots record `owner_key`; existing rows read `owner_key` empty as their conversation id. No backfill.
- **Metrics.** `eddi.attachment.derived.stored{kind}` and `eddi.attachment.derived.bytes{kind}`, on the Full Metrics dashboard's Attachments panel.
- **Settings.** `DocumentSettings.derivedCaps()` exposes the five caps to runtime code; the stores read the same properties themselves, like their quotas.

### Design decisions

- **Dedup key vs cache key.** The plan specifies dedup on `(ownerKey, rootRef, sha256)` and `findDerived` on `(kind, unitId)`. Identical bytes written under a second key return the first blob, which keeps its own key, so `findDerived` misses for the second key (a cache miss, never a wrong hit). A second write to an existing key with different bytes stores a new blob, and `findDerived` returns the newest. Both behaviours are pinned in the contract.
- **Designer keys stay off.** The designer block `documents.derived.*` is not made live: the store has no agent context at write time, so the keys would do nothing. The producers that store views (2a.5a onwards) apply them.
- **Platform Operator, MCP, UI: no change.** No endpoint, tool or designer key is added, and nothing stores a derived file yet, so there is nothing an admin could act on; the operator learns about documents with the first UI package (2a.7). `operator-revision.json` is not bumped.
- **GDPR.** Roots are conversation-owned in this release, so the existing conversation cascade reaches every derived blob; no new erasure participant (plan §3.3).

### Tests

`AttachmentStoreContract` gains 19 cases run on both databases by `GridFsAttachmentStoreIT` and `PostgresAttachmentStoreIT` (46 each, green locally): grantee-written view owned by the root owner and surviving the grantee; same bytes across owners share nothing; stranger told "not found" by every method; root delete leaves no lineage or grants and fires once; conversation delete fires per root; deleting a view; roots-only listings and counts; text and slices leave the upload quota unchanged while media count exactly once; view of a view; parent from another root refused; `findDerived` exact key and newest; the media cap; slice LRU eviction; grant on a view; page count; view of a deleted root; a root stored before this release (no owner key); the owning user's byte quota. `PostgresAttachmentStoreIT` also plays both delete races with a raw connection holding the root `FOR SHARE`; `GridFsAttachmentStoreIT` covers a view of a blob known only by its ObjectId. 29 mutants were run against these tests and all were killed. `DerivedCapsTest` and `DerivedBlobsTest` cover the pure parts; `DocumentSettingsDefaultsTest` the defaults.
