## fix(operator): the prompt's literal braces no longer reach Qute, and the tool-name guard runs in the unit suite (2026-11-15)

**Repo:** EDDI (`fix/operator-prompt-and-tool-names`)

Two defects were reported on both 6.7.0 deployments. Both root causes were already fixed on `main` by #1314 (merged earlier today); what was still open is described below, with the investigation, because the deployed operators will not change until they are upgraded.

### Defect 1: `Template processing failed for LLM parameter 'systemMessage'`

- **Root cause, as shipped in 6.7.0.** The operator's system prompt is stored as an LLM task's `systemMessage`, which `LlmTask` renders as a Qute template on every turn. The `forEach` line of the apicalls section opened with a literal `{` (`forEach {pathToTargetArray (a plain dot path such as …, required), iterationObjectName (…)}`), which Qute reads as an expression with a virtual method. Qute's message echoes it as `{required),(iterationObjectName}`, the text in the log. A second line, `eddi_email_outbound_total{outcome: sent, …}`, read as a namespaced expression. A failed render is only logged, and `LlmTask` then sends the RAW prompt, so every turn logged an ERROR and the model saw unrendered `{#if}` sections. The deploy-time `TEMPLATE_DOES_NOT_PARSE` finding is the same parse error caught by the compatibility lint.
- **What #1314 did.** It reworded those two lines (operator revision 60 → 61). It did not touch the other 20 or so brace spans in the prompt (`eddi_cluster_nats_errors_total{cause}`, `eddi_turn_rejected_total{reason="…"}`, `/agents/{agentId}/profile`, the guardrail variables `{input}` `{output}` `{risk}` `{context}`, …). Those parse, so nothing is logged, but with `property-not-found-strategy=NOOP` each renders as nothing: the operator was told a guardrail template is "rendered with , and" and that a metric takes no labels. The prompt was 860 characters shorter after rendering than before.
- **Fix.** `buildOperatorSystemPrompt` now escapes every `{` in an unparsed block of its own (`{|{|}`, the `TemplateEscaping` convention), in one place, instead of rewording mention by mention. The rule is conservative on purpose: it does not try to mirror which braces Qute's lexer would read as an expression. Exactly three things are left alone: the Manager's own per-turn context block, matched as that exact text (so `{context.screen}` or `{#if …}` typed into the instructions is literal); the `${vault:…}`/`${vars:…}`/`${connection:…}`/`${caller:…}` mentions that `LlmTask` escapes itself (the escape splits around a mention, because wrapping one twice would print the markers); and any unparsed block already there. A prompt section added by any other branch is covered without anyone remembering to escape it. New: [`qute-literal.ts`](../../ui/manager/src/lib/operator/qute-literal.ts).
- **Guard.** The outcome is written down once as a corpus ([`qute-literal-corpus.json`](../../ui/manager/src/lib/operator/__tests__/qute-literal-corpus.json)) and checked on both sides. `OperatorPromptQuteCorpusTest` (Java, plain unit suite, no Docker, no browser) renders every case through EDDI's real `TemplatingEngine`, forced to parse (the engine returns a string with none of its control characters untouched, so `{0}` or `{_x}` rendered alone proves nothing), and checks that the escaped form renders back to exactly the text. The corpus includes mixed input (`{0} {input}`, `{_x}`, Unicode identifiers, `{@java.lang.String x}`, `{#if …}` and `{context.screen}` typed by an admin, `{passwordRef: ${vault:key}}`) and the context block, which stays evaluated. `qute-literal.test.ts` (vitest) applies the same rule to the corpus and to every prompt the Manager can send, for both scopes and the longest brand name, and fails on any brace left unescaped except in the context block. A Qute change that makes an escaped form render differently fails the Java test; a new unescaped brace fails the vitest. The Java test also reproduces the logged parse error from the 6.7.0 `forEach` line.
- **Operator revision bumped to 79 (main was already at 78).** The text sent to `setup-api` changed, and the revision fingerprint now also covers the SENT prompt (not only the default body), so a later change to the escaping reaches existing operators too. The deployments still running a 6.7.0 operator need the Upgrade (a Reconfigure with every setting carried over), and the backend must be a build with #1314.

### Defect 2: `Tool name collision: http tool 'list' clashes with the already-registered http tool`

- **Root cause.** `GET /groupstore/groups/{groupId}/lessons` and `GET /groupstore/groups/{groupId}/outcomes` were both JAX-RS methods called `list`, and the spec's operationId is the method name (`operation-id-strategy=METHOD`). Both carry the tag "Agents / Groups", so `setup-api` put them in one apicalls config as two calls named `list`. Tool assembly registers by name, so the second, the **outcomes tool**, was dropped on every turn, although the endpoint was granted and the admin was told so. No second config and no upgrade re-adding one was involved; the collision is inside one generated config.
- **What #1314 did.** The two operations have their own ids (`listGroupLessons`, `listGroupOutcomes`), and `McpApiToolBuilder.uniqueToolName` keeps names unique across every group of one build, which `setup-api`, the dry run and `ApiAgentSyncService` all share.
- **Guard.** `OperatorToolNamesTest` rebuilds the spec from the JAX-RS interfaces (449 operations; path, verb, tag and method name are all that naming reads) and holds three lines: the generator hands every operation of the whole spec a distinct tool name and response object; EDDI's own spec repeats no operationId beyond a listed, shrinking set of seven (none reachable from the operator); and no endpoint in the Manager's allow-list (`tool-scopes.ts`, including the GET/PUT/POST/PATCH entries it builds per extension store, which the test expands itself and fails on a template it does not know) shares its id, nor is renamed by the generator. Before this, only the Operator Activation E2E (Docker, an image build) could notice.
- **Caught on merge.** The guard's first catch after landing: #1377 added `GET /administration/spend-control-changes/{id}` as a method named `read`, which collided with `GET /administration/update-check`. It now has `operationId = "readSpendControlChange"`; the operator allow-list matches verb and path, so neither the allow-list nor the fingerprint changes.

### Verification

Both guards fail without their fix: the Java tests when `listGroupOutcomes` is given the lessons id, and when the generator stops de-duplicating; the vitest when the prompt is no longer escaped, when the rule leaves a brace unescaped, splits no longer around a mention, or the context block is not matched exactly.

```decision-log
| 2026-11-15 | Escape literal braces when the operator prompt is built, not reword them one by one | Rewording fixed the two spans somebody noticed in 6.7.0 and left twenty that silently rendered as nothing; every branch that edits the prompt would have to repeat it | Rewording each mention; a `{{…}}`-style convention authors must remember |
| 2026-11-16 | Escape every brace except three named exceptions, instead of mirroring Qute's lexer | A mirrored rule (letters, `! # / \|`, `{@…}`, `{0}`, Unicode identifiers, backslash escapes) drifts and what it misses is dropped silently; the conservative rule needs no knowledge of the lexer | Keeping the lexer mirror and patching it per review finding |
| 2026-11-15 | The prompt guard is a corpus shared by a Java test (real Qute) and a vitest, not a Java test that reads the prompt | The prompt is assembled in TypeScript from template literals, so a Java test would parse TS or need a committed generated copy that ~20 open PRs would conflict on | A golden copy of the prompt; a JS Qute port in the browser |
```
