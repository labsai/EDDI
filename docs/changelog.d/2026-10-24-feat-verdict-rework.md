## ✨ feat(hitl,groups): humans and groups produce verdicts — revise with the note, rework within a run, stop on a verdict (2026-10-24)

**Repo:** EDDI (`feat/verdict-rework`) — item E2 of `planning/evaluated-generation-plan.md`.

### What changed and why

Three places where a check already ran but its verdict could not repair anything now can, each off by default.

**1. Single-agent HITL: `hitlConfig.onRejection: "REVISE"`** (decision 9.5: a `hitlConfig` policy, not a new verdict value). Under the default `SKIP` a rejected rule pause skips the remaining tasks, as before. Under `REVISE`, a rejection **with a human's note** has the same model revise the answer it gave before the pause: one tool-less re-ask over the frozen request that produced the draft (system prompt, history, retrieved context, tool results), the draft as the assistant turn and the note as the user turn, then the pipeline continues from the task after the model's, so a rule that paused on the draft pauses again on the revision. `maxRevisionsPerTurn` (1..10, default 3) bounds it.
- Scope: behavior-rule (`RULE`) pauses only. A rejected tool call (`TOOL_CALL`) is a rejected action, not a rejected answer, and already reaches the model as a tool result with the note; it is unchanged. A rejection without a note, an automated one (`system:*`), a Slack button (its note is its own attribution), a pause before any answer, an answer from a later task or workflow, an over-cap request, a spend refusal, a model failure, a failed `responseValidation` or a guardrail block all fall back to `SKIP`, and `hitl:revision:outcome` records which.
- The note is data: concatenated into the user message, never template source. The revision passes `responseValidation` and the output guardrails and asks the spend gate first; its tokens and cost are recorded like any answer's.
- The candidate (`HitlRevisionCandidate`) is recorded by `LlmTask` only while the policy is on, stamped with its pipeline position by `LifecycleManager`, and persisted by the RULE pause as step data `hitl:revision:candidate` — so it travels through both stores unchanged, is scrubbed of secret input and context with the step, is withheld from `returnDetailed` and from the approver's full snapshot, and is removed when the pause is decided. Cap `eddi.hitl.revision.transcript-max-bytes` (256 KB). The round count rides on the candidate, so the bound holds across re-pauses and reloads.
- New seam: `IAnswerRevisingTask` (implemented by `LlmTask`) and `ILifecycleManager.reviseAnswerAt`, which runs one task's revision with its audit entry and converts a later task's gated tool call into a TOOL_CALL pause. Output that the draft and the tasks after it wrote is cut back before they run again.
- Records: `hitl.approval` carries `onRejection: REVISE`; meter `eddi_hitl_revision_total{outcome}`.

**2. TASK_FORCE `maxReworks`** (group field, 0..5, default 0). A task that fails VERIFY returns to `ASSIGNED` with the verifier's feedback (`SharedTaskList.reworkTask`, the same transition and feedback channel as `onTaskRejection: RETRY`), the nearest EXECUTE phase runs it again inside the VERIFY phase and VERIFY checks it again, up to `maxReworks` times per task. Stopped by `maxTurns` (a round needs one turn per task plus the verifier's) and the cost ceiling; a rework that could not run ends `FAILED`, never stranded. Not applied when EXECUTE gates tasks for human approval. Counts persist in `taskList.reworkCounts` (additive, no schema bump: an older pod re-saving drops them, which fails soft). An unparseable verdict keeps the fail-open auto-verify but is now warned and counted (`eddi_group_verify_unparseable_total`); reworks are `eddi_group_task_reworks_total`.

**3. `convergence.mode: "VERDICT"`** on a repeating phase. The moderator reviews the latest repeat against the question and the phase ends once it passes (`{"passed": true}` as a JSON boolean; anything else keeps it going). `threshold` is unused and `minRepeats` may be 1. `"SIMILARITY"` stays the default, and an unknown mode is a save-time 400.

**Compatibility:** stored agent and group configs load and behave identically — `onRejection` absent is `SKIP` and captures nothing, `maxReworks` absent is 0, `convergence.mode` absent is `SIMILARITY` with the old `minRepeats` floor. Old pods ignore the new fields (`FAIL_ON_UNKNOWN_PROPERTIES` is off). The approval API (REST `/resume`, MCP `resume_conversation`, Slack buttons, Manager approvals) is unchanged in shape.

**Manager:** the agent HITL section gains "When a reviewer rejects" and "Revisions per turn"; the phase editor gains a convergence "Stop when" select (VERDICT hides the threshold, floor 1); Task force settings gain "Reworks after a failed verification". All 11 locales. **Platform Operator:** a cheatsheet entry for the three settings; revision 36 → 37. Four other open branches (E1c, E4, E5, #1121) also bump `operator-revision.json`, so whichever lands second must re-bump and refresh the fingerprint.

**Docs:** [`hitl.md`](../hitl.md) (new "Revise with the reviewer's note"), [`group-conversations.md`](../group-conversations.md) (rework within a run, `convergence.mode`), [`llm-resilience.md`](../llm-resilience.md), [`metrics.md`](../metrics.md), [`configuration-reference.md`](../configuration-reference.md); three dashboard panels, synced to the Kubernetes copy.

### Verification

New tests: `LlmTaskHitlRevisionTest`, `ConversationHitlRevisionTest` (including a resume after a JSON and a BSON round trip of the paused snapshot), `LifecycleManagerRevisionTest`, `HitlRejectionPolicyConfigTest`, `TaskForceEngineReworkTest`, `ConvergenceVerdictModeTest`, plus Manager tests for the three editors. Nine mutants (revision bound, default policy, note requirement, automated decisions, per-task rework bound, `maxReworks` default, rework turn budget, convergence default mode, boolean-only verdict) are each killed.
- End-to-end ITs on MongoDB and PostgreSQL (`HitlRevisionIT`, `GroupVerdictIT` and their `postgres/` twins), with WireMock as the model: a rejection with a note revises over the frozen request (the note and the draft reach the model, the candidate and its round count survive the store across both pauses, approval delivers the revision only), `no_note` and `exhausted` skip; VERDICT convergence stops on a JSON `"passed": true` while prose, a string `"true"` or a failing judge run every repeat, and an unknown mode is a 400; TASK_FORCE `maxReworks` sends a failed task back with the verifier's feedback and persists `taskList.reworkCounts`. Not persisting the candidate, dropping the rework feedback and never passing a verdict each fail them.
- **Fix — the raw read leaked the frozen request.** `GET /conversationstore/conversations/{id}` (the owner's and the Platform Operator's raw read) served the paused step's `hitl:revision:candidate` whole, so its `transcriptJson` — the compiled system prompt and every tool result — reached anyone allowed to read the conversation, in `result` and again in the `possibleResults` copy. `ConversationMemoryUtilities.redactRawPendingToolCallsForRead`, already the raw surface's single redaction point for the tool-call batch, now also withholds the candidate's frozen input (`REVISION_CANDIDATE_FROZEN_INPUT_FIELDS`) on every step and the redo cache, keeping the draft and bookkeeping. The other surfaces were already safe: `returnDetailed` (REST, MCP `read_conversation`, the Manager's inspector and the `/simple` read) drops the key, `approval-status?detail=full` (REST and MCP) removes the candidate, and the GDPR export carries only `conversationOutputs`. `ConversationMemoryUtilitiesRevisionRedactionTest`; `HitlRevisionIT` asserts no candidate entry carries the transcript or the system prompt while the revision request still carries it. **Not changed, and older than E2:** the raw read still serves `audit:compiled_prompt`, the LLM task's own audit step data (written on every answered turn while the audit ledger is on), which holds the same compiled system prompt; the IT pins that this is the only place it appears. Whether the raw read should drop `audit:*` like `returnDetailed` does is a separate decision. `hitl.md` now says `hitlDecision` reads `REJECTED` only until the revision is decided.

### What's next

The judge machinery of E1 (#1121) could serve as VERIFY's and VERDICT's verdict parser, and the agent-testing harness's LLM-as-judge expectation should reuse it. A failing VERDICT review is recorded but not shown to the members of the next repeat; feeding it back is a follow-up.
