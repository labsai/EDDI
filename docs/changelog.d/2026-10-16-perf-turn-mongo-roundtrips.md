## perf(engine): fewer MongoDB round trips per conversation turn (2026-10-16)

**Repo:** EDDI (`perf/turn-mongo-roundtrips`)

A JProfiler profile of the virtual-thread build (labsai/EDDI#1045) counted about 17 MongoDB reads per turn, each with a named caller, and found the driver's connection pool to be the ceiling once turns run on virtual threads (418 operations queued for a connection at 500 in-flight turns). This branch removes the redundant ones, one commit each, in the order the profile suggested.

### What changed and why

- **One conversation-descriptor read per request.** A REST turn read the same descriptor three times before it started: `RestAgentEngine`'s ownership check, the same check again in `ConversationService.say`, and the soft-delete check right after it. New `ConversationDescriptorMemo` (`@RequestScoped`) remembers the resolved descriptor (live, archived or none) for the rest of the request; `ConversationAccessGuard` and `ConversationService.isSoftDeleted` both resolve through it. Only the descriptor is shared, never a decision: each check still compares the owner against its own identity. Store failures are not remembered, every write through `ConversationDescriptorStore` forgets the conversation, and outside a request (worker threads, schedules) every lookup reads the store as before. Saves 2 reads per turn on the request thread, where the profile saw most of the pool waits.
- **`updateTimeStamp` is one update (WS3c).** It was `getCurrentResourceId` + `readDescriptor` + `ModifiableHistorizedResourceStore.set` (which reads again) + a version-checked full replace: 3 reads and a write on every turn's completion path. New storage SPI method `IResourceStorage.setNumberField(id, field, long)`: MongoDB `updateOne` with `$set`, PostgreSQL `UPDATE … SET data = jsonb_set(…, to_jsonb(?::bigint))`, both on the live row only (a soft-deleted or unknown id writes nothing). `DescriptorStore.touchLastModified` uses it; `ConversationDescriptorStore.updateTimeStamp` falls back to the old rewrite only for a backend without it. The value is stored as a number, exactly as the persistence mapper writes dates (epoch millis), so retention (`RestConversationStore` compares `getLastModifiedOn()`) and the listings' server-side sort see no difference — `DescriptorTouchParityTest` checks the read-back date, the stored type (BSON int64 / jsonb number), the sort position among fully written descriptors and that no other field or version changes, on a real MongoDB and PostgreSQL. A side benefit: the replace could overwrite a concurrent edit of any other descriptor field with the copy it had read; a single-field update cannot. A failure is now logged and swallowed instead of thrown into the completion callback, where it would have broken the response of a turn that was already stored.
- **Signing negative cache (WS8.1).** `AgentSigningService.loadPrivateKey` cached only keys it found, so with an active vault every audit entry of a keyless agent (three per turn) asked the vault — a `secretvault_secrets` read — only to hear "not found" again. A "not found" is now remembered for 60 s per key (`MISSING_KEY_TTL_NANOS`, bounded at 10 000 entries). A vault *failure* is never remembered. Generating or rotating a key on this node evicts the entry, so the new key signs at once — including when a lookup that started before the key was stored answers "not found" after the eviction: every eviction is counted, and a miss whose lookup saw the count move is withdrawn instead of remembered; a key created on another node is picked up within the TTL, and entries written meanwhile carry no signature, as they would have a moment earlier. This is also step 7 of PQ-5a in the PQC plan — implemented once, here.
- **Pinned agent configuration from memory.** `ConversationHitlService.lookupAgentConfigPinned` read the agent document at the conversation's pinned version on every turn, only to learn its tool-approval policy. New `AgentConfigurationCache` (`@ApplicationScoped`, Caffeine, 1 000 entries, 30 min after last access) keeps `(agentId, version)` configurations: a stored version never changes (edits write a new version; the only in-place writers are the descriptor stores and the startup migrations). Absence and store failures are not cached, so the HITL gate still fails closed on a read error and still falls back to the latest version when the pinned one is gone. `AgentFactory` drops an agent's entries on every deploy and undeploy. `WorkflowTraversal`'s own short-lived traversal cache is left as it is; WS1 should hang its invalidation off the same deployment hooks.
- **One full conversation load per turn (WS3a).** The conversation-id entry points (`say` / `sayStreaming` without an environment — REST, SSE, MCP, Slack, `/v1`) load the snapshot to find the agent and run the pre-turn checks, then called the environment-qualified overload, whose admission (`admitTurn`) loaded the same document again. That load is now handed down (`preloaded`) and converted instead of re-read. The idempotency admission (`admitOrServe`) still runs between the load and the turn, as before; a deferred duplicate re-enters the whole entry point and loads afresh. The environment-qualified overloads (A2A, group members, tests) still load on their own. Staleness is unchanged: the second load used to happen a moment after the first, and the step runner's `reloadIfSuperseded` revision check still guards the turn either way.

### Measured

Load-test harness from labsai/EDDI#1044 (`steady`, 50 conversations × 20 turns, mock LLM delay 0 ms, everything in Docker), `origin/main` (`aa8806c68`) against this branch, 1 000 turns each. MongoDB operations per successful turn (`serverStatus().opcounters`, per-collection from `top`):

| | Before | After |
|---|---|---|
| **Queries per turn** | **16.67** | **6.65** |
| `descriptors` queries | 6.05 | 1.05 |
| `conversationmemories` queries | 5.04 | 4.08 |
| `secretvault_secrets` queries | 3.05 | 0.06 |
| `agents` queries | 1.09 | 0.09 |
| Updates / inserts per turn | 2.05 / 3.11 | 2.05 / 3.11 |
| Turns/s (single run, indicative) | 117 | 146 |

On PostgreSQL (`pg_stat_statements`, `SELECT conversation_state, data FROM conversation_memories`), full conversation loads per turn went from 2.09 to 1.13 with short conversations, and from 2.74 to 1.88 in the `long-conversation` scenario (10 × 200 turns). An instrumented build traced the excess over MongoDB's 2.0 to `ConversationStepRunner.reloadIfSuperseded`: the reply is delivered before the turn is persisted, and on PostgreSQL the full-document append grows with the conversation, so the client's next turn is often admitted against the row as it was before the previous turn's write and reloaded when it runs (68 % of turns on `main`). That reload is what keeps the turn on the current document, so it stays; avoiding it means loading at run time when a turn is already in flight, or a cheaper PostgreSQL write (WS6/WS7).

The descriptor write stays one per turn, now a `$set` instead of a replace. Left on the turn path: one descriptor read (the ownership check), the full conversation load, the state and revision projections, and the GDPR restriction check on `usermemories`.

### Design decisions

- **A request-scoped memo, not new parameters.** The checks sit behind `IConversationService.say` / `sayStreaming`, which Slack, MCP, `/v1` and A2A also call; threading a resolved descriptor through all of them would have changed every signature for a saving that only the REST path needs twice.
