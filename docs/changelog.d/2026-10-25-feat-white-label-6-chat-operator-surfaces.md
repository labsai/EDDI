## 🎨 feat(chat): deployment brand for title, logo, accent and head — white-label phase 5 (2026-10-25)

**Repo:** EDDI (`feat/white-label-6-chat-operator-surfaces`)

### What changed and why

Phase 5 of the [white-labeling plan](../../planning/white-label-ui-plan.md): the Chat UI widget follows the deployment brand. [`docs/white-labeling.md`](../white-labeling.md#the-chat-ui) has a new "The Chat UI" section, and the [Chat UI README](../../ui/chat/README.md) and [embedding guide](../chat-ui-embedding.md) say what overrides what.

- **`ui/chat/src/api/brand.ts`** reads `window.__EDDI_BRAND__` field by field, with `DEFAULT_BRAND` equal to the Vite plugin's `DEFAULT_BRAND_SCRIPT` (`brand.test.ts` pins it; `BrandDeliveryTest` already pins the plugin against the backend). It derives the header title (`brandTitle`), the logo (`brandLogoUrl`: `/branding/logo?r=<revision>` when a logo is uploaded, `null` meaning "show the name as text" when branded without one, EDDI's logo otherwise), the tab title (`brandDocumentTitle`) and the brand's config layer.
- **Precedence**, highest first: URL parameters, the embedder's `<ChatProvider config>`, the agent's own appearance (`agentAppearanceLayer()`, a named seam that answers nothing yet), the brand, the built-in defaults. `ChatProvider` builds its initial config from those layers once, at mount; `ChatWidget` dispatches the URL's config over it as before.
- **Header.** The title nobody overrode is the product name; an explicit `?title=` still replaces the agent name. A brand without a logo shows its name as a text wordmark (`chat-header__title--wordmark`). Alt text is the title. The tab title is `<agent> — <product>` when branded and exactly `<agent> — EDDI Chat` / `EDDI Chat` when not.
- **Accent, and the old gap.** `ChatConfig.accentColor` was stored but never applied. It now goes through `applyAccentColor`, the same function `?accentColor=` uses (accent, user bubble, focus ring, the `color-mix` tints). One effect applies `config.accentColor` and then the URL's colour parameters, so `?accentColor=` beats the embedder and the brand, and `?userBg=` still beats the bubble colour an accent derives. `defaultConfig` no longer carries `accentColor: "#113B92"` or the logo URL: unset means "the stylesheet's tokens" and "the brand's logo", so setting either is always an override and an unbranded widget paints exactly as before.
- **Demo route.** `ChatRoute` wraps the `/chat/:environment/:agentId[/:userId]` routes; under a brand `/chat/demo/showcase` shows a neutral "The demo is not available on this site." (`demo.unavailable`, all four locales) instead of EDDI's showcase script, and makes no request.
- **Head.** `chat.html` already had the placeholders, `/branding/favicon.ico` and `/branding/og-image` from Phase 1. The dev entry `index.html` now has the same brand wiring (placeholders, `brand.css`, `__brand__.js`), the plugin knows its defaults, and `vite-plugin-brand.test.ts` grades both shells. `vite-proxy.test.ts` exempts `/branding`, which the dev plugin serves itself.
- **Guard.** `src/no-eddi-brand-literal.test.ts` fails on `\bEDDI\b` in a locale value, a string literal or JSX text outside an exact allow-list (the unbranded defaults and one integrator console warning) and `demo-api.ts`. It caught the old tab-title template when mutated back in.

### Design decisions

- **The accent is applied in JS, not only by `brand.css`.** `brand.css` sets `--chat-accent` alone, so the user bubbles, focus ring and quick replies stayed EDDI blue. The JS path sets the full set the URL parameter sets, as inline styles that beat both stylesheets. Both read the same resolved value (chat accent, else primary), so they never disagree; `brand.css` stays for the first paint.
- **The demo route is refused in the client, not with a backend 404.** The Chat shell is one SPA page; a 404 would need a route-aware resource for one path. The neutral state shows nothing of EDDI either way.
- **The "Chat" suffix was not made translatable.** Branded titles no longer carry it, and the unbranded title stays byte-identical.

### Verified

In `ui/chat` on Node 24: `npm run typecheck`, `npm run lint` and the full `npm test` — 32 files, 531 tests, green. New: `brand.test.ts` (defaults = plugin script, normalisation, title/logo/tab-title/config layer), `ChatWidget.brand.test.tsx` (12 tests: unbranded unchanged, branded logo and alt, text wordmark, tab title, `?title=` and `logoUrl` still override, brand accent, `?accentColor=` beats the brand, `config.accentColor` beats the brand and an unsafe one is ignored, `?userBg=` beats the derived bubble colour, demo route branded and unbranded) and the guard. Mutation checks: the old `ChatHeader` fails the guard and two header tests; dropping `applyAccentColor(config.accentColor)` fails three accent tests; disabling the demo guard fails the demo test. Backend: `BrandDeliveryTest,BrandedShellRendererTest,RestHtmlChatResourceTest,ChangelogFragmentTest,Documentation*Test,BuildQualityGatesTest,ImportStyleTest` — 93 tests, green. Against a real backend (full `./mvnw package`, the jar on MongoDB 7, an agent with no workflows deployed): unbranded, the demo and a chat look as before (EDDI logo, `EDDI Chat`, no inline accent); with a name and teal colours, the header shows "Zebra Labs" as text, the user bubble and focus ring are teal, the tab title is the product name and the demo shows the notice; after an SVG logo upload the header shows `/branding/logo?r=2` with alt "Zebra Labs", and the head carries the brand's description, `theme-color`, favicon and `og:image`; `?accentColor=%23cc3366&title=Support%20Desk` turns the bubble pink and titles the tab "Support Desk" under the brand; after a reset everything is EDDI again.

### What's next

Phase 6 (Platform Operator, Keycloak theme download) and Phase 7 (brand-leak E2E). The per-agent appearance seam (`agentAppearanceLayer`) needs its own design pass (§4.6). Noticed, not changed: `chat.html` lacks the `viewport-fit=cover, interactive-widget=resizes-content` viewport the dev `index.html` got in #1075, so production phones do not get that fix.

## 🎨 feat(branding): operator persona, API surfaces, Keycloak theme download and Helm values — white-label phase 6 (2026-10-25)

**Repo:** EDDI (`feat/white-label-6-chat-operator-surfaces`)

### What changed and why

Phase 6 of the [white-labeling plan](../../planning/white-label-ui-plan.md) (§4.7–4.9, R6, R7, R9). [`docs/white-labeling.md`](../white-labeling.md) gains "The Platform Operator", "API surfaces", "The Keycloak login page" and "Helm"; [`docs/kubernetes.md`](../kubernetes.md#white-labeling-helm) and the [configuration reference](../configuration-reference.md#white-labeling) point at them.

- **Platform Operator** (`ui/manager/src/lib/operator/system-prompt.ts`, revision **38**). The preamble now opens "You are the <product> Platform Operator" and carries the one sentence that still names the engine ("built on the EDDI engine; its documentation and `eddi.*` configuration properties use that name"); every other mention says "this deployment", "the platform" or "the engine". The default body is brand-independent, so a rebrand never flips an untouched body to "customized", and the revision fingerprint hashes the preamble with the EDDI default name. The body tells the operator that Admin → Branding exists, what it controls, that it has no tool for it and that its own name changes on Upgrade; the docs map gains "white-labeling". Braces are dropped from the name in the prompt (it is a Qute template server-side and the validator allows `{}`). New operators are named `operatorAgentName()` = `<product> Platform Operator`. The branding endpoints stay off the allow-list; `tool-scopes.ts` documents the exclusion and a test keeps any `/branding` path out of both scopes. `use-current-screen-context.ts` gains `/manage/branding` → `branding`. The operator's user-facing errors say "this deployment" / "the server" instead of EDDI.
- **Identification audit.** Activation, supersede, upgrade, trust (`useOperatorTrust`) and discovery read the `[eddi-platform-operator]` descriptor marker or the configured agent id; the only name read is discovery's fallback for pre-marker operators (`/operator/i`), which every built name satisfies. A new test proves a marked operator named "Acme Assist Helper" is still recognised; requiring a name match fails it.
- **Guard.** `no-eddi-brand-literal.test.ts` loses its Phase-6 exclusions and now also grades `new Error("…")` messages.
- **Manager, other.** The A2A card preview on the agent page uses the product name. The two generated LLM-parameter notes say "the server" (`model-parameters.json`, regenerated into `llm-parameter-catalog.data.ts` and `docs/llm-parameters.md`). On the Branding page an empty colour's swatch shows what it falls back to — dark → light, chat accent → primary, otherwise the unbranded default (`UNBRANDED_COLORS`, pinned to `index.css` and the chat's `variables.css`) — instead of black.
- **A2A** (`AgentCardService`): provider, fallback name and description, default skill and token description use the product name, read per card; an unreadable brand serves the card under EDDI.
- **OpenAPI** (`BrandedOpenApiRoute`): under a brand `info.title` is `<product> API` and the LABS.AI contact is dropped; unbranded the request falls through to SmallRye's cached document untouched. A first attempt as a `RUNTIME_PER_REQUEST` `OASFilter` passed its unit tests and did nothing at runtime: SmallRye's `OpenApiDocument.initialize` runs `filterModel` and then `ConfigUtil.applyConfig`, so the `info-*` properties overwrite whatever a filter set. Found only against the real jar.
- **Swagger UI** (`BrandedSwaggerUiRoute` + `SwaggerUiBranding`, R6 spike → implemented). Swagger UI requests `index.html`, `logo.png`, `favicon.ico` and `style.css` relative to `/q/swagger-ui/`; Quarkus serves them from generated web-jar resources (`META-INF/io.smallrye_smallrye-open-api-ui__jar/META-INF/resources/openapi-ui/`). A Vert.x route at the shell route's order answers those four while a brand is set: title and alt from the product, no footer, the brand's logo (or its name as text), its favicon/icon, and the stylesheet with amber accents swapped per mode (the PUT method colour stays). Unbranded, and under `quarkus:dev` where the files are not on the classpath, it falls through.
- **MCP** (`BrandedMcpServerInfo implements InitialResponseInfo`): `serverInfo.name`/`title` are the product name under a brand, asked per `initialize`; an explicit `quarkus.mcp.server.server-info.name` wins.
- **Keycloak theme ZIP** (`KeycloakThemeExport`, `GET /administration/branding/keycloak-theme.zip`, `eddi-admin`). `pom.xml` copies `keycloak/themes/eddi` to `keycloak-theme/eddi` on the classpath (outside `META-INF/resources`). The ZIP is the theme renamed `brand`: the shipped files byte for byte, `theme.properties` loading `css/brand-overrides.css` last, the generated overrides (the `--eddi-*` palette per mode plus both PF5 tiers, F18; warnings stay amber; text heading when there is no logo), the brand's logo / dark logo / ICO-or-PNG favicon, and a README with `loginTheme`, `displayName` and HTML-escaped `displayNameHtml` as JSON. Fixed file list (a test pins it to the directory), fixed entry times, colours re-validated on output, the name only in the README. Branding page: "Download login theme" (all 11 locales), MSW handler, `openapi-operations.json`.
- **Helm** (chart **2.13.0**, `EXPECTED_CHART_VERSION`): `eddi.branding.*` values (names, colours, `poweredBy`/`showUpdateCheck`, `locked`, `assets.configMap` + `mountPath`) render `EDDI_BRANDING_*` only when set and mount the ConfigMap read-only as `assets-dir`. Off by default. `HelmBrandingValuesTest` pins the mapping.

### Design decisions

- **Neutral wording over i18n for the operator's errors.** They are thrown `Error` messages shown verbatim; "this deployment" / "the server" removes the leak without a second translation path for one screen.
- **The operator's persona lives in the non-editable preamble.** The body stays brand-free, so "is the body the default?" keeps working across a rebrand, and the persona is rebuilt on every Upgrade/Reconfigure.
- **OpenAPI as a response rewrite, not a filter or a property change.** Moving the title and contact from properties to `@OpenAPIDefinition` was tried so a filter would win; Quarkus then defaults the title to `quarkus.application.name` + " API" ("eddi API") and dropped the annotation contact, changing the unbranded document. The route keeps the unbranded document byte-identical and cached, and costs one parse and serialisation per `/openapi` fetch only while branded.
- **Swagger's page is derived from the generated file** rather than re-implemented, so a Quarkus upgrade that changes the page keeps working (the rewrites are regex replacements that leave a non-matching page as it was).
- **The Keycloak favicon is replaced only by an ICO or PNG**, because Keycloak links `favicon.ico` by name; an SVG icon keeps the shipped one and the README says so.
- **No Keycloak theme mount in the Helm chart.** Its in-cluster Keycloak mounts no themes today; documented instead of adding a second ConfigMap layout. `install.sh` / `docker-compose.auth.yml` are documented, not changed.
- Outbound `User-Agent` and logs keep EDDI, as decided.
