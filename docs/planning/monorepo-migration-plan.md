# Monorepo Migration Plan — EDDI + EDDI-Manager + EDDI-Chat-UI

> **Status:** Proposed, not started.
> **Author context:** This document is self-contained. An implementing agent should need no
> other conversation context. Read it top to bottom before touching anything.

---

## 1. Why

The three repos are already one build unit — but held together by hand.

**`EDDI-Chat-UI` cannot be built standalone at all.** Its `vite.config.ts` sets:

```ts
outDir: resolve(__dirname, "../EDDI/src/main/resources/META-INF/resources")
```

The build writes straight into a sibling checkout of the backend. There is no `dist/`.

**`EDDI-Manager` is worse in a subtler way.** It builds to its own `dist/`, and then
`deploy-to-local-eddi-repo.sh` copies the assets into the backend and **`sed`-patches three
HTML shells that live only in the backend repo**: `manage.html`, `welcome.html`,
`workforce.html`. Those three files are the real production entry points. They are *not* in
the Manager repo, are not generated by Vite, and have no source-of-truth relationship to the
Manager source at all. The Manager's own `index.html` is dev-server-only.

Both then commit generated output into the backend, with commit messages that are hand-rolled
submodule pointers:

```
14c7046bc chore: update Manager UI assets (Manager@44a0e684)
2925707d7 chore: update Chat UI assets (chat-ui@71fa395)
```

**562 files** currently sit in `src/main/resources/META-INF/resources/assets/` as committed
build output. Nothing verifies they match the Manager source that produced them.

Neither frontend has an independent version, release, deployment, or consumer.
`eddi-manager` is `"private": true`, version `6.2.0` — identical to `pom.xml`. Both ship
inside the backend jar, in the backend's Docker image, under the backend's git tag. The
standalone `Dockerfile` / `build-service.sh` in the Manager repo are confirmed relics.

The repo split therefore buys nothing that is actually in use, and costs:

| Cost today | Fixed by the monorepo |
|---|---|
| Full-stack E2E runs against `labsai/eddi:latest` pulled from Docker Hub — never the code under test | E2E runs against the image built from the PR's own commit |
| Manager PRs are validated only against MSW mocks; mock drift is silent by construction | Same PR builds the real backend; the API-integration tier runs for free |
| A backend PR that breaks a Manager contract is caught post-publish and blamed on the wrong repo | Caught in the PR that caused it |
| Generated assets committed by a human running a shell script | Built in CI, correct by construction |
| Three HTML production shells orphaned from their source | They become Vite inputs with proper hashing |

## 2. Decisions already made (do not re-litigate)

| Decision | Rationale |
|---|---|
| **Merge both frontends**, not just the Manager | Chat-UI literally cannot build without the backend checked out; it is 64 commits / 2 MiB |
| **Maven stays at the repo root**; Java is not moved to `backend/` | Avoids touching the Dockerfile, all CI path references, and ~40 docs files. Zero benefit to the move. |
| **`git subtree add` without `--squash`** | Preserves history and blame. All three repos are open source, so attribution matters. Costs ~90 MiB of pack. |
| **No npm workspaces** | Two independent `package.json` + `package-lock.json`. Hoisting can break Vite/Tailwind resolution, and a migration should not change two things at once. Revisit later. |
| **Stop committing build output** | This is the entire point. Requires Maven to build the UI (§5). |
| **Keep Node 20** (matches current Manager CI) | Bumping to 22 is a separate, independently reversible change |
| **Archive the old repos, never delete** | They are public; forks and stars exist |

## 4. Phase 0 — Preconditions (do this first, do not skip)

### 4.1 Branch freeze

`EDDI-Manager` has **30+ live branches**. The migration orphans every one of them. Before
starting:

1. Merge or close everything that can be merged or closed.
2. Announce a freeze on `EDDI-Manager` and `EDDI-Chat-UI`.
3. For each branch that must survive, record `<branch-name>` and port it after cutover with:

```bash
git -C ../EDDI-Manager format-patch origin/main..<branch-name> --stdout > /tmp/<branch>.patch
git checkout -b <branch-name> origin/main          # in the EDDI repo
git am --directory=ui/manager /tmp/<branch>.patch
```

`git am --directory=` rewrites every path in the patch under the given prefix. Verify with
`git log --stat -1` that the files landed under `ui/manager/`.

### 4.2 Verify the Trivy blast radius — **do this before merging anything**

`ci.yml` job `trivy-scan` runs `scan-type: fs`, `scan-ref: .`, `severity: CRITICAL,HIGH`,
**`exit-code: 1`**. Once `ui/*/package-lock.json` exist in the repo, npm dependencies become a
**release-blocking gate on the backend**.

Trivy excludes npm dev dependencies by default (`--include-dev-deps` is off), so the exposure
is the ~40 production dependencies of the Manager plus the Chat-UI's. Still: run this on a
scratch checkout with the lockfiles copied in, *before* committing the subtrees:

```bash
trivy fs --severity CRITICAL,HIGH --ignore-unfixed --exit-code 1 .
```

If it fails, resolve the findings (or add justified `.trivyignore` entries) as a **separate
preparatory PR in `EDDI-Manager`**. Do not discover this after the subtree merge.

### 4.3 Baseline capture

Record these so the post-migration result can be diffed:

```bash
git -C . rev-parse HEAD                                   # backend baseline
git -C ../EDDI-Manager rev-parse origin/main              # manager baseline
git -C ../eddi-chat-ui rev-parse origin/main              # chat baseline
ls src/main/resources/META-INF/resources/assets | wc -l   # expect 562
```

Also capture the current bundle entry names from `manage.html` — the migration must produce a
working page with *different* hashes, and you need the old ones to confirm the swap happened.

## 5. Phase 1 — Bring the code in

Work on a branch off `origin/main`. **Each phase below ends in a state that compiles and is
committed separately.**

```bash
git fetch origin main
git checkout -b chore/monorepo-migration origin/main
```

### 5.1 Add the subtrees

```bash
git remote add manager-origin https://github.com/labsai/EDDI-Manager.git
git remote add chat-origin    https://github.com/labsai/EDDI-Chat-UI.git
git fetch manager-origin main
git fetch chat-origin main

git subtree add --prefix=ui/manager manager-origin main
git subtree add --prefix=ui/chat    chat-origin    main

git remote remove manager-origin
git remote remove chat-origin
```

> Use `main` from the **remotes**, not the local checkouts — the local `EDDI-Manager` is on
> `feat/operator-write-scope` and `eddi-chat-ui` on `fix/release-6.2-polish`.

Expect the pack to grow from ~173 MiB to ~260 MiB. That is accepted (§2).

### 5.2 Delete what does not survive the move

```bash
git rm -r ui/manager/.github                 # workflows only run from the repo root
git rm    ui/manager/Dockerfile ui/manager/build-service.sh    # confirmed relics
git rm    ui/manager/deploy-to-local-eddi-repo.sh
git rm    ui/manager/deploy-to-local-eddi-repo.ps1
git rm -r ui/manager/.husky
git rm    ui/chat/deploy-to-local-eddi-repo.ps1
git rm --cached -r ui/manager/.claude        # settings.local.json should never have been tracked
```

Before deleting `ui/manager/.github`, **move the audit script**, which `package.json`
references:

```bash
mkdir -p ui/manager/scripts
git mv ui/manager/.github/scripts/audit-prod.mjs   ui/manager/scripts/audit-prod.mjs
git mv ui/manager/.github/scripts/audit-prod.d.mts ui/manager/scripts/audit-prod.d.mts
```

Then in `ui/manager/package.json`:
- `"audit:prod"` → `node scripts/audit-prod.mjs`
- **remove** `"prepare": "husky"`

> **Accepted loss:** the Manager's pre-commit hook (`lint-staged` + `tsc --noEmit`) goes away.
> CI still runs both. Re-adding a root-level hook is optional follow-up work; the backend
> already has `.githooks/pre-push`, and mixing husky with it during the migration is
> unnecessary risk.

**Commit:** `chore(monorepo): vendor EDDI-Manager and EDDI-Chat-UI as ui/manager and ui/chat`

## 6. Phase 2 — Make the frontends build themselves

This is the fiddliest part. Do it carefully and verify visually before moving on.

### 6.1 Move the three production HTML shells into the Manager

`manage.html`, `welcome.html`, and `workforce.html` currently live in
`src/main/resources/META-INF/resources/`. They are 55-line shells that are identical except for
`<title>`, `<meta name="description">`, and nothing else. Each contains:

- `<script src="/manage/__auth_config__.js"></script>` — **must be preserved verbatim**
- a hashed `<script type="module" crossorigin src="/assets/index-<hash>.js">`
- a hashed `<link rel="stylesheet" crossorigin href="/assets/index-<hash>.css">`
- an inline `.app-loader` `<style>` block and loader markup — **preserve verbatim**
- `<div id="root">`

```bash
git mv src/main/resources/META-INF/resources/manage.html    ui/manager/manage.html
git mv src/main/resources/META-INF/resources/welcome.html   ui/manager/welcome.html
git mv src/main/resources/META-INF/resources/workforce.html ui/manager/workforce.html
```

In each moved file, **replace the two hashed asset tags with the Vite source entry**:

```html
<!-- delete both of these -->
<script type="module" crossorigin src="/assets/index-CeAE4N_O.js"></script>
<link rel="stylesheet" crossorigin href="/assets/index-BCjUK49W.css">

<!-- replace with, immediately before </body> -->
<script type="module" src="/src/main.tsx"></script>
```

Keep `<script src="/manage/__auth_config__.js"></script>` in `<head>` where it is. Vite leaves
absolute non-module script tags alone; it is served by Quarkus at runtime.

### 6.2 Manager `vite.config.ts`

Add a `build` block. Everything else in the file (the ~45 dev-server proxy entries, the
`__APP_VERSION__` define, the `@` alias, `optimizeDeps`, `worker.format`) stays exactly as is.

```ts
import { resolve } from "node:path";

// … existing config …
  build: {
    // dist/ is copied into the Quarkus resources by maven-resources-plugin.
    // index.html is deliberately NOT an input — it is the dev-server entry only.
    // The backend serves its own hand-written index.html redirect shell.
    rollupOptions: {
      input: {
        manage:    resolve(__dirname, "manage.html"),
        welcome:   resolve(__dirname, "welcome.html"),
        workforce: resolve(__dirname, "workforce.html"),
      },
    },
  },
```

**Verify after `npm run build`:**
- `ui/manager/dist/manage.html`, `welcome.html`, `workforce.html` exist
- each references hashed assets under `/assets/`
- each still contains `/manage/__auth_config__.js` and the `.app-loader` styles
- `dist/index.html` does **not** exist
- the three pages share chunks (Rollup does this automatically for multi-page inputs); the
  bundle layout will differ from today's single `index-<hash>.js` — that is expected and fine

### 6.3 Chat `vite.config.ts`

One line. Change:

```ts
outDir: resolve(__dirname, "../EDDI/src/main/resources/META-INF/resources"),
```

to:

```ts
outDir: "dist",
```

Leave `base`, `rollupOptions.input` (`chat.html`), and the output naming
(`scripts/js/chat-ui.[hash].js`, `scripts/js/chat-ui-[name].[hash].js`,
`scripts/css/chat-ui.[hash][extname]`) untouched — those paths are what `chat.html` resolves
against at runtime.

If `emptyOutDir` is set, it is now safe either way; leave it as-is.

### 6.4 Stop tracking generated output

```bash
git rm -r --cached src/main/resources/META-INF/resources/assets
git rm    --cached src/main/resources/META-INF/resources/chat.html
git rm    --cached src/main/resources/META-INF/resources/scripts/js/chat-ui.*.js
git rm    --cached src/main/resources/META-INF/resources/scripts/css/chat-ui.*.css
rm -rf src/main/resources/META-INF/resources/assets
rm -f  src/main/resources/META-INF/resources/chat.html
rm -f  src/main/resources/META-INF/resources/scripts/js/chat-ui.*.js
rm -f  src/main/resources/META-INF/resources/scripts/css/chat-ui.*.css
```

**Do not touch** `scripts/js/landing-redirect.js`, `index.html`, `fonts/`, `img/`,
`eddi-icon.*`, `logo_eddi.png`, `robots.txt`.

Append to `.gitignore`:

```gitignore
# === Generated frontend output (built by frontend-maven-plugin into target/) ===
# The backend serves these from target/classes; they must never be committed again.
ui/*/dist/
ui/*/node/
ui/*/node_modules/
src/main/resources/META-INF/resources/assets/
src/main/resources/META-INF/resources/manage.html
src/main/resources/META-INF/resources/welcome.html
src/main/resources/META-INF/resources/workforce.html
src/main/resources/META-INF/resources/chat.html
src/main/resources/META-INF/resources/scripts/js/chat-ui*.js
src/main/resources/META-INF/resources/scripts/css/chat-ui*.css
```

> The last six entries are protective only — nothing writes there any more. They exist so that
> a stale local copy of the old deploy script cannot silently re-introduce committed assets.

**Commit:** `chore(ui): build the frontends into dist/ instead of the backend source tree`

## 7. Phase 3 — Wire the UI into the Maven build

Without this, `mvnw package` produces a jar with no UI and the Docker image ships a broken
`/manage`. This step is **mandatory**, not optional.

### 7.1 Properties (in the existing `<properties>` block of `pom.xml`)

```xml
<frontend-maven-plugin.version>1.15.1</frontend-maven-plugin.version>
<node.version>v20.19.0</node.version>
<skipUi>false</skipUi>
```

### 7.2 Plugins (append inside the existing root `<build><plugins>`)

```xml
<plugin>
    <groupId>com.github.eirslett</groupId>
    <artifactId>frontend-maven-plugin</artifactId>
    <version>${frontend-maven-plugin.version}</version>
    <configuration>
        <skip>${skipUi}</skip>
        <nodeVersion>${node.version}</nodeVersion>
    </configuration>
    <executions>
        <execution>
            <id>install-node</id>
            <goals><goal>install-node-and-npm</goal></goals>
            <phase>generate-resources</phase>
            <configuration>
                <installDirectory>${project.basedir}/ui</installDirectory>
            </configuration>
        </execution>
        <execution>
            <id>manager-install</id>
            <goals><goal>npm</goal></goals>
            <phase>generate-resources</phase>
            <configuration>
                <arguments>ci</arguments>
                <workingDirectory>${project.basedir}/ui/manager</workingDirectory>
                <installDirectory>${project.basedir}/ui</installDirectory>
            </configuration>
        </execution>
        <execution>
            <id>manager-build</id>
            <goals><goal>npm</goal></goals>
            <phase>generate-resources</phase>
            <configuration>
                <arguments>run build</arguments>
                <workingDirectory>${project.basedir}/ui/manager</workingDirectory>
                <installDirectory>${project.basedir}/ui</installDirectory>
            </configuration>
        </execution>
        <execution>
            <id>chat-install</id>
            <goals><goal>npm</goal></goals>
            <phase>generate-resources</phase>
            <configuration>
                <arguments>ci</arguments>
                <workingDirectory>${project.basedir}/ui/chat</workingDirectory>
                <installDirectory>${project.basedir}/ui</installDirectory>
            </configuration>
        </execution>
        <execution>
            <id>chat-build</id>
            <goals><goal>npm</goal></goals>
            <phase>generate-resources</phase>
            <configuration>
                <arguments>run build</arguments>
                <workingDirectory>${project.basedir}/ui/chat</workingDirectory>
                <installDirectory>${project.basedir}/ui</installDirectory>
            </configuration>
        </execution>
    </executions>
</plugin>

<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-resources-plugin</artifactId>
    <executions>
        <execution>
            <id>copy-ui-bundles</id>
            <goals><goal>copy-resources</goal></goals>
            <!-- process-resources runs after default-resources, so these land
                 on top of the static shells copied from src/main/resources. -->
            <phase>process-resources</phase>
            <configuration>
                <skip>${skipUi}</skip>
                <outputDirectory>${project.build.outputDirectory}/META-INF/resources</outputDirectory>
                <resources>
                    <resource><directory>${project.basedir}/ui/manager/dist</directory></resource>
                    <resource><directory>${project.basedir}/ui/chat/dist</directory></resource>
                </resources>
            </configuration>
        </execution>
    </executions>
</plugin>
```

The two `dist` trees do not collide: the Manager emits `manage/welcome/workforce.html` +
`assets/**`; the Chat emits `chat.html` + `scripts/js|css/chat-ui.*`.

### 7.3 Verification gates for this phase

```bash
./mvnw clean package -DskipTests
```

Then assert, in `target/classes/META-INF/resources/`:
- `manage.html`, `welcome.html`, `workforce.html`, `chat.html` all present
- `assets/` present and non-empty
- `index.html` present and still the redirect shell (not overwritten by the Manager)
- `scripts/js/landing-redirect.js` still present

And check the escape hatch works:

```bash
./mvnw clean package -DskipTests -DskipUi=true    # must succeed, and skip npm entirely
```

> **`.dockerignore` needs no change.** It is a deny-all + allowlist that already permits
> `target/quarkus-app/**`, and the UI now travels inside the Quarkus app jar.

> **Dev-mode note for the team:** `mvnw quarkus:dev` serves the UI from `target/classes`, and
> Quarkus live-reload will not rebuild it. Frontend development continues to use
> `npm run dev` in `ui/manager` on port 3000 with its existing backend proxy — unchanged from
> today.

**Commit:** `build(ui): build and bundle the Manager and Chat UIs via Maven`

## 8. Phase 4 — CI: the actual payoff

Edit `.github/workflows/ci.yml`. Existing jobs referenced below by their current names.

### 8.1 `detect-changes` — add a `ui` output

Add to the `dorny/paths-filter` `filters:` block:

```yaml
            ui:
              - 'ui/**'
```

Add `ui: ${{ steps.result.outputs.ui }}` to the job `outputs:`, and mirror the tag-push
short-circuit that `code` already has (a tag must force `ui=true` too).

Also add `'ui/**'` to the existing `code:` filter list — a UI change must trigger an image
build.

### 8.2 New job: `ui-build-and-test`

Gated on `needs.detect-changes.outputs.ui == 'true'`. Node 20, `cache: npm` with
`cache-dependency-path: ui/*/package-lock.json`. Steps, all with
`working-directory: ui/manager` unless noted:

1. `npm ci`
2. `npm run audit:prod`
3. `npm run lint`
4. `npm run typecheck`
5. `npx vitest run --coverage`
6. `npx playwright install --with-deps chromium`
7. `npm run test:e2e` — the MSW-mocked `ui` tier, ~184 tests, no backend
8. upload `ui/manager/playwright-report/` and `ui/manager/coverage/`
9. then `working-directory: ui/chat`: `npm ci`, `npm run typecheck`, `npm test`

This replaces `EDDI-Manager/.github/workflows/ci-cd.yml` and the `ui-tests` job of its
`e2e.yml` one-for-one.

### 8.3 Restructure image build so E2E tests the artifact that ships

The current `docker` job builds, scans, pushes, signs and attests in one place — so no test
can run against the image before it is published. Split it:

**New job `build-image`** — `needs: [detect-changes, build-and-test]`, runs whenever
`code == 'true'` (**including on pull requests**):

1. Move the existing `Compute Docker tags` step here verbatim; expose `primary-tag`,
   `is-release`, `is-stable`, `minor-tag`, `major-tag` as job outputs.
2. `./mvnw clean package -DskipTests -Plicense-gen -B` — now also builds the UI.
3. `docker build … -t labsai/eddi:ci` (plus the real tags, so the artifact is already tagged).
4. `docker save labsai/eddi:ci | gzip > eddi-ci.tar.gz`
5. Upload `eddi-ci.tar.gz` as an artifact, retention 1 day.

**New job `e2e-fullstack`** — `needs: build-image`, matrix `database: [mongodb, postgres]`,
`fail-fast: false`:

1. Download + `docker load < eddi-ci.tar.gz`
2. Node 20, `npm ci` in `ui/manager`, `npx playwright install --with-deps chromium`
3. `EDDI_IMAGE=labsai/eddi:ci docker compose -f ui/manager/docker-compose.integration<-postgres>.yml up -d --wait`
4. Poll `http://localhost:7070/q/health/live` for `"UP"` (reuse the existing 60×2s loop)
5. `npm run test:e2e:integration`
6. `npm run test:e2e:fullstack`
7. On failure, dump `docker compose logs`; always upload the Playwright report; always
   `docker compose down -v`

**Cost control:** on `pull_request`, run only the `mongodb` leg; run both on push to `main`
and on tags. Implement with a matrix `include` guarded by
`github.event_name == 'push'`, or simply skip the postgres leg via
`if: matrix.database == 'mongodb' || github.event_name != 'pull_request'`.

**Modified job `docker`** (now publish-only) —
`needs: [detect-changes, build-image, build-and-test, integration-test, trivy-scan, codeql, gitleaks, e2e-fullstack]`:

1. Download the artifact and `docker load` — **do not rebuild**. The published image is then
   byte-identical to the one E2E ran against.
2. Retag from `labsai/eddi:ci` to the computed tags (from `needs.build-image.outputs.*`).
3. Keep the existing Trivy image scan, Docker Hub login, push, cosign sign, and SLSA
   attestation steps unchanged.

Keep the existing `if:` guard on this job exactly as-is (push-only, repo check,
`[skip docker]`, tag short-circuit) — and keep the comment at ci.yml:496 explaining why there
is deliberately no `always()`.

### 8.4 `ui/manager/docker-compose.integration*.yml` — parameterize the image

In both files:

```yaml
services:
  eddi:
    image: ${EDDI_IMAGE:-labsai/eddi:latest}
```

Locally, `npm run infra:up:mongo` keeps working unchanged (falls back to `latest`). In CI,
`EDDI_IMAGE=labsai/eddi:ci` points it at the artifact.

### 8.5 Delete the migrated workflows

`ui/manager/.github/` was already removed in §5.2. Confirm nothing else references
`EDDI-Manager/.github/workflows/e2e.yml`.

> Note in passing: that workflow's `backend-tests` job condition included
> `github.event_name == 'schedule'`, but no `schedule:` trigger was ever defined. Dead
> condition; do not carry it over.

### 8.6 `notify-slack`

Add `ui-build-and-test`, `build-image`, and `e2e-fullstack` to its `needs:` list and to the
status-field block, matching the existing `status_icon` pattern.

**Commit:** `ci(monorepo): build once, E2E the built image on both DBs, then publish it`

## 11. Risks and rollback

| Risk | Severity | Mitigation |
|---|---|---|
| Trivy fs scan newly blocks backend releases on a frontend CVE | **High** | §4.2 — verify before merging, not after |
| 30+ orphaned Manager branches | **High** | §4.1 freeze + `git am --directory=` recipe |
| Multi-page Vite build changes bundle layout; a shell renders blank | Medium | §6.2 verification list; test all four pages in a real container before merge |
| `mvn package` now needs Node + network | Medium | `-DskipUi=true` escape hatch; frontend-maven-plugin vendors its own Node |
| PR CI wall-clock grows | Medium | Path filters (§8.1) + PR runs only the mongodb E2E leg (§8.3) |
| ~90 MiB pack growth | Low | Accepted. Cannot be reclaimed without a history rewrite, which `AGENTS.md` §2.4 forbids. |
| Loss of the Manager pre-commit hook | Low | Accepted; CI covers it. Optional follow-up. |

**Rollback:** every phase is a separate commit and nothing is force-pushed, so
`git revert` unwinds any phase independently. The old repos stay archived-but-intact, so a
full retreat means un-archiving them and reverting the monorepo merge commit. Do not delete
the source repos until the monorepo has been green on `main` for at least one release cycle.
