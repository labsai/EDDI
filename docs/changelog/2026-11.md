## 🐛 fix(loadtest): the load-test stack admits its plaintext mock LLM to the vault transport check (2026-11-03)

**Repo:** EDDI (`fix/loadtest-vault-plaintext`)

### What changed and why

The `Load Test DB Ops` workflow (check "DB ops per turn") went red on `main` from the 2026-11-03 nightly: `ci-gate-10vu-10t: 0 ok ... errors: app_error=100`. Every turn failed in the EDDI container with `VaultHostAllowlist$HostNotAllowedException: LLM provider 'openai' sends ${vault:...apiKey} to wiremock:8080 over unencrypted http`. #1175 added a separate plaintext-transport check, so a vault secret is no longer sent over `http://` to a non-loopback host unless `eddi.vault.allow-plaintext-remote-hosts=true`, even when the host is listed in `allowedHosts`. The load test points its OpenAI-compatible model at the plain-http mock `http://wiremock:8080/v1` and stores the API key as a vault secret, so every LLM call was refused before it left EDDI. The 2026-11-02 nightly ran before #1175 merged.

Both load-test compose files ([`docker-compose.loadtest.yml`](../../scripts/loadtest/docker-compose.loadtest.yml), [`docker-compose.cluster.yml`](../../scripts/loadtest/docker-compose.cluster.yml)) now set `EDDI_VAULT_ALLOW_PLAINTEXT_REMOTE_HOSTS=true`, the deployment-level opt-in the check documents. The setting still admits plaintext only to a host on the secret's own `allowedHosts`.

### Design decisions

- The opt-in goes on the throw-away benchmark stack, not into the driver: switching the mock to https would measure TLS rather than turns, and the check is correct in production.

## ✨ feat(llm): cascade judge grades against the request, MCP on the capped client — langchain4j 1.23 follow-ups (2026-11-03)

**Repo:** EDDI (`feat/langchain4j-1-23-adaptations`)

Dependabot moved EDDI to langchain4j 1.23.0 / 1.23.0-beta33 (#1214) with no code change, and CI passed. EDDI
implements no `McpTransport` and uses none of the Jackson 2 MCP methods the release removed (#6824), so nothing
broke. This change adopts what the release made possible, and one lesson from its new Confidence Cascade pattern
(langchain4j#6765).

### What changed and why

- **The `judge_model` cascade judge sees the request.** It was sent only the answer and asked to rate it, so a
  fluent answer to the wrong question scored as well as a right one. langchain4j's cascade grades "does the answer
  fully and correctly address the request?". `ConfidenceEvaluator` now sends the text of the latest user message
  the step's model saw (8,000 characters at most: a single long text keeps its end, where a templated prompt puts the question; with attachments the typed question is kept whole and the head of the attached text fills the rest) together with the
  answer, and asks for the probability that the answer is acceptable for the request. With no user text (an
  image-only message) the judge rates the answer on its own, as before. `CascadingModelExecutor` passes the request
  from both the legacy and the agent-mode step.
- **`modelCascade.acceptanceCriterion`** (optional string): one sentence an acceptable answer must also meet, added
  to the judge's instructions. It is langchain4j's `yesWhen` for the same pattern. Only the judge reads it, so
  `CascadeConfigValidator` warns when it is set without a `judgeModel`. The Manager's cascade editor shows it under
  the judge model editor (all 11 locales).
- **Untrusted text is data, not instructions.** The request and the answer go to the judge as JSON string values
  (Jackson-encoded, so neither can close its field), and the system message tells it to ignore instructions and
  self-reported scores inside them. The author's criterion is trusted config and sits in the system message. The
  docs now say so plainly: this keeps graded text from posing as instructions, but the grade can still be swayed,
  so the cascade is a cost/quality trade-off and not a security boundary.
- **MCP runs on `BoundedJdkHttpClient`.** langchain4j 1.23 made the `StreamableHttpMcpTransport` backend pluggable
  (#6726). The transport now uses EDDI's capped JDK client: a response past `eddi.llm.max-response-bytes` (32 MB)
  fails instead of being read into the heap whole, and the per-request URL re-check against DNS rebinding moved from
  the header hook into the client's request guard, which runs before every send. `followRedirects(false)` stays
  pinned, and `streamingBackpressure(true)` keeps what the transport's own backend set. The cap's error message no
  longer says "LLM provider", since MCP shares it. This puts MCP on the same client as the LLM builders, not on
  `OutboundHttp`: the HTTP client consolidation's Phase 3 (a langchain4j `HttpClient` adapter over `OutboundHttp`) is
  not built yet, and its Vert.x engine is Phase 4. When Phase 3 lands, MCP moves with the builders through this same
  `httpClientBuilder` hook — the hook the October security review noted was missing.
- **Version stamps.** `docs/rag.md`, `InputTypedEmbeddingModelTest` and `VertexGeminiLanguageModelBuilder` named
  1.22. Checked against the 1.23 jars: still only Gemini (and Cohere) declare `INPUT_TYPE`, and the Vertex streaming
  builder still has no `seed`.

### Tests

`ConfidenceEvaluatorJudgeRequestTest` (6): the request and criterion reach the judge, hostile text stays inside its
JSON field, no request means no `request` field, request extraction and its tail truncation.
`CascadingModelExecutorToolReplayTest.judgeSeesRequestAndCriterion` covers the executor wiring.
`McpTransportResponseCapTest` serves a 40 MB handshake answer from a loopback server; it and
`McpTransportRevalidationTest` both fail when the `.httpClientBuilder(...)` line is removed (mutation-checked). In the
Manager, two `task-cascade-section` tests cover editing and clearing the field and hiding it for other strategies.

### Considered, not done

- **Skip the judge on a step that is accepted anyway** (the last step, a null threshold). langchain4j never grades
  its last tier. Here the last step's confidence feeds `audit:confidence`, `cascadeConfidence`, the confidence
  metric and `returnBestAcrossSteps`, so skipping the call would change what those report. That needs its own
  decision.
- **A `decision_model` strategy** on langchain4j's `DecisionModel` (OpenAI Decisions API, Ollama): it returns
  probabilities instead of a number the model writes as text. The API is `@Experimental`, and its token usage goes to
  a `DecisionModelListener`, outside EDDI's cost accounting. Revisit when it stabilises.
- **The agentic layer** (`ConfidenceCascadePlanner`, decision agents, activation conditions) and AiServices-only
  features (tool search strategy, `AiServiceInvocationSummaryEvent`): EDDI's orchestration is config-driven and does
  not use `AiServices`.

## Update check is on by default, with a server-side opt-out and a notification (2026-11-03)

**Repo:** EDDI — branch `feat/update-check-default-on`.

**What changed**

- The "is a newer EDDI out?" check used to be browser-only and opt-in (a `localStorage` flag). It is now **on by default** and EDDI itself runs it: `UpdateCheckService` (`engine/updatecheck/`) asks `api.github.com` once a day (first run a minute after boot), compares with `quarkus.application.version`, and raises a notification when the release is newer. The announced version is stored, so a dismissed notice is not raised again by the next day's check or a restart.
- **Two opt-outs.** `eddi.update-check.enabled=false` (env `EDDI_UPDATE_CHECK_ENABLED`, wired through `docker-compose.yml`, `.env.example` and the Helm value `eddi.updateCheck.enabled`, chart 2.14.0) stops it entirely — it is tested before the database is read, so the first check after the first boot is suppressed too — and wins over the Manager's switch, which shows as locked. The Manager's Updates page has the other switch (administrators), stored through the new `ISystemSettingStore` (`system_settings`, Mongo and Postgres), so it holds across restarts, browsers and nodes. `GET/PUT /administration/update-check`.
- **Notification reuses the existing inbox** (`WorkspaceNotifications`): new type `UPDATE_AVAILABLE`, addressed to the shared recipient `system:admins`, which administrators read in addition to their own inbox (with authorization off, everyone is an administrator). The bell no longer requires workspaces; it shows while workspaces or the update check are on.
- White-labelled deployments that did not set `eddi.branding.show-update-check` neither check nor notify.
- Manager: the banner/card read the server's switch instead of `localStorage`; the old key is ignored. `api.github.com` is still the only off-origin host the Manager contacts.

**Design decisions**

- State lives on the backend because only the backend can honour the env var before anyone reaches the UI.
- Platform Operator checked (§4.6.6): no prompt or allow-list change. The operator cannot write this switch (`PUT` stays off its allow-list on purpose) and the behaviour is documented in `docs/docker.md`, which it can read.
- 11 locales updated for the reworded `updates.autoCheck*` strings and the two new ones.

**Not done:** the browser still makes its own per-load request to GitHub for the card's release notes while the switch is on (a second, cheap call; the server's notification is the primary signal).

## ✨ feat(pricing): correct cost accounting — usage normalization, one price resolution, deployment price catalog, unpriced visibility, strict mode, spend SPI (2026-11-02)

**Repo:** EDDI (`feat/cost-accounting`)

### What changed and why

EDDI's dollar figures — `audit:cost`, every cost ceiling, the tenant's monthly budget, the audit ledger, `/v1`
usage — were only as good as the token counts and prices behind them, and both were off. Anthropic and Bedrock
report prompt-cache reads and writes outside `input_tokens`, so cached prompts cost $0; Gemini reports thinking
outside its output count; the only per-call sum point (`ToolContextBudget.sumTokens`) threw away every provider
field beyond the three base counts; a rolling summary on a cheap model was charged at the task's rates; group
window and stance summaries never reached the tenant budget; and a model with no price on its config was simply
free, with nothing telling anyone. See [Model Pricing](../model-pricing.md).

- **Usage normalization** — the decorators around every chat model
  ([`UsageMetering`](../../src/main/java/ai/labs/eddi/modules/llm/pricing/UsageMetering.java),
  [`UsageNormalizer`](../../src/main/java/ai/labs/eddi/modules/llm/pricing/UsageNormalizer.java)) replace each
  response's usage with a [`MeteredTokenUsage`](../../src/main/java/ai/labs/eddi/modules/llm/pricing/MeteredTokenUsage.java):
  input = all prompt tokens, cache reads/writes kept as subsets, output includes thinking, per-call long-context
  buckets, the pricing model, and the call's price at the catalog entry it matched when it returned. Sums and
  usage-map merges keep every field. `audit:token_usage` gains `cacheReadTokens`/`cacheWriteTokens`.
- **One price resolution** — [`ModelPriceResolver`](../../src/main/java/ai/labs/eddi/modules/llm/pricing/ModelPriceResolver.java):
  config prices, then the task's / cascade step's new optional `pricing` object (cache and long-context prices),
  then the catalog, then fallbacks (cache at the input price, tier at the base price; no price at all is unpriced,
  an explicit `0` is priced). `ModelPrices` and `TokenPricing` delegate to it, so every existing call site gains it.
- **Deployment price catalog** — one CAS-revisioned document (MongoDB `modelpricecatalog`, PostgreSQL
  `model_price_catalog`), `/administration/model-prices` (admin writes; admin/editor read, resolve and unpriced
  sightings), published as a static snapshot every pricing site reads, refreshed every 30 s. Bundled, never-active
  **reference prices** (Anthropic, OpenAI, Gemini list prices as of 2026-11-02, each with its source) for one-click
  adoption in the Manager.
- **Visibility** — `[unpriced-model]` deployment warnings, `audit:pricing` per step (→ `llmDetail.pricing`),
  `eddi.llm.cost.usd`, `eddi.llm.calls.unpriced`, `eddi.llm.pricing.refused`, cache/reasoning token types on
  `eddi.llm.tokens`, catalog gauges, and node-local unpriced sightings.
- **Strict mode** — `unpricedPolicy` `ALLOW` (default) / `REFUSE_WHEN_BUDGETED` / `REFUSE`, never looser than the
  `eddi.llm.pricing.unpriced-policy-floor` property; refused before the call through each caller's existing
  failure path (task fallback with reason `unpriced_model`, failed cascade step, undecided guardrail, truncation
  for group summaries, Dream stops).
- **Spend attribution SPI** — [`ISpendSink`](../../src/main/java/ai/labs/eddi/engine/pricing/ISpendSink.java) /
  [`SpendEvent`](../../src/main/java/ai/labs/eddi/engine/pricing/SpendEvent.java), fired synchronously after each
  accepted tenant charge by `TurnCostMeter` (exactly once per step), `DreamService` and the new
  [`SystemSpendMeter`](../../src/main/java/ai/labs/eddi/engine/pricing/SystemSpendMeter.java), which also charges
  group window and stance summaries to the tenant and admits them against the budget first.
- **Call sites** — summaries and the tool-response summarizer priced at their own model; guardrail, streaming and
  summary usage maps are the metered ones; Dream falls back to the catalog.
- **Manager** — a *Model Prices* page (admin) and a catalog hint plus cache/long-context fields in the LLM task's
  pricing section.

### Design decisions

- No active shipped prices: silently active, code-shipped prices go stale invisibly and an EDDI upgrade would change
  what a tenant is charged. An empty catalog prices exactly as before.
- Static snapshot holder (`ModelPriceCatalogs`) instead of injecting the catalog into the tool loop, cascade executor
  and resumer — every pricing method also has a snapshot-taking overload for tests.
- A provider response metadata subclass (`OpenAiChatResponseMetadata`, …) narrows `tokenUsage()` to its own type, so
  the decorator replaces it with a plain `ChatResponseMetadata` (id, model, finish reason). EDDI reads none of the
  provider-only extras.
- Strict mode never fails a deployment; the warning says the calls will be refused, and the per-call check enforces
  it. Failing deploy would race the catalog load at boot.

### Not done / next

- The MCP tool `read_model_prices` and the Platform Operator grants are deferred to the combined follow-up
  (`planning/operator-followups/cost-accounting.md`).
- Strict mode does not refuse the rolling conversation summary, the tool-response summarizer or the cascade's
  confidence judge yet (they are priced and counted).
- Embeddings are not priced (next gap; the catalog could take `kind: embedding`).
- Summarization retries that failed after consuming tokens stay unpriced.

## ✨ feat(groups): `convergence.judge: "SERVICE"` makes one direct model call (2026-11-02)

**Repo:** EDDI (`feat/group-service-judge`)

### What changed and why

`judge: "SERVICE"` on a phase's `convergence` block used to be accepted, documented and then quietly run as the
moderator agent: the group config carried no model coordinates or credentials for a direct call. A phase can
now name the model in a new `convergence.service` block, and the judge asks it directly — one short call
instead of a full moderator-agent turn, and it works in a group that has no moderator at all.

```json
"convergence": {
  "enabled": true, "minRepeats": 2, "threshold": 0.8, "judge": "SERVICE",
  "service": { "llmProvider": "openai", "llmModel": "gpt-4o-mini",
               "parameters": { "apiKey": "${vault:openai-key}" },
               "inputPricePer1M": 0.15, "outputPricePer1M": 0.60, "timeoutMs": 20000 }
}
```

- **Config** — [`ServiceJudgeConfig`](../../src/main/java/ai/labs/eddi/configs/groups/model/ServiceJudgeConfig.java),
  a sixth component on `ConvergenceConfig` (the five-argument constructor is kept as an overload). Normalized like
  `ContextWindowConfig`/`StanceSummaryConfig`: blank identifiers absent, negative prices unpriced, timeout default
  20 s and ceiling 60 s. The stale Javadoc that said the config "does not carry" provider coordinates is fixed.
- **Engine** — [`ServiceConvergenceJudge`](../../src/main/java/ai/labs/eddi/engine/internal/groups/ServiceConvergenceJudge.java)
  calls `SummarizationService.summarizeWithUsage` with a fixed system instruction and the existing judge prompt
  as the user message (data, never template source), parses it with the same `ConvergenceDetector` parsers, prices
  it through the one-method seam [`JudgeCallPricing`](../../src/main/java/ai/labs/eddi/engine/internal/groups/JudgeCallPricing.java)
  (today `TokenPricing.cost`), books it as `system:judge:<phase>:<repeat>` and announces it with `cost_updated`.
  `PhaseExecutionEngine.runJudge` asks it **before** the no-moderator early return; it is wired by a setter from
  `GroupConversationService`, so no construction site changed. A failure, timeout or unreadable reply is "not
  converged"; the provider's error text never reaches the transcript.
- **Save time** — [`ServiceJudgeValidation`](../../src/main/java/ai/labs/eddi/configs/groups/validation/ServiceJudgeValidation.java),
  one line in `AgentGroupStore.memberAndLimitProblems`: a plaintext credential in `service.parameters`, a
  `${connection:...}` reference (the model registry refuses those) and a half-named provider/model are 400s.
  `SERVICE` without a model and an unknown `judge` value are warnings only, so stored configs keep saving.
- **Vault grants** — [`ServiceJudgeVaultGrants`](../../src/main/java/ai/labs/eddi/configs/groups/validation/ServiceJudgeVaultGrants.java):
  a `${vault:...}` reference in `service.parameters` is refused at group save unless the secret exists and its
  grant contains `"*"` (a group has no agent identity for a narrower grant), and re-checked before the judge
  resolves its parameters; a narrowed grant fails that judge with `outcome=error`, not the discussion.
- **Metrics** — timer `eddi.group.convergence.judge.duration{judge=service, mode, outcome}`.
- **Manager** — the phase editor shows provider, model, API key reference, prices and timeout when Judge is
  Service (`service-judge-fields.tsx`); `normalizeConvergence` carries the block through. New i18n namespace
  `groupServiceJudge` in all 11 locales; the "not yet wired" note is gone.
- **Docs** — new page [Group Convergence Judge: SERVICE](../group-service-judge.md); the convergence paragraph in
  [Group Conversations](../group-conversations.md) now links to it.

### Behaviour of existing configs

Unchanged. `judge: SERVICE` without a `service` model still runs the moderator agent (now counted as
`outcome=fallback_moderator`), and no stored config can fail the new save-time checks because they only read the
new block.

### What's next

- `JudgeCallPricing` is the seam the cost-accounting work re-points at its central price resolver.
- MCP/Operator: no new tool; the Platform Operator follow-up is in
  [`planning/operator-followups/group-service-judge.md`](../../planning/operator-followups/group-service-judge.md).

## ✨ feat(hitl): edit-on-approve everywhere and the HITL decision audit contract (2026-11-02)

**Repo:** EDDI (`feat/hitl-edit-on-approve`)

### What changed and why

An approver can now approve **with an edit**, and every HITL decision is recorded in the audit ledger in one typed
shape that analytics can rely on.

- **Config** — `hitlConfig.review` on agents ([`HitlReviewConfig`](../../src/main/java/ai/labs/eddi/configs/hitl/model/HitlReviewConfig.java))
  and groups ([`GroupHitlReviewConfig`](../../src/main/java/ai/labs/eddi/configs/hitl/model/GroupHitlReviewConfig.java)),
  and `toolApprovals.rules[].approvalCategory`. All optional; a config without them behaves exactly as before.
  Validated at save time by [`HitlReviewConfigValidation`](../../src/main/java/ai/labs/eddi/configs/hitl/HitlReviewConfigValidation.java).
- **Audit contract** — every `hitl.approval` entry is now written by
  [`HitlApprovalAudit`](../../src/main/java/ai/labs/eddi/engine/hitl/audit/HitlApprovalAudit.java) with `schema: 2`:
  the legacy fields stay, and the decision gains `decisionId`, `pauseId`, `pausedAt`, `decidedAt`, `latencyMs`,
  `channel` (`REST`, `MANAGER` from the `X-EDDI-Client: manager` header, `MCP`, `SLACK`, `TIMEOUT`, `SYSTEM`),
  `automationReason`, `approvalCategory`/`approvalCategorySource`, `reasonCode` and a `units[]` list — one unit per
  answer, tool call, phase or task, each with its `decisionOutcome` (`APPROVED`, `APPROVED_EDITED`, `REJECTED`,
  `AUTO_APPROVED`, `AUTO_REJECTED`, `ABORTED`) and edit metrics. `HitlApprovalAudit.parse` reads schema 1 and 2 into
  [`HitlDecisionUnit`](../../src/main/java/ai/labs/eddi/engine/hitl/audit/HitlDecisionUnit.java)s, and the CDI event
  [`HitlDecisionRecorded`](../../src/main/java/ai/labs/eddi/engine/hitl/audit/HitlDecisionRecorded.java) is fired
  (async) after each write. The four writers were uneven before: a regular cancel had no agent or user, a group
  cancel had no `decidedBy`, a group decision had no phase — all fixed.
- **Reason codes** — `reasonCode` on a decision and on `toolDecisions[]`, checked before the pause is consumed by
  [`HitlDecisionValidator`](../../src/main/java/ai/labs/eddi/engine/hitl/review/HitlDecisionValidator.java)
  against `review.reasonCodes` or the built-in vocabulary. `approval-status` lists the vocabulary and the category in
  `pauseDetails`.
- **Approve a RULE pause with an edited answer** — `editedAnswer` on the resume body, for agents with
  `review.allowAnswerEdits`. The draft is kept with the pause (also without `onRejection: REVISE`), checked before the
  CAS (not blank, `maxEditChars`, no control characters, a JSON object for a `convertToObject` task), and applied by
  the LLM task in place ([`LlmAnswerEditor`](../../src/main/java/ai/labs/eddi/modules/llm/impl/LlmAnswerEditor.java)):
  the answer's own output item and data keys, nothing after it, no `postResponse`, no task re-run. Under
  `screenEdits: OUTPUT_GUARDRAILS` the task's output guardrails screen the edit (`reprompt` acts as `block`); a blocked
  edit or a changed configuration pauses the turn again on the unchanged draft, records `hitl.edit.refused` and shows
  `lastEditRefused` on the next pause. `approval-status` serves the redacted draft as `pauseDetails.editableAnswer`.
- **Group edits** — `taskDecisions` on the group approve body (`{verdict, note, editedResult, reasonCode}` per task,
  exclusive with `taskApprovals`) and `decision.editedAnswer` on a PHASE pause after a SYNTHESIS phase, for groups with
  `review.allowResultEdits` ([`GroupReviewEditor`](../../src/main/java/ai/labs/eddi/engine/internal/groups/GroupReviewEditor.java)).
  An edited result replaces `TaskItem.result` (dependents and the summary read it) and is noted in
  `SharedTaskList.reviewerEdits`; a synthesis edit is appended as an unsigned `SYNTHESIS` entry (speaker
  `hitl:<decidedBy>`, `errorReason: "reviewer-edit"`) — signed entries are never rewritten, and the signing guard skips
  reviewer entries.
- **Slack** — approval cards of regular conversations gain "✏️ Edit & approve" and "Reject with reason…"
  ([`SlackHitlEditModal`](../../src/main/java/ai/labs/eddi/integrations/slack/SlackHitlEditModal.java)), opened as
  modals with `views.open`. A TOOL_CALL card offers Edit for a single call whose redacted arguments fit Slack's 3000
  characters; edited arguments are merged server-side against the raw ones
  ([`SlackRedactedArgumentsMerge`](../../src/main/java/ai/labs/eddi/integrations/slack/SlackRedactedArgumentsMerge.java)),
  so redacted secrets never travel through Slack and cannot be edited there. A RULE card offers Edit only with the new
  integration setting `platformConfig.hitlShareRuleDrafts=true`, for agents that allow edits and drafts without
  secrets. `view_submission` re-runs every check (approver, workspace, card, pause) and is validated synchronously
  through `IConversationService.validateHitlDecision`, so errors show in the modal. Group cards keep Approve/Reject.
  `SlackHitlSupport.buildApprovalBlocks` keeps its signature; the new overload takes the card's edit controls and keeps
  the `actions` block last.
- **Manager** — the approval banner offers "Edit the answer before approving" on a RULE pause whose
  `pauseDetails.editableAnswer` is present (textarea with the draft, a counter against `maxChars`, JSON validation for
  a JSON answer, the original one click away), a reason-code select for rejections and edits, and a notice when the
  engine refused the last edit; the group transcript marks a reviewer's SYNTHESIS entry. Every Manager decision sends
  `X-EDDI-Client: manager`. New keys under `hitlReview.*` in all 11 locales.
- **Docs** — new page [HITL Review & Audit](../hitl-review-and-audit.md) (config, edit semantics per surface, Slack
  modals, the full audit contract with the schema-1 mapping, the reason-code vocabulary, a worked GitHub-reply
  example), linked from `hitl.md`, `group-conversations.md`, `mcp-server.md` and `SUMMARY.md`. The operator and MCP
  follow-up is in [`planning/operator-followups/hitl-edit-on-approve.md`](../../planning/operator-followups/hitl-edit-on-approve.md).

### Review follow-ups (2026-11-04)

- **Slack**: a tool-call card offers Edit only when the shown arguments are a JSON object (or blank) — malformed model
  arguments opened a modal every submission of which the server-side merge refused (`SlackHitlEditModal.forCard`).
- **Manager**: an amendment identical to the shown arguments is no amendment, so a selected reason code is not sent
  with what the server treats as a plain approval (it answered that with a `400`) (`approval-banner.tsx`).
- **Group cancel audit**: a cancel that lands while a running leg commits its pause is audited by that leg on its own
  thread; the token now records the caller that signalled it (`DiscussionControlToken.getSignalledBy`), so the entry
  names the canceller instead of the owner or `system:unattributed`.
- **Docs and dashboard**: [`hitl-review-and-audit.md`](../hitl-review-and-audit.md) separates request validation
  (`400`, still paused) from screening (a refused edit re-pauses), says the resume reply needs a reply flag and
  owner-or-admin access, and what an edit reaches for an `addToOutput: false` task; "Size of approver edits" says
  "no samples yet" when empty.

### Contract for the features built on this branch

- **Approval analytics** reads `hitl.approval` entries only through `HitlApprovalAudit.parse(AuditEntry)` →
  `List<HitlDecisionUnit>`, and observes `HitlDecisionRecorded(String auditEntryId, List<HitlDecisionUnit> units)`
  with `@ObservesAsync`. Values of `DecisionOutcome`, `HitlChannel`, `UnitKind` and `EditSummary.Kind` are only ever
  added. HUMAN_TURN resolutions have no units and no outcome.
- **Approval card context** extends the Slack card through `SlackHitlSupport.buildApprovalBlocks`, whose signatures

## ✨ feat(groups): native cross-team handoff (2026-11-02)

**Repo:** EDDI (`feat/team-handoff`)

### What changed and why

A standing team could only receive work from a human typing into its backlog. Cross-team handoff lets another team, or a standalone agent, file a task into a team's workspace, under **two-sided consent enforced by code**: the source lists the target (`teamHandoff.targets` on an LLM task, `handoffConfig.targets` on a group) and the target lists the source (`handoffConfig.accept.from`, `agent:<id>` or `group:<id>`, exact ids). Nothing else changes by default: every new field is absent-means-off, and old stored or imported configs and workspaces behave exactly as before.

- **One pipeline.** `TeamHandoffService.file` is the only code that writes to another team's workspace. It checks consent against the target's *current* config, refuses self-handoff, cycles and the hop limit (`eddi.groups.handoff.max-hops`, default 3), cleans the text, reserves a per-run and two per-UTC-day slots (the `toolQuotas` store, so atomic across pods), asks any `HandoffAdmission` bean, then writes through the workspace compare-and-set, re-validating duplicates, decline tombstones and capacity on every retry. A refused attempt gives its slots back.
- **Two entry points.** A `handoff_to_team` tool whose `team` argument is an enum of the aliases the source declared (new approval source `team`), and deterministic `handoffConfig.onDecision` rules that file a task when a discussion completes with a matching `VOTE`/`VERDICT`/`AGREEMENT`/`AWARD`, with an idempotent dedupe key per discussion, round and rule.
- **AUTO vs REVIEW.** REVIEW (the default) puts the item in an intake inbox that is in no task list, so a cadence can never pull it; a human with EDIT accepts (optionally edited) or declines it. Both write an audit entry in the shared approval vocabulary (`team_handoff_intake`, `APPROVED | APPROVED_EDITED | REJECTED`, `reasonCode`).
- **Lineage and provenance.** The origin of a handed-off task lives in a side map keyed by task id, and the cadence stamps the lineage of the tasks it pulled onto the discussion, so A to B to A is caught across discussions. A handed-off task is marked in the cadence question as a request to evaluate, not instructions.
- **New REST** under `/groupstore/groups/{groupId}/workspace`: `GET /handoffs`, `POST /handoffs/{id}/accept`, `POST /handoffs/{id}/decline`, and `DELETE /backlog/{taskId}` (the 200-task backlog had no way to shrink; handoff makes the ceiling reachable). Manager: an Intake section and an origin badge on the workspace page, a handoff section in the group advanced editor.
- `team` is added to the known HITL tool sources and to the tool-cache side-effecting sources (a cached result must never stand in for a write). SSE gets a `team_handoff` event; metrics `eddi_team_handoff_*`.

Not built here: new MCP tools for the intake (the service methods are public and web-free for thin wrappers), and the Platform Operator update, both listed in `planning/operator-followups/team-handoff.md`.

**Rolling upgrade caveat:** an older pod that re-saves a workspace drops the unknown `handoffs` field, losing pending inbox items and origins (same as `reworkCounts`); the audit entries hold the subject and source for recovery.

## ✨ feat(llm): `toolQuotas` — per-subject, per-window caps on tool calls (2026-11-02)

**Repo:** EDDI (`feat/tool-quotas`)

### What changed and why

An agent designer can now cap how often one **subject** — normally the end user — may make a tool run within a
time window, counted **across conversations and across nodes**: "at most 100 content improvements per user per
day". Until now EDDI had a per-tool-per-minute rate limit per conversation (`toolRateLimits`), a per-conversation
budget that a new conversation resets (`maxBudgetPerConversation`) and per-tenant quotas — none of them is per
user per day.

```json
"toolQuotas": {
  "subject": "{context.personId}",
  "tools": {
    "updateAction":        { "limit": 100, "window": "P1D", "pool": "improvements" },
    "updateSession":       { "limit": 100, "window": "P1D", "pool": "improvements" },
    "generateActionImage": { "limit": 30,  "window": "P1D" }
  }
}
```

- **Config** — `LlmConfiguration.Task.toolQuotas` ([`ToolQuotaConfig`](../../src/main/java/ai/labs/eddi/modules/llm/model/ToolQuotaConfig.java)).
  Keys are tool names with the same matching as `toolRateLimits` (dispatch name wins over slug) and work for every
  tool source, HTTP-call tools included. Tools of one `pool` share one counter. Validated at save time
  ([`ToolQuotaConfigValidator`](../../src/main/java/ai/labs/eddi/modules/llm/tools/quota/ToolQuotaConfigValidator.java),
  wired into `LlmStore` like the `toolApprovals` check, so it is a 400): `limit` a positive integer, `window` an
  ISO-8601 duration from `PT1M` to `P31D`, every rule of a pool states the same limit and window. Windows are fixed
  and aligned to the UTC epoch (`P1D` resets at 00:00 UTC).
- **Subject** — an optional template rendered with the turn's template data; default is the conversation's user id.
  Managed conversations use composite user ids (`<user>-<company>-<program>`), so the default counts per program and
  the template is how a deployment counts per person. A blank render falls back to the user id, a caller with no user
  id is capped per conversation, a subject over 256 characters becomes a prefix plus a digest, and the subject is only
  ever logged as a short digest.
- **Counts real executions only.** The reservation is made in one place, `ToolExecutionService.executeToolWrapped`,
  after the rate limit and the cache and immediately before the tool runs (`ToolQuotaGate.reserve`). Cache hits,
  rate-limited calls, calls refused by the conversation or tenant budget, rejected approvals and calls that never ran
  are never counted. A failed call gives its reservation back (`ToolQuotaGate.settle`): an exception, a tool-reported
  error, an HTTP non-2xx or transport failure — judged by the same `ToolOutcomeClassifier` the repeat guard uses. A
  **timed-out** call keeps its count, because the abandoned worker cannot be stopped and may still finish the side
  effect.
- **Atomic, no overshoot, multi-node.** A new counter store, `IToolQuotaStore`, with a MongoDB implementation
  (`findOneAndUpdate` with a `count < limit` filter and upsert; the duplicate-key race on the window's first insert is
  retried as a conditional update; TTL index on `expiresAt`) and a PostgreSQL one (`INSERT … ON CONFLICT DO UPDATE …
  WHERE used < ? RETURNING used`; an hourly sweep removes expired rows). Selected in `DataStoreProducers` like the other
  stores. With three calls left, a batch of five parallel calls runs exactly three.
- **Refusal** is a tool result the model sees, a final `NOT_EXECUTED` envelope with the limit and the reset time
  ("Not run: the daily limit for this tool (100) is reached; it resets at 2026-11-03T00:00:00Z …"), not a thrown error;
  the turn carries on and the model is not invited to retry.
- **Human approval.** Approved calls run on the resume path through the same `ToolLoopRunner.executeToolCall` →
  `executeToolWrapped` pipeline as live calls, so the quota is applied (and counted) at execution time there too. A
  gated call proposed while its quota is already exhausted is refused immediately by a read-only pre-check
  (`ToolLoopRunner.refuseExhaustedGatedCalls`, before the pause is built), so a human is never asked to approve what
  will then be refused; pausing counts nothing.
- **Fails closed.** If the store cannot answer, a stored rule cannot be applied or the subject template fails to
  render, the call is not run and the model is told the limit could not be checked. One WARN a minute with agent,
  conversation and a digest of the user id; every failure is counted.
- **Metrics** — `eddi.tool.quota.decisions{tool, outcome}` (`allowed`, `refused`, `precheck_refused`, `unavailable`,
  `released`) and `eddi.tool.quota.store.failures{operation}`; documented in `docs/metrics.md` and charted on the Full
  Metrics Reference dashboard.
- **GDPR** — counters are keyed by a user identifier, so
  [`ToolQuotaGdprParticipant`](../../src/main/java/ai/labs/eddi/modules/llm/tools/quota/ToolQuotaGdprParticipant.java)
  joins the erasure cascade (delete by subject) and the export (the user's counters). If a deployment's subject
  template derives an identifier other than the conversation's user id, erasure deletes the counters whose subject
  equals the erased user id; counters hold counts only and expire an hour after their window ends.

### Design decisions

- The reservation sits inside `executeToolWrapped`, not in `ToolLoopRunner` around the supplier: only there is it after
  the cache check, and a refusal returned from inside the supplier would have been cached and charged as a result.
- A rule keyed by a slug is one counter for all of that tool's operations (unlike the per-dispatch-name rate-limit
  bucket), because "30 web searches a day" is naturally per tool; `pool` is the explicit way to share across tools.
- Pre-check only refuses an *already exhausted* quota; it does not reserve slots for pending approvals.
- A call with no quota rule takes exactly the old 10-argument `executeToolWrapped` path.

### What's next / not done

- The Manager has no form for `toolQuotas` yet; its LLM task editor spreads the task object on save, so a configured `toolQuotas` is preserved.

[`ToolQuotaService.java`](../../src/main/java/ai/labs/eddi/modules/llm/tools/quota/ToolQuotaService.java),

## Group HITL transitions are bound to their pause with a multi-field CAS (2026-11-01)

Repo: EDDI, branch `fix/groups-pause-cas` (stacked on #1188).

**Problem:** the group approve, reject, cancel and human-turn timeout-skip writes compared only `state` in their compare-and-set. A resume followed by a re-pause between the read and the write (ABA) left the state `AWAITING_APPROVAL` / `AWAITING_HUMAN_INPUT` again, so a stale decision could act on a newer pause it never saw. The in-memory pause-id checks narrowed the window but could not close it.

**Change:**
- `IResourceStorage.storeIfFieldsEqual(resource, Map)` — an atomic conjunctive conditional write (a `null` expected value means "absent"), implemented in `MongoResourceStorage` (one `replaceOne` filter) and `PostgresResourceStorage` (one `UPDATE ... WHERE a = ? AND b = ?`), with the same 404/409 zero-match distinction as the single-field CAS.
- `GroupConversation.pauseId` is persisted next to `pausedAt` and kept in lockstep by `setPausedAt`, so no pause or resume site can forget it. `IGroupConversationStore.updateIfStateAndPause` writes with state AND pauseId; `GroupHitlCoordinator` uses it for approve, reject, `cancelStored` (so `cancelDiscussion` and `cancelPausedDiscussion`) and the human-turn timeout skip and submit, each bound to the pause it read.

**Design decisions:** a separate string field rather than comparing `pausedAt`, because an `Instant` is stored differently by the two backends while a string compares identically on both. Documents written before the field existed are matched as absent (still state-bound, still atomic) so pauses in flight at upgrade remain decidable; the next write stamps the id. The pause→cancel conversion inside a running leg is unchanged: it acts on the pause that same leg just committed.

**Tests:** coordinator tests per transition (the CAS names the pause that was read and a stale refusal surfaces), store unit tests, and Testcontainers tests on MongoDB and PostgreSQL showing that a decision read before resume + re-pause is refused while the newer pause is untouched.

## fix(hitl,alerts): self-heal the journal TTL index and release digests held by stale rules (2026-11-01)

**Repo:** EDDI (`fix/hitl-alerts-followups`, stacked on `fix/review-engine-hitl-alerts`)

Closes the two items deferred in the HITL/alerts review fixes (`2026-10-31-review-engine-hitl-alerts`).

### What changed and why

- **Journal TTL index self-heals.** During a rolling update an old pod could recreate the unfiltered `idx_journal_ttl_claimed` after a new pod dropped it, silently expiring `EXECUTING` claims again. `IHitlToolJournalStore.reconcileRetention()` (MongoDB: lists the indexes, drops any unfiltered TTL on `claimedAt` or a legacy name with a `WARN`, re-ensures the partial `idx_journal_ttl_completed`) is called by the new `HitlToolJournalMaintenance` scheduled job every `eddi.hitl.tool.journal-reconcile-interval` (`15m`); the constructor still drops the known names at startup. PostgreSQL has no such index (default no-op).
- **Stale-cache digest events are released.** `IAlertEventStore.findDigestPendingRuleIds` (Mongo `distinct`, Postgres `SELECT DISTINCT`) lets `AlertMaintenanceService` release `DIGEST_PENDING` events whose rule is now deleted, disabled or has no digest, so an event created by a replica that still cached the old rule stays in the inbox instead of being held until retention. `AlertMaintenanceService.Result` gained `released`.

### Design decisions

- The reconciliation is a periodic pass over the existing alert maintenance job and a small `@Scheduled` bean for the journal, not a new scheduler or a migration marker: both repairs are idempotent, so every replica may run them.
- The journal job lives in its own bean because the Mongo store is created lazily only on MongoDB; a `@Scheduled` method on the store would instantiate it on PostgreSQL.

## fix(runtime): persist late agent-test charges and fence dead letters behind GDPR erasure (2026-11-01)

**Repo:** EDDI (`fix/runtime-late-charges-erasure`, stacked on `fix/review-engine-runtime`)

The two items the engine-runtime review PR deferred. Each has unit tests that fail without the fix.

### What changed and why

- **Late charges of an abandoned agent-test turn** (`AgentTestRunner`): the terminal record was built from the run's cost at the moment `run()` returned, so a turn that completed afterwards updated only the in-memory total and the reported spend stayed too low. A `LateChargeLedger` now tracks what the terminal record accounted for. Once that record is stored, every further difference (cost, newly seen models) is handed out exactly once and applied to the stored run as an adjustment, and an `AGENT_TEST_LATE_CHARGE` entry carrying just the added cost goes to the audit ledger. Charges that land between building the record and storing it are collected right after the write. A failed adjustment is handed out again with the next charge.
- **Dead letters vs GDPR erasure across nodes** (`ClusterConversationCoordinator`, new `ErasureTombstones`): a node that reconnects between the erasure's shared purge and the deletion of the conversation's snapshot still found the conversation existing and republished its erased dead letter. `purgeDeadLetters(conversationId)` now writes a marker to a shared `ERASED` bucket first; forwarding reads it before publishing (erased: discard), and again after the publish (erased meanwhile: purge the published copy). An unreadable marker defers the entry, as an unreadable conversation store already did.

### Design decisions

- The late-charge adjustment is a compare-and-swap loop on the terminal record's `heartbeatAt`, which no longer means anything once the run is terminal, so it doubles as the version counter. No new store method was needed. The alternative, holding finalisation for abandoned turns, would delay every timed-out run by up to the turn timeout plus the write-back wait.
- The adjustment does not recompute status, cases or `costCeilingReached`: it corrects the figure, not the verdict.
- The marker lives in the coordinator's purge, not in `GdprComplianceService`, so every caller of the purge gets it; if it cannot be written, the shared stream is purged anyway and the failure is reported to the cascade (step `deadLetters`).
- The marker's lifetime is configurable (`eddi.cluster.erasure-marker-ttl`, default `P7D`). It holds only the conversation id as key. Past it, the existing existence check takes over.

## Scheduler keeps claiming due schedules while long fires run (2026-11-01)

**Repo:** EDDI, branch `fix/schedule-claim-cycle` (stacked on #1197)

- `SchedulePollerService.pollDueSchedules()` waited for its whole batch of fires, so with `concurrentExecution = SKIP` one fire running for minutes suppressed every 15-second poll on that instance; schedules that fell due meanwhile (HITL approval deadlines included) waited for the long fire. The poll is now a short claim cycle: it claims due schedules and hands each to a bounded fire executor, then returns.
- New `eddi.schedule.max-concurrent-fires` (default 100) caps fires in flight per instance. A poll takes a slot before claiming, so nothing is claimed that cannot start; the rest stay due.
- Each fire is bounded by its own watchdog (`fire-timeout` plus grace) instead of a shared batch deadline; a timed-out fire is interrupted, counted in `eddi.schedule.fire.timedout`, and gives its slot back even if it ignores the interrupt. The lease invariant (lease > fire-timeout + grace), dead-lettering, `failCount`, expired-claim-as-failed-attempt and the manual-fire path are unchanged.
- Graceful shutdown (`@PreDestroy`): stop claiming, let in-flight fires finish for 5 s, interrupt the rest.
- Tests: a long fire does not block the next poll from claiming another schedule; the in-flight cap holds and slots are returned (also after a lost claim); shutdown drains and cancels; the per-fire timeout frees its slot.
- Docs: `docs/scheduling.md`, `docs/configuration-reference.md`.
