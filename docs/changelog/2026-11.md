## 🐛 fix(cluster): shared state, events, deployments, node identity, signed control plane (2026-11-03)

**Repo:** EDDI (`fix/cluster-shared-state`) — workstream C of the cluster production-readiness
hardening (findings B1–B5, C4 signing part, C6, C15 versioning part, D6 presence part, D7).

### What changed and why

- **B1 — `autoDeploy=false` deployments are recorded.** They existed only as `deployment.changed`
  events, so a lost undeploy, an outbox that delivered an undeploy before its redeploy, or a node
  that joined later left them deployed (or missing — 404 for about 1/N of the requests) on some
  nodes for good. They now live in a `<prefix>_DEPLOYMENTS` KV bucket as `DEPLOYED` or an
  `UNDEPLOYED` tombstone, ordered by the KV revision; the deployment sweep reconciles them like the
  deployment collection, refreshes them (compare-and-set) while they are served and re-creates an
  expired one only when it was confirmed within the TTL. A deployment event is checked against the
  records before it is applied: an undeploy older than a redeploy, or a transient deploy older than
  its tombstone, is dropped. Not in the database, as the review suggested: the record must vanish
  once the whole cluster is gone (that is what "not recorded" means), and a new status value in the
  deployment collection would have broken older nodes that parse it during a rolling upgrade.
- **B2 — events.** A node resyncs once after its first subscription (it subscribes at
  `DeliverPolicy.New`, so whatever was published while it booted with NATS down never arrived),
  and when the event stream was recreated — detected by its creation time (checked every 30 s) or
  by a sequence that goes back — it re-subscribes and resyncs.
- **B3 — cache events.** A read-through fill (`ICache.fill` / `fillIfAbsent`) is no longer
  announced as an eviction; only mutations are. Dispatch runs on two bounded lanes (cache
  evictions vs everything else), so a burst of evictions no longer delays a secret rotation; a
  full lane drops the event and resyncs.
- **B4 — webhook de-duplication fails closed** while NATS is unreachable under
  `eddi.cluster.degraded.nonces=reject` (the default): 503, the sender retries. The docs now list
  the cache TTLs of secrets (5 min), connections (1 min) and global variables (2 min) and no longer
  claim that security state always fails closed.
- **B5.** A GDPR stop waits for the member count it read itself, with its own timeout
  (`eddi.cluster.gdpr-stop-timeout`, 10 s), and the user-id hash travels sealed (AES-GCM, key derived
  from the signing key) on the RPC, on `gdpr.user-erased` and in cache-eviction keys when a signing
  key is set. Audit-position counters that are (re)seeded are counted (`outcome=seeded`).
- **C4 (signing part) — signed control plane.** With `eddi.cluster.signing.key` every node RPC, RPC
  reply and cluster event carries an `Eddi-Sig` header: HMAC-SHA256 over the subject, a timestamp, a
  random nonce and the SHA-256 of the body, compared in constant time. Without a key a WARN is logged
  and nothing changes; `eddi.cluster.signing.required=true` refuses unsigned messages and refuses to
  start without a key. Configuration lives in the new `ClusterSigningConfig`, not `ClusterConfig`.
- **C6 — duplicate node ids.** The presence record is written with compare-and-set; a node whose key
  is held by another boot waits one interval and takes over only a record that stopped changing
  (a crashed predecessor). A live twin stops announcing itself, logs an ERROR, reports
  `eddi_cluster_node_duplicate 1` and its new `cluster-node-identity` readiness check is DOWN.
  Falling back to `eddi.schedule.instance-id` as the node id now logs a WARN.
- **C15 (versioning part).** RPCs and events carry their payload version (`Eddi-V`, event `v`); an
  unversioned message is version 1; a newer one is handled best-effort and counted. Presence records
  carry the payload protocol, and members on mixed versions log a WARN (`eddi_cluster_versions`).
- **D6 (presence part).** Members come from a KV watch on the presence bucket instead of listing it
  and reading every record every few seconds on every node.
- **D7.** The event stream is updated only when its configuration differs, and a cluster-wide
  resync starts after a random delay (`eddi.cluster.events.resync-jitter`, 5 s).

### Threat model of the signing

Who is kept out: anyone who holds the shared NATS credentials (every pod has them) or can read and
write NATS traffic, but not the signing key. Such a party could drain every node, stop a user's
work, undeploy agents or trigger resync storms; with a key, a message must carry a valid HMAC made
with it. A signature is bound to the subject and the body hash, so it cannot be moved to another
operation or payload. Replay is bounded twice: a request older (or further ahead) than
`eddi.cluster.signing.max-age` (60 s) is refused, and within that window a nonce already seen is
refused; an event's window is the event retention plus that, because a reconnecting node
legitimately receives events that old. A reply is bound to the nonce of its request, so an old
answer cannot be passed off as a new one. Not covered: confidentiality (use NATS TLS), the KV and
stream state (per-node NATS permissions, workstream D), flooding NATS, and a holder of the key. The
nonce memory is per node and in memory: a node that restarts inside the window could accept one
replay of a message it had already seen, which the 60 s window keeps short.

### Design decisions

- Rolling upgrade first: unsigned and unversioned messages from older nodes stay accepted unless
  `eddi.cluster.signing.required=true`; a node without a key accepts signed messages it cannot
  check. The three-step order is in [Clustering](../clustering.md#rolling-upgrades).
- The audit-counter margin the review recommends was **not** added: a margin is a gap in the
  conversation's chain, which verification grades `BROKEN`. A re-seed is counted instead, so a
  duplicate position can be attributed.

### Needs from other workstreams

- WS-A: `KvLeaseManager` should not sweep or take over "our earlier boot" leases while
  `ClusterPresence.isDuplicate()` is true (a twin still runs its lease sweeps).
- WS-B: `RestAgentAdministration` keeps calling `announceTransientDeployment`; nothing else needed.

### Review follow-ups

- **The boot sweep waits for presence to confirm the node id.** On a twin's first connect presence
  has not yet told a live twin from a dead predecessor (that takes one interval), so the
  duplicate flag was still down and the sweep deleted the live twin's leases. The sweep, and the
  own-node-id takeover, now need `ClusterView.isNodeIdentityConfirmed()` (this JVM holds its own
  presence record and no twin is flagged); `ClusterPresence.onIdentityConfirmed` re-runs the
  sweep when that happens.
- **A failed event re-subscribe is retried by the periodic stream check**, which resyncs once it
  succeeds. Before, a subscribe that failed after a stream recreation while the connection stayed
  up left the node deaf until the next reconnect.
- **Key rotation and sealed GDPR hashes.** A rotated node also opens hashes sealed with a key in
  `previous-keys`; a node still on the old key cannot open the new key's, so `clustering.md` now
  says to re-run erasures made during the rolling window.
- `eddi-cluster-alerts.yml` gains the `EddiClusterNodeDuplicate` and `EddiClusterSigningRejected`
  rules `metrics.md` already promised. The presence watch drops records past the TTL instead of
  only skipping them, and the signed-event test tampers with the timestamp and the nonce too. Test fixture keys are low-entropy strings (a hex-looking
  key tripped secret scanning).
- **Second round.** A presence takeover needs one full interval of (monotonic) clock time, not
  two writes in a row — a reconnect and a scheduled tick can come milliseconds apart and would
  have confirmed the id over a live twin. A create lost after the own record expired resets the
  own revision, so the node is no longer "confirmed" without a record. The
  `eddi.cluster.signing.rejected` series are registered at zero on a node that can refuse
  anything, so `EddiClusterSigningRejected` fires on the first refusal. A failed subscribe retry
  falls through to the stream check, which recreates a missing stream; a resync the full control
  lane refuses is kept and retried after a second instead of waiting for the next request.

## 🐛 fix(cluster): fence first, never lower the fence, dead-letter what was refused (2026-11-03)

**Repo:** EDDI (`fix/cluster-turn-fencing`)

Workstream B of the cluster production-readiness review (`planning/cluster-production-readiness-review.md`):
the turn path, the conversation stores, HITL resume, dead-letter replay and the admin console.

### What changed and why

- **A3, fence first.** A turn under a cluster lease raised the conversation's `_fence` only *after*
  it had read the state, the revision, a reloaded snapshot and the recorded `Idempotency-Key`s, so an
  expired predecessor could still append in between: the successor then ran without that step, its
  properties overwrote the predecessor's, and a duplicate `Idempotency-Key` could run twice. A failed
  raise was only logged. Now the fence goes up before anything is read, and a turn that cannot raise
  it — or whose lease is already lost — does not run: 409 + `Retry-After`, input not consumed. The
  HITL resume is ordered differently: it reads the snapshot and moves the state `AWAITING_HUMAN` →
  `IN_PROGRESS` on the request thread, and only its queued task raises the fence, before the resumed
  pipeline runs; a resume that cannot raise it does not run and restores the pause.
  `ConversationStepRunnerLeaseTest.raiseFailureDoesNotStopTheTurn` asserted the old behaviour and was
  replaced by `raiseFailureAnswersBusy`.
- **A4, the fence only grows.** A full-document write (Mongo `replaceOne`, Postgres `data = ?`)
  persisted the `_fence` it had loaded. A raise does not move `_rev`, so an unfenced writer that
  loaded before a raise passed the revision guard and put the old fence back, after which the holder
  the raise had shut out could write again. Postgres now builds `_fence` in SQL (`GREATEST` for a
  fenced write, the stored value for an unfenced one); Mongo refuses to write a lower fence and adopts
  the stored one. Documents without `_fence` stay writable. Undo and redo, which ran on the REST
  thread outside the lease, now run through the coordinator in cluster mode, under the lease, with
  its token on their write (single-node undo/redo are unchanged). A turn whose write lost the
  optimistic-concurrency race after its reply had gone out is dead-lettered in cluster mode
  (`reason: conflict`) instead of only logged.
- **A6.** A conditional write (pause commit, resume, undo, redo) refused by the fence returned
  `false`, which every caller read as "a concurrent writer moved the state": the turn was dropped
  without a dead letter. It now throws `ConversationFencedException`; the say path and the resume
  dead-letter it, undo/redo answer 409.
- **A5.** A HITL resume that lost its lease only raised the cancel flag, and nothing then moved the
  conversation off `IN_PROGRESS` until crash recovery minutes later. The pause is now restored at
  once with a fenced compare-and-set (new `IConversationMemoryStore.compareAndSetStateFenced`: only
  while no newer holder has started on the conversation) and the resume is dead-lettered; its caller
  is answered 409.
- **A1 (turn side).** The turn's memory reads `LeaseHandle.isLost()` itself
  (`IConversationMemory.setLeaseLostCheck`), so a lease that can no longer be trusted cancels the
  turn, skips the unfenced long-term user-memory write and answers the reply as not processed, even
  before the lease manager's lost-callback arrives. When `isLost()` turns true is the lease
  workstream's part (`fix/cluster-lease-validity`).
- **A7.** A replay deleted its dead letter as soon as the turn was *queued*, so a replayed turn that
  was then skipped, timed out on the lease or failed lost its input. The entry is now deleted only
  once the replayed turn commits (checked through its `Idempotency-Key`, `dead-letter-replay:<id>`,
  which every replay of one entry carries), the claim is held until then, and the outcome is on the
  activity timeline. With turn idempotency switched off there is no key to look for, and the check
  falls back to "the conversation's revision moved past the one read before the replay" — another
  turn can move it too, so in that mode a deleted entry does not prove the replay itself committed.
  The legacy `POST /administration/coordinator/dead-letters/{id}/replay` goes
  through the same path, so it now claims the entry and is audited with the calling admin.
- **A9.** A turn the runtime refused after its lease was granted was both dead-lettered and answered
  "retry". It is answered busy, and its dead letter is marked `answeredRetry` and cannot be replayed
  (`notReplayableReason: ANSWERED_RETRY`).
- **A11 (group lease).** A discussion whose `g.<id>` lease another live node holds no longer runs a
  second leg here; it stops without writing. Only when no holder can be read (NATS unreachable) does
  a discussion run without its lease. `ClusterHitlRecovery` no longer takes a lease read made while
  NATS is unreachable for "nobody holds it, recover now" (it checks the connection around the read
  until the lease workstream's `peekStrict` is wired in).
- **C4 (receiving side).** A drain request that arrives over RPC is checked again on the node it
  drains: the drain gate must be held, its own `drain.<node>` key written, and another live node must
  still take turns — so a request published straight onto the RPC subject, a broadcast included,
  drains nothing. What a node applies or refuses on another node's request (drain, undrain,
  reconcile, forward) is written to its audit ledger (actor `cluster-rpc`) and activity timeline.
- **D6 (console reads).** One scan of the lease bucket and one read of each dead-letter page is
  shared for 3 s by every console polling this node, and dropped by a force-release, replay, discard
  or forward.
- **C12 (part).** `eddi.cluster.fence.rejected` is registered at startup, so the first rejection on
  a pod is visible to `increase()`.
- **A8, A10 (docs).** `clustering.md` no longer claims "no loss" for degraded turns (conversation
  properties are last-writer-wins), nor that node-local dead letters survive a restart or the
  1000-entry cap.

### Design decisions

- Mongo cannot express `$max` inside a `replaceOne`, so the full write is filtered on "the stored
  fence is not above the one written" and, on a miss caused only by that, adopts the stored fence and
  tries again (at most three times). Only an unfenced write can miss this way.
- Undo/redo go through the coordinator only in cluster mode: that is where the fence exists; on one
  node the state-and-revision CAS already orders them.
- The node-local dead-letter ring (A10) is not persisted to disk here: it lives in the coordinator
  base class, and a durable journal would also have to honour GDPR erasure. The docs now say what it
  does; persisting it is left to the coordinator workstream.

### Review follow-ups

- A resume that lost its lease re-arms the pause's timeout from the **stored** bookmark: the
  resumed pipeline had already cleared the live memory's, so a finite `AUTO_REJECT` /
  `AUTO_APPROVE` / `ABORT` policy was left without a schedule until the next restart.
- A force-release drops the shared lease scan *after* the release, not before, and a scan that
  read the bucket while an invalidation happened is returned but not cached (generation counter),
  so the console does not show a released lease as held for 3 s.
- `clustering.md` no longer calls the group `g.<id>` lease exclusive: the discussion's writes are
  not fenced and a holder that loses the lease is not stopped. The A3 and A7 entries above now
  state the resume's real fencing order and the replay check's fallback without idempotency.

## Log capture starts at boot; unauthenticated reminder is opt-in (2026-11-03)

**Repo:** EDDI, branch `fix/log-capture-at-startup`

**Defect.** `/administration/logs` and `/administration/logs/history` returned nothing on a production instance that had been serving conversations for hours; capture began at the first request to the log API. `BoundedLogStore` was a plain `@ApplicationScoped` bean that registered itself with `LogCaptureFilter` in `@PostConstruct`, but it was only injected by `RestLogAdmin` and `McpConversationTools`, so it was created on first use. Until then `LogCaptureFilter` (which forwards only when a store is registered) fed nothing to the ring buffer, the SSE tail or the DB persistence, and every startup warning was lost from EDDI's own log view after each restart. Console output was never affected.

**Fix.**
- `BoundedLogStore` is now `@Startup`, so the ring buffer, DB flush scheduler and shutdown flush run from application start.
- `LogCaptureFilter` holds records logged before a store exists in a bounded pre-start buffer (1000, newest kept, drops counted) and replays them in order, plus a WARN naming any dropped count, when `setStore` is called. Only redacted text is buffered; a record whose redaction fails is never buffered raw and is still stripped for the console. Console output is unchanged. Javadoc "Bootstrap Safety" updated.
- Docs: `docs/log-administration.md` states capture starts at boot.

**Unauthenticated reminder.** `AuthStartupGuard` logged a WARN `REMINDER: OIDC is DISABLED` every hour for deployments that knowingly set `eddi.security.allow-unauthenticated=true`. It now logs the `[SECURITY]` ERROR once at startup (wording and level unchanged) and the repeat is opt-in through `eddi.security.unauthenticated-reminder-interval` (default `off`; a duration such as `1h` enables it; repeats closer than 5 minutes are throttled). Documented in `application.properties`, `docs/configuration-reference.md`, `docs/security.md`, `docs/troubleshooting.md`, `docs/docker.md`, `docs/architecture.md`.

**Tests.** `LogCaptureFilterPreStartTest` (eager store, ordered replay with MDC, bounded buffer, redaction, fail-closed, live path) and extended `AuthStartupGuardTest`.

**Brand-leak E2E.** With capture running from boot, the Logs page now shows startup records that name the engine, which `brand-leak.fullstack.spec.ts` flagged. Log message and stacktrace text is server output, not product chrome: `LogRow` (Logs page) and the live log viewer mark it `data-log-content`, and the spec's snapshot skips that text and its attributes while still scanning the rest of the page. `docs/white-labeling.md` "Not branded" notes it.

**Review follow-ups.** A plain JUL `LogRecord` with parameters whose message redaction left unchanged was skipped by the pre-start buffer: `LogRecordRedactor` hands back no reusable message for that shape (capture formats it printf-first), and the filter read that as a redaction failure. The filter now formats it with `BoundedLogStore.formatRecord` (now package-private), redacts it with `LogRecordRedactor.rewrite` and buffers it; two tests cover the printf and MessageFormat cases. `docs/architecture.md`'s auth table no longer promises an hourly WARN (it is opt-in), and `docs/log-administration.md` names what the ring buffer (`eddi.logs.buffer-size`), database history (`db-enabled`, `db-persist-min-level`, retention) and the live tail (50 recent entries on connect) keep of startup records. The brand-leak spec gains a server-free `page.setContent` test proving the `data-log-content` exclusion.

## 🔒 fix(deps): minimatch 11.0.4 in Manager and Chat UI — Dependabot #75 and #76 (2026-11-03)

**Repo:** EDDI (`fix/minimatch-dos-alerts`)

Both alerts (minimatch globparts amplification DoS, patched in 11.0.1) were dev-only transitive dependencies
through ESLint and typescript-eslint, which pin `^10`, and in the Manager also through
`@stryker-mutator/core`, which pins `~10.2.4`. A lockfile refresh alone could not reach the fix, so
`ui/manager/package.json` and `ui/chat/package.json` gain an `overrides` entry `"minimatch": "^11.0.1"`, and both
lockfiles resolve to 11.0.4 (new transitive `@isaacs/nonrecursive-glob-match`). The lockfiles were edited by hand
rather than regenerated on Windows, which drops the `libc` and `peer` fields. `npm ci` and ESLint pass in both
packages.

**Decision:** the override is a major bump for tooling only; remove it only once none of ESLint,
typescript-eslint and (Manager only) Stryker selects an affected `minimatch` 10.x range any more.

**Review follow-ups:** the dependency summary and the removal condition now name Stryker, whose `~10.2.4`
range would otherwise bring an affected 10.x back the moment the override is dropped.

## feat(integration): F9 — the cross-feature fixes, MCP tools and Platform Operator for the ten feature PRs (2026-11-03)

**Repo:** EDDI (`feat/operator-mcp-integration`)

The combined follow-up to cost accounting, team handoff, the SERVICE judge, human tie-breaks, human task executors,
tool-call guardrails, edit-on-approve, approval analytics and earned autonomy, approval card context and team
budgets. Those ten PRs deliberately left out what every one of them would have conflicted on — new MCP tools and
the Platform Operator — and wrote down what each needed in `planning/operator-followups/<feature>.md`. This entry is
what was built from those notes, after checking each against the merged code.

### Cross-feature fixes

- **A handoff into a team that cannot pay is refused.** `TeamBudgetHandoffAdmission` is the first
  `HandoffAdmission` bean: the *receiving* team's `TeamBudgetService.decide` (spent, tenant spent, or unreadable
  — fail closed) refuses the handoff with the budget's own sentence, before anything is filed. New refusal surface
  `handoff` on `eddi_team_budget_refusals_total`. See [Team Budgets](../team-budgets.md#what-happens-at-the-cap)
  and [Cross-Team Handoff](../team-handoff.md).
- **A follow-up respects the team ceiling and is charged.** `GroupConversationService.resolveEffectiveCostCeiling`
  ignored `teamBudgetState.ceilingUsd`, so a follow-up on a discussion that had already reached its team's ceiling
  ran one more paid turn; and a follow-up starts no leg, so its spend reached the team only if the discussion was
  ever continued. The ceiling now includes the team's, and `GroupLifecycleOps.followUpWithMember` charges the turn
  as soon as its cost is harvested, as a phase turn does.
- **The SERVICE judge prices from the catalog.** `JudgeCallPricing` was the seam left for the price resolver; it now
  passes the judge's `llmProvider/llmModel` to `ModelPriceResolver`, so a judge without prices of its own is priced
  from the [price catalog](../model-pricing.md) instead of $0. Explicit prices still win.
- **Dashboard.** The HITL row of the Full Metrics Reference had two panels at the same position after the merge
  (approval-context renders and decision latency); the former moved below. The k8s copies are regenerated.
- **Schema version.** `handoffState` and `teamBudgetState` ride `GroupConversation` schema v5 with the tie-break
  fields — recorded in the version comment as decided, valid while the ten ship in one release.
- `GroupConversationService.executeTaskExecutionPhase` keeps its unused `speakers` parameter (the reflection seam
  every phase delegator shares); the reason is now in its Javadoc.

### MCP tools (96 → 108)

Thin wrappers over the in-process REST beans, so every access rule of the REST resource — existence first, VIEW or
EDIT on the group, per-agent oversight scoping, the caller's principal as the recorded actor — applies to the MCP
caller unchanged. Each class checks its tier itself, because an in-process call never passes the HTTP layer's
`@RolesAllowed`; `McpRoleTierParityTest` measures the tiers and compares them with the REST annotations (now also
method-level ones). New tiers in `McpRoles`: `OVERSIGHT` (admin, editor, approver) and `BUDGET_READ` (admin, editor,
viewer). `McpToolUtils.responseJson` turns a resource's `Response` into the tool result, keeping its sentence or code.

| Class | Tools | Tier |
| --- | --- | --- |
| `McpPricingTools` | `read_model_prices(provider?, model?)` | Author (read only — prices are a budget lever) |
| `McpTeamHandoffTools` | `list_team_handoffs`, `accept_team_handoff`, `decline_team_handoff` | Author, then VIEW / EDIT on the group |
| `McpTeamBudgetTools` | `read_team_budget(groupId, historyMonths?)`, `list_team_budgets` | Budget read |
| | `adjust_team_budget`, `transfer_team_budget` | Admin |
| `McpOversightTools` | `summarize_approvals`, `list_autonomy_recommendations`, `get_autonomy_state`, `count_pending_audit_samples` | Oversight |

Not built: a tool to file a handoff or delete a backlog task, any oversight write (never), the per-decision and
sample listings (they carry users' redacted tool arguments), `preview_approval_context` (no render-preview service
method exists) and a separate `get_hitl_decisions` (`summarize_approvals` answers it). The `eddi-admin` Claude Code
skill teaches the new tools (`SKILL.md`, `references/groups.md`, `references/destructive-ops.md`).

**Found on the way:** `RestTeamHandoffs` caught the guard's `io.quarkus.security.ForbiddenException` in its generic
`catch (Exception)` and answered **500** to a caller without access to the group, over REST and MCP alike; its test
threw the JAX-RS `ForbiddenException`, which the guard never throws. It now rethrows the Quarkus exception (403), and

## 🧪 test(cluster): multi-process end-to-end cluster suite, nightly cluster demo, soak and scale harness (2026-11-03)

**Repo:** EDDI (`test/cluster-e2e-evidence`)

### What changed and why

The [cluster readiness review](../../planning/cluster-production-readiness-review.md) (committed with this
branch) found that nothing ran more than one JVM against a real database and a real NATS, with no
fault injection, no soak and no scale test, and that `scripts/cluster-demo` never ran in CI. This
is its Phase 3 ("evidence"), written against the contract of the Phase 1 fixes rather than against
today's behaviour.

- **End-to-end suite** (`src/test/java/ai/labs/eddi/integration/cluster`). `ClusterHarness` starts three
  EDDI processes from the packaged app (the production Dockerfile, as `ContainerBaseIT` builds it), an
  R3 NATS cluster (`--no_advertise`, so clients stay behind the proxy), MongoDB or PostgreSQL, the
  demo's mock LLM, and a Toxiproxy proxy per (EDDI node, NATS server). The 8 scenarios in
  `AbstractClusterE2EIT` cover ordering without faults, latency, a partitioned node in
  `degraded.turns=reject`, NATS replies dropped after the write was applied (A2), a half-open link
  (A1), a holder frozen by SIGSTOP past `lease.ttl` (A1/A6), repeated stream-leader step-downs under
  load (A2/D3), and `kill -9` mid-turn. Each scenario writes JSON evidence to
  `target/cluster-e2e/<db>/`. A scenario that `main` is expected to fail names the finding in its
  title, and its assertions state the contract.
- **`ConversationHistoryChecker`**: a history checker in the style of Knossos and Elle, reduced to the
  ordering contract. It compares client answers, committed history and the LLM's view, and flags
  lost, duplicated, phantom, refused-but-committed, out-of-order (real-time order), overlapping and
  stale-context turns. It has 20 unit tests of its own in `ConversationHistoryCheckerTest`, which run
  in the normal build.
- **Opt-in.** The suite runs only with `-Deddi.cluster.e2e=true`, so `./mvnw verify -DskipITs=false`
  skips it. It runs through surefire, which has no 15-minute fork timeout and no rerun.
- **`.github/workflows/cluster-e2e-nightly.yml`**: the suite on MongoDB and on PostgreSQL, nightly and
  on PRs that touch `engine/cluster/**`. The cluster demo runs nightly on both databases. Results and
  node logs are uploaded as artifacts, with a job summary. The workflow is not a required check.
- **`scripts/cluster-demo/demo.py`**: `--exit-code`, so CI sees a failed scenario, and `--summary-md`,
  for the step summary.
- **`scripts/loadtest/cluster_soak.py`**: `soak` runs chunked steady load for a configurable duration,
  restarting replicas along the way. It samples per-node heap, threads, held leases and open files,
  plus NATS subscriptions and stream and bucket growth, and fits a per-hour slope to each series.

## 🐛 fix(configs,datastore): agent findings for the configuration stores and the datastore (2026-11-03)

**Repo:** EDDI (`fix/agent-findings-configs-datastore`)

Verified the 56 CodeRabbit "agent findings" for `configs/**`, `datastore/mongo`, `datastore/postgres` and
`ui/BrandedOpenApiRoute` against `main`. Many had been closed since the scans, mostly by #1191
(`87f98b7b3`), #1190, #1175, #1173 and #1161. Verdicts: 14 fixed here, 29 already fixed, 5 accepted risk,
8 needing a decision, 0 false positives (two of the already-fixed ones left a gap that is fixed here too).

### What changed and why

**Reference checks.**
- `RestWorkflowStore.addReference` now needs only a host, not a scheme. A scheme-relative
  `//ai.labs.output/outputstore/outputsets/<id>` was skipped, but the engine resolves a step by host and
  id and loaded it anyway.
- A parser document's own `config.uri` is now one of the references `RestParserStore` checks. The
  standalone parse endpoint follows it (`InputParserTask.loadParserDocument`) and uses that parser's
  dictionaries.
- `RestAction` and `RestExpression` (the Manager's action/expression helpers) check VIEW on every rule
  set, API-call set, output set and dictionary they read, not just on the workflow. They pick a store by
  step type and read whatever id `config.uri` spells, relative ones included. A resource the caller
  cannot read contributes nothing.

**Artifact validators (group conversations).**
- A JSON-schema validator is refused at save, and not run at write, when its evaluation is unbounded
  (`ArtifactSchemaComplexity`). The library evaluates every `$ref` separately and reads no clock.
  Measured: 20 `$defs` that each `allOf` the previous one twice took 2 s to save and 3.6 s per artifact
  write, doubling with each further level. A self-`allOf` threw a `StackOverflowError` out of the tool
  call, and two routes to the same property doubled the work per nesting level. The check refuses:
  - an expansion beyond 2000 subschemas;
  - recursion that comes back at the same content location;
  - two recursive routes that do not start with differently named properties.

  Trees and binary trees still pass. A nested `$id` is refused rather than resolved by guesswork.
- `REGEX` validators and schema `pattern`s are run through `BoundedRegex.excessiveRepetition`, the scan
  agent tests already use. A counted repetition of an empty match (`(?:(?:){99999}){99999}`) spins
  without reading input, so the match deadline never saw it.

**JSON Patch.** `ConfigJsonPatcher` masks credentials and judges their relocation by the store's own
read rules. Before, it used the generic redaction rules, while `RestLlmStore`'s read leaves
`tasks[].toolCacheScopes` as it is. A key copied to `toolCacheScopes.apiKey` was accepted as "still
hidden" and then returned in plain text. The LLM and API-call stores pass their `NOT_CONFIGURATION` skip
paths through a new `RestVersionInfo.patch` overload.

**Knowledge bases.**
- A 6.5.0 name-layout knowledge base that changes its `storeType`, or the server it connects to, moves
  to the id layout. The server parameters are `host`, `port`, `database`, `databaseName`,
  `connectionString`, `serverUrl`, `baseUrl` and `tenantName`. On the new backend or server the same
  name maps to that one's default store, which can belong to another legacy knowledge base with the
  same name.
- The standalone endpoints (search, ingest, documents, chunks) apply the deployment rule: the caller
  must belong to every space tenant the configuration's `${vars:<tenant>/…}` / `${vault:<tenant>/…}`
  references name, with variables expanded and connections followed. They build the model and store on
  the spot with the server's authority, and no deployment ever checked them. This adds
  `SpaceReferenceGuard.requireMayUse` and `VaultGrantChecker.referencedTenantsOf`. Docs:
  [RAG](../rag.md).

**Connections.** `ConnectionStore.readByName` reads the live version of each connection. Before, it
read the version the descriptor names. The response filter advances that descriptor only after
`updateConnection` has invalidated the registry, so a lookup in between cached the previous
`allowedHosts` for the registry's one-minute TTL.

**Datastore.** `GridFsAttachmentStore` counts quota usage, and enumerates a conversation's blobs for
erasure, on the primary, like `MongoScheduleStore`'s erasure reads. The client reads `nearest`, so a
lagging secondary undercounted admitted uploads and left committed blobs out of an erasure.

**API description.** `quarkus.http.auth.permission.api-docs.paths` now lists `/openapi.json`, `.yaml`,
`.yml` and their `/q/` forms. Neither `/openapi` nor `/openapi/*` matches them, so the role-gated
document was served to any authenticated token through a suffix URL. Docs:
[security](../security.md), [configuration reference](../configuration-reference.md).

### Design decisions

- **Schema complexity is bounded statically.** networknt offers no hook that runs during evaluation, so
  a budget cannot be enforced while the schema runs. The analysis follows only references inside the
  document. References to other documents are left to the loader, which loads nothing but the bundled
  meta-schemas.
- **Standalone RAG reuses the deployment rule** (`SpaceReferenceGuard`) instead of a second
  tenant-membership check.

### Needs a decision (not changed)

- Descriptor `PATCH` against sharing: the full descriptor is written back, guarded only by the resource
  version, so a concurrent revocation can be undone. Needs a descriptor revision or field-level writes
  on both backends.
- Mongo authorization reads use `nearest`. Moving descriptor reads to the primary affects every
  descriptor read.
- Slack approval records are keyed by the integration's name, not its id.
- A non-admin `duplicateLlm` (or a deep workflow copy) carries plaintext credentials the copier cannot
  read.
- The knowledge-base collision check does not see locations used by older, still-pinned versions.
- Uploads are not fenced against a concurrent conversation erasure (MongoDB and PostgreSQL).

### Follow-up: review findings on the parse path and the connection lookup

- **Standalone parse checks a parser document's `config.uri` per request.** Parser documents saved
  before the save-time check can still name another owner's parser, and `RestSemanticParser` loaded
  them unchecked. The cache entry now records the parser documents `config.uri` named when it was
  built, and every request requires `VIEW` on each of them on the request thread, hit or miss, with the
  same rule `RestParserStore` applies on save. The cache stays shared and the document is still read
  once per cached parser. The parser is now resolved on the request thread instead of the pool thread,
  so that the check has the caller's identity. Not done: a one-off scan or migration of stored legacy
  parsers, and the same per-request check for dictionary references in `extensions`.
- **The connection lookup reads from the primary.** `IResourceStorage.primaryReads()` returns a view
  served by the authoritative copy: on MongoDB the same collections with `ReadPreference.primary()`,
  on PostgreSQL the storage itself. `ConnectionStore` resolves the current version and fetches the
  connection through it, so a lagging secondary cannot hand the registry a connection whose
  `allowedHosts` was just narrowed. Every other store keeps `nearest`. Authorization descriptor reads
  are unchanged and remain the open decision above.

- **Self-conversation check decodes JSON.** The raw-argument fallback compared the serialized arguments with the conversation id; an id written with a JSON unicode escape passed the check and was decoded by the executor. The arguments' string values are now checked after JSON decoding as well (`ToolLoopResumer`, live and resume path).
- **Mistral and Gemini embeddings and the Chroma store re-check their destination per request.** They now use `BoundedJdkHttpClient` with the outbound policy, like OpenAI/Ollama embeddings (DNS rebinding on cached clients).
- **A MongoDB connection string's `proxyHost` is checked** like its seeds — for SSRF and as an `allowedHosts` destination; the driver dials the proxy and sends it `proxyUsername`/`proxyPassword`.
- **An invalid Chroma `apiVersion` no longer echoes its value** (resolved vault references reach this message in RAG search responses and ingestion status).
- Docs: [`security.md`](../security.md) (DNS-rebinding table, cost tracking) and [`secrets-vault.md`](../secrets-vault.md) (`allowedHosts` scope).

### Design decisions

- Fixed-vendor defaults (OpenAI, Anthropic, Mistral … with no endpoint key) stay unchecked against `allowedHosts`, as `secrets-vault.md` documents: the destination is a vendor host, not one the editor controls. Changing that is a contract change (every builder would report its fixed host, and existing secrets whose list omits the vendor host would stop working).
- The per-request re-check is a pre-send check with the documented cache-expiry residual, not address pinning: the JDK client has no resolver hook.

### Needs a decision (not implemented)

- **Jlama loader** (`jlama-core` 0.8.4): header allocation before a bounds check and unchecked shard paths in a downloaded index. Options: an operator allow-list of Hugging Face repositories for `jlama`, waiting for an upstream fix, or disabling `jlama` by default.
- **Elasticsearch (and other) store transports are not closed** when the store cache is invalidated; each secret or variable change followed by a rebuild leaves a live REST client behind. Options: share transports per endpoint/credential like the pooled `MongoClient`s, or close retired stores after a grace period.
- **HITL resume fallback** rebuilds messages from memory (which holds the input as sent) when the paused transcript was omitted, without re-running the task's input guardrails. Options: re-run the input guardrails on the rebuilt messages, or refuse model continuation when the screened transcript cannot be restored.

### What changed and why

The 29 CodeRabbit "agent findings" filed against `modules/llm/tools/**` and `modules/llm/guardrails/**` (scans of 2026-10-26 … 11-02), each re-traced through the current code. Many were already closed by #1160, #1163, #1192 and #1194; the ones still live after those are fixed here:

- **`enableRateLimiting: false` no longer skips the operator's deployment-wide limit.** The flag turned off the whole admission call, so an agent designer's task setting opted out of `eddi.tools.ratelimit.global.*`. It now skips only the task's own per-conversation limit (`ToolRateLimiter.refusedByGlobalLimit`, same bucket, cluster-aware). Documented in [`langchain.md`](../langchain.md) and [`configuration-reference.md`](../configuration-reference.md).

- **An update in `rememberFact` cannot recreate a memory a GDPR erasure just deleted.** Updates go through the update-only compare-and-set `replaceIfUnchanged` first; when that no longer applies, the inserting write runs and counts as an insert, so the existing post-write cancellation check takes it back.

The tolerant reader is now the default mapper, compared number-aware.

## 🔒 fix(secrets): agent-findings pass over the vault, grant checks, redaction and connections (2026-11-03)

**Repo:** EDDI (`fix/agent-findings-secrets-connections`)

### What changed and why

The 45 CodeRabbit "agent findings" filed against the secrets vault, the grant and host checks, the redaction layer and connections were each traced through the current code. Most had already been closed by the October hardening rounds; nine were still real and are fixed here.

- **Space-membership check could miss a tenant** ([`VaultGrantChecker`](../../src/main/java/ai/labs/eddi/secrets/VaultGrantChecker.java)). Tenant discovery used one scanner for `${vault:` and `${vars:`, so a malformed opener of one namespace (`${vars:a${vault:t.finance…/key}`) swallowed a real reference of the other into a single bogus tenant, while the runtime resolved the inner reference with its own rules. Vault tenants now come from a vault-only scanner and variable tenants from `GlobalVariableResolver.VARS_PATTERN`, the grammar the resolver uses (made public for this).
- **Rotation racing a delete** ([`VaultSecretProvider.store`](../../src/main/java/ai/labs/eddi/secrets/impl/VaultSecretProvider.java)). A rotation whose row vanished was turned into a create, and the create checks its endpoint runs had been skipped. The Manager's rotate call, which restates the agent grant but no host list, re-created the key sendable to any host. The rotation now fails and writes nothing.
- **Stale conditional grant edit** ([`RestSecretStore.updateGrant`](../../src/main/java/ai/labs/eddi/secrets/rest/RestSecretStore.java)). With `expectedAllowedAgents` and `allowedHosts` together, the host list was committed before the precondition was checked, so a stale request answered 409 "nothing was written" after it had changed where the key may go. The precondition is now checked before the host write. An edit landing in the moment between that check and the grant write is still refused by the conditional grant write, after the hosts. One atomic operation for both lists would need a new persistence operation on both backends.
- **Linear unresolved-reference check** ([`CredentialReferenceResolver`](../../src/main/java/ai/labs/eddi/connections/CredentialReferenceResolver.java)). The last `find()` over a `[^}]*` reference regex in the area, run on decrypted credential text, was quadratic on unterminated openers. It is replaced by an exact linear equivalent.
- **Read redaction** ([`ConfigSecretRedactor`](../../src/main/java/ai/labs/eddi/secrets/sanitize/ConfigSecretRedactor.java)). A numeric value in an embedded `customHeaders` / `customQueryParams` map is judged like a string. A JSON request body has every literal under a credential-named field masked whatever its length, because the shape scan's eight-character floor left `{"password":"hunter2"}` legible to editors. Only one whole JSON document is re-serialized, never a prefix.
- **Long non-JSON text** ([`SecretRedactionFilter`](../../src/main/java/ai/labs/eddi/secrets/sanitize/SecretRedactionFilter.java)). The 1 MiB bound that assumes a JSON carrier now applies only to text that could be JSON. Text that cannot be JSON keeps apostrophe-quoted passwords whole across an embedded double quote.
- **Export scrubbing** ([`SecretScrubber`](../../src/main/java/ai/labs/eddi/secrets/sanitize/SecretScrubber.java)). The additional query-name rule (`key`, `sig`, …) now also judges the percent-decoded name on both export branches, so `%6Bey=` no longer survives export.

Docs: [`secrets-vault.md`](../secrets-vault.md) (rotation racing a delete, the grant precondition and host lists) and [`security.md`](../security.md) (JSON body masking).

### Verdicts (45 findings)

FIXED 9 · ALREADY_FIXED 27 · ACCEPTED_RISK 6 · NEEDS_DECISION 2 · FALSE_POSITIVE 1.

- **Accepted (documented):** the connections master switch does not stop `${connection:…}` resolution ([`connections.md`](../connections.md)). Unreadable or absent grant metadata is allowed at deploy time, with the grant checked at creation instead, and a deployment racing a secret's creation is a named gap ([`secrets-vault.md`](../secrets-vault.md#what-counts-as-granted)).
- **Open:** whether an OAuth service grant should carry the connection's immutable id, so that a stale configuration minting during a delete and re-create cannot store its token under the successor. And whether GDPR erasure should report the auto-vaulted-secret step incomplete when the vault is disabled (no master key) but secret rows remain.

### Design decisions

- No runtime per-agent grant check was added. `VaultGrantChecker`'s class Javadoc records why resolution time is the wrong place, and the race findings that ask for one are accepted as documented.
- The rotation now prefers "the delete wins" over re-creating the key. A re-create would have to repeat every endpoint check (host list, deployed-agent impact) inside the provider, which knows neither the mode nor the deployments.

## 🐛 fix(cluster): leases stop trusting themselves, survive lost replies, and cost fewer round trips (2026-11-03)

**Repo:** EDDI (`fix/cluster-lease-validity`) — workstream A of the cluster production-readiness review (`planning/cluster-production-readiness-review.md`, findings A1, A2, A11, D1–D5, D7, and the lease part of C12).

### What changed and why

**A1 — a holder cut off from NATS stops itself.** A renewal that could not reach NATS used to be ignored forever (`KvLeaseManagerTest.heartbeatIoFailureKeepsLease` asserted it), so a partitioned holder kept running — LLM calls, tools, the unfenced user-memory upsert, a 200 to its client — after another node had taken the conversation over at `lease.ttl`. A lease is now trusted for `ttl − 2 × heartbeat` (10 s by default) after the last renewal NATS *acknowledged*, counted from when that renewal was *sent*, so the server-side TTL always ends later. Past that `LeaseHandle.isLost()` is true at once and the lost callbacks fire (from the tick every quarter heartbeat, or from `isLost()` itself, on the I/O executor). The test is rewritten to assert the new contract. Contract for the turn side (WS-B): check `isLost()` before the user-memory upsert and before delivering the reply.

**A2 — a write applied on the server whose reply was lost.** Every lease value now carries a lease id (`lid`) unique within the process. A renewal that conflicts re-reads the key from the stream leader: if it still holds this lease (same node, boot and `lid`), an earlier renewal landed although its reply timed out — the lease is kept at the revision found (`eddi_cluster_lease_adopted_total{op="renew"}`) instead of cancelling a healthy turn. An acquire that finds its own `lid` adopts the lease its timed-out create wrote; a lease of this process that nobody here holds (an acquire that gave up) is deleted instead of blocking the conversation for the TTL — this node included. `release()` of a lost handle now still deletes the key when it is provably still this lease.

**A11 — waiter markers and peek.** A granted waiter deletes its `w.<key>` marker by compare-and-set at the revision it wrote, so another node's marker survives; a waiter that times out, is drained or shut down removes its own. New `IConversationLeaseManager.peekStrict` / `peekKeyStrict` throw `ClusterUnavailableException` instead of reading an outage as "no lease" (for `ClusterHitlRecovery.eligible`, owned by WS-B).

**D1 — fewer round trips.** Acquire reads the key's last record (`ISharedKv.latest`, which also returns a delete marker's revision) and writes at that revision: 2 round trips instead of jnats' 3 for a `create` on a deleted key. Release is one guarded delete that returns the marker's revision (`deleteReturningRevision`); the unconditional waiter-marker read and the broadcast are gone. An uncontended turn's lease went from about 6 to 3 round trips; a waiter woken by a release acquires with 1.

**D2 — contention.** The coordinator hands a healthy lease straight to the next turn of the same conversation queued on this node (`IConversationLeaseManager.handOver`: no I/O, refused when less than a heartbeat of validity is left, when another node is known to wait, or after 16 handoffs in a row). The waiter poll is capped at 500 ms (250–750 ms jittered; it was 2.5–7.5 s at the default TTL).

**D3 — reopen storm.** `NatsSharedKv` reopens a bucket handle once, under a lock, for all the callers that failed on it; it never drops a handle younger than 1 s or on a full outgoing queue / closed connection, and a failed open is not retried for 250 ms.

**D4 — heartbeats at scale.** At most 64 renewals in flight, least recently confirmed first; each lease is renewed when 3/4 of a heartbeat has passed since its last renewal, from a tick every quarter heartbeat, so thousands of leases no longer go out in one burst.

**D5 — stale-lease sweep.** Runs once per process (leases of an earlier boot cannot appear after it started), with one watch instead of a read per key — no more whole-bucket scans on every node at every reconnect.

**D7 — release notifications.** A waiter tells the holder's node that it waits (`<root>.lease.to.<nodeId>`, core NATS, repeated with each poll); the holder addresses the release only to those nodes, with the delete marker's revision. The cluster-wide broadcast is kept only for an administrative force-release.

**C12 (lease part).** `eddi_cluster_lease_acquire_seconds` (every outcome × contended), `eddi_cluster_lease_lost_total` (every reason), `eddi_cluster_lease_adopted_total` and `eddi_cluster_degraded_decisions_total{area="turns"}` are registered at construction, so `increase()` sees the first occurrence on each pod.

### Rolling upgrade: why old and new nodes keep mutual exclusion

- **Acquisition stays create-if-absent.** The new acquire is a compare-and-set at the revision of the key's last record, which succeeds only while the key holds no live value — the same server-side check jnats' `create` makes. An old node's `create` and a new node's write race on the one stream leader; exactly one wins. `LeaseProtocolIT.earlierVersionInteroperates` runs both against real NATS.
- **The delete marker is jnats' own.** `deleteReturningRevision` publishes the `KV-Operation: DEL` marker with `Nats-Expected-Last-Subject-Sequence`, exactly as jnats' `delete(key, revision)` does, only keeping the acknowledgement's sequence; old nodes read it as a deleted key.
- **The value only gains a field.** `lid` is ignored by old nodes, which read `node`, `boot` and `since` as before. A new node treats a value without `lid` as somebody else's lease, so it never adopts or deletes an old node's lease as its own.
- **Takeover rules are unchanged** (presence, boot id, three unchanged heartbeats); renewals and releases stay compare-and-set on the revision.
- **Notifications are hints.** Old nodes still broadcast on `lease.released.<key>`, and new nodes still listen there. New nodes no longer broadcast a plain release, so an old node waiting for a lease a new node releases falls back to its poll (`ttl/4`, 5 s by default) until it is upgraded, and a new holder does not see an old waiter's marker when it decides to yield or hand off — fairness toward old-version waiters is weaker for the length of the upgrade. Neither affects mutual exclusion or the fence.

`KvLeaseManagerValidityTest` (A1, A2, A11), `KvLeaseManagerScaleTest` (D1, D2, D4, D5, D7, C12), `NatsSharedKvReopenTest` (D3), two handoff tests in `ClusterConversationCoordinatorTest`, and `LeaseProtocolIT` against a real NATS: the delete-marker round trip, interoperation with an earlier version's jnats `create`/`delete`, a renewal and a create applied on the server whose replies are reported as timeouts, and addressed release notifications with no broadcast. Rewritten: `KvLeaseManagerTest.heartbeatIoFailureKeepsLease` (now `…KeepsLeaseOnlyUntilItsValidityRunsOut`).

assign and time work on agent latencies. A HUMAN member may now **execute** the tasks assigned to them; planning

  groups containing humans stay refused.
- **Surfaces** — the summaries' `pendingKind: TASK` / `pendingTaskId` (from the tie-break PR), a Slack task notice,

## ✨ feat(groups): `tiePolicy: HUMAN_DECIDES` — a named person breaks a tied vote (2026-11-02)

**Repo:** EDDI (`feat/group-human-tiebreak`)

### What changed and why

`HUMAN_DECIDES` was a real enum value that every save refused: a tie that waits on a person needed resume
machinery a finished VOTE phase did not have. It now pauses the discussion until the decider chooses, riding
I6's human-input path rather than the approval path.

```json
"voteConfig": {
  "method": "MAJORITY", "optionsSource": "EXPLICIT", "options": ["Double down on SEO", "Launch the paid pilot"],
  "tiePolicy": "HUMAN_DECIDES",
  "humanTieBreak": { "decider": "founder@acme.com", "timeout": "PT24H", "onTimeout": "MODERATOR_DECIDES" }
}
```

- **Config** — [`HumanTieBreakConfig`](../../src/main/java/ai/labs/eddi/configs/groups/model/HumanTieBreakConfig.java)
  as an eighth `VoteConfig` component (the seven-argument constructor stays). Save time
  ([`GroupGapsValidation`](../../src/main/java/ai/labs/eddi/configs/groups/validation/GroupGapsValidation.java),
  called from `AgentGroupStore.validateVotePhases` in place of the old throw) needs a resolvable decider (named,
  or the single HUMAN member), a positive ISO-8601 timeout, and a moderator for `MODERATOR_DECIDES`.
- **Engine** — `PhaseExecutionEngine.recordVoteDecision` records the NONE tally as before and returns a
  `PendingTieBreak` ([`HumanTieBreakEngine`](../../src/main/java/ai/labs/eddi/engine/internal/groups/HumanTieBreakEngine.java):
  decider, prompt from option texts and totals only, choice matching, decision building).
  `GroupConversationService` pauses on it after the persist and `onPhaseComplete`, after applying a deferred
  `INSERT_VOTE` and dropping a deferred escalation with a note.
  [`GroupTieBreakPauses`](../../src/main/java/ai/labs/eddi/engine/internal/groups/GroupTieBreakPauses.java) commits
  the pause (`speakerIdx = -1`, `RESUME_KIND_TIE_BREAK`, no turn charged), resolves a choice (validated before
  any mutation, CAS out of the pause, rollback on executor refusal) into a `vote+human-tiebreak` VOTE record with
  the losing ballots as dissents, and resumes at the next phase — or pauses for the vote phase's own approval
  gate. Timeouts: `NO_DECISION`, `MODERATOR_DECIDES` (turn- and cost-gated, one turn) or `ABORT` (the plain ABORT
  policy, so the timeout handler needs no change). `GroupHitlCoordinator` dispatches to it from
  `submitHumanInput` and `skipHumanTurnOnTimeout`.
- **Persisted shape** — `PendingHumanInput` gains a `detail`
  ([`HumanRequestDetail`](../../src/main/java/ai/labs/eddi/configs/groups/model/HumanRequestDetail.java): kind, options,
  taskId, transcriptFrom, timeoutResolution); the nine-argument constructor stays. **Schema v5**
  (`GroupConversation.CURRENT_SCHEMA_VERSION`), an identity hop, so an older pod refuses a tie-break pause instead
  of re-running the vote.
- **Surfaces** — REST `HumanInputRequest` gains an optional `choice` (and `content` loses `@NotBlank`; the service
  keeps requiring it for every other kind); MCP `submit_group_human_input` gains an optional `choice`; the REST and
  MCP status summaries add `pendingKind`/`pendingOptions`/`pendingTaskId`
  ([`PendingHumanInputView`](../../src/main/java/ai/labs/eddi/engine/internal/groups/PendingHumanInputView.java)), the
  inbox `PendingApprovalSummary` a `pendingKind`; `HumanInputRequestedEvent` carries the `detail`; Slack posts a
  tie-break notice (still notification-only).
- **Audit and metrics** — one `hitl.approval` entry per resolution: `verdict TIE_BROKEN`,
  `approvalCategory group.vote_tiebreak`, `reasonCode`, options, choice — and no `decisionOutcome`, because a
  tie-break is a human turn. Counter `eddi.group.vote.tiebreaks{policy, resolution}`.
- **Manager** — the phase editor enables HUMAN_DECIDES with decider/timeout/on-timeout fields; the human-turn
  banner's tie-break variant asks for one option plus an optional rationale; the inbox labels tie-breaks. New i18n
  namespace `groupTieBreak` (11 locales).
- **Docs** — new page [Group Human Decisions: Tie-Breaks](../group-human-decisions.md); links from
  [Group Conversations](../group-conversations.md) and [HITL](../hitl.md); the AGENTS.md roadmap row no longer
  lists HUMAN_DECIDES as pending.

### Compatibility

Every other tie policy behaves as before. A document without `detail` is a speaking turn; a pending record's
`onTimeout` is still `SKIP_TURN`/`ABORT`. The schema bump to v5 collides with any other branch that bumps it —
whichever merges second renumbers.

## ✨ feat(groups): per-team monthly budgets — a calendar-month dollar cap per group, metered from the cost ledger, enforced at the gate and inside the run (2026-11-02)

**Repo:** EDDI (`feat/team-budgets`, stacked on `feat/cost-accounting`)

### What changed and why

Several standing teams share one tenant and one monthly cost budget. One busy team could spend the whole month and
leave the others nothing, and nothing said who had spent what. A group can now carry a `teamBudget`; see
[Team Budgets](../team-budgets.md).

- **Config** — [`TeamBudgetConfig`](../../src/main/java/ai/labs/eddi/configs/groups/model/TeamBudgetConfig.java)
  (`monthlyBudgetUsd`, `onExhausted`, `oversight.teams`) on `AgentGroupConfiguration`, validated at save
  ([`TeamBudgetConfigValidator`](../../src/main/java/ai/labs/eddi/configs/groups/TeamBudgetConfigValidator.java), 400),
  and changeable only by `eddi-admin` while `eddi.groups.team-budget.admin-only-edits=true` (default).
- **Store** — one document per `(groupId, UTC month)` in `team_budget_months` (MongoDB and PostgreSQL twins) holding
  spend, the month's cap adjustment, a bounded adjustment history and the applied transfer ids; atomic `$inc` /
  `ON CONFLICT` spend, one conditional update for a debit, 13-month retention.
- **Off when absent** — a group without a `teamBudget` is not metered, gated or ceilinged: no store access, no state on its discussions. `eddi.groups.team-budget.metering-enabled=false` is the global kill switch. Spend before a cap is added is not back-filled.
- **Metering** — [`TeamSpendMeter`](../../src/main/java/ai/labs/eddi/engine/groups/budget/TeamSpendMeter.java) charges
  the increase of the root discussion's `gc.totalCost` after each member turn, each nested roll-up and each leg. A nested
  child charges nothing (its parent pays). Never fails a discussion; an outage is carried to the next charge.
- **Gate** — a new root discussion, a follow-up or a continuation is refused (409) when the team or the tenant has no
  budget left or the budget cannot be read (fail closed); a cadence fire is skipped, or failed when unreadable.
- **Inside a run** — the team ceiling is written in the discussion's `totalCost` terms
  ([`TeamBudgetCeilings`](../../src/main/java/ai/labs/eddi/engine/groups/budget/TeamBudgetCeilings.java)), so the
  existing `maxCostPerDiscussion` checks enforce it unchanged, with the team's policy and its own transcript text.
- **REST** — snapshot, history, batch listing, set this month's cap, idempotent transfers; reads are VIEW-guarded,
  money moves are `eddi-admin`, both write the audit ledger.
- **Template values** — `{context.teamBudget}` and `{context.teamBudgets}` (a board's `oversight.teams`, filtered by
  the discussion owner's view; numbers only).
- **Manager** — a team budget card on the group workspace page (cap/spent/remaining, history), a team table on the Quotas page, and admin-only adjust-this-month and transfer dialogs (transfers send an `Idempotency-Key`); strings in a `teamBudget` namespace in all 11 locales.
- **Metrics** — `eddi_team_budget_{metering,refusals,adjustments}_total`, a Team Budgets dashboard row (the
  Kubernetes copy is synced).

### Design decisions

- The root discussion's group pays; the ledger delta is the charge. The F1 `ISpendSink` feed was evaluated and not
  used: it attributes a nested child's turns to the child's group, carries no root, and fires only for
  tenant-accepted charges, while the in-run ceiling must live in `totalCost` terms.
- The team ceiling excludes its boundary (`Math.nextDown`) so a team at its cap stops instead of taking one more turn.
- One document per team per month (history for a board) rather than the tenant's roll-in-place row.
- 409 for refusals through the existing `GroupDiscussionException` handling; no edits in the hot REST resource.
- Equality exhausts, like the tenant.

### Not done / next

- Deferred to the combined follow-up (`planning/operator-followups/team-budgets.md`): the MCP tools, the Platform
  Operator grants and prompt text, and a `HandoffAdmission` bean that refuses a handoff to a team over budget (after F2).
- The LLM budget-transfer proposal tool was not built in this change.
- GDPR erasure does not yet pseudonymise the admin principal recorded in a month's adjustment history (the audit-ledger
  entry carries it as its user id and is covered by the ledger's own erasure).
- No oversubscription warning (sum of team caps above the tenant budget); `limitedBy` shows the tighter limit.

  ceiling; a state created on a discussion that already spent takes that spend as its baseline (no back-fill).
- `GroupConversation.CURRENT_SCHEMA_VERSION` 4 → 5 for `teamBudgetState`: an older pod re-saving a paused document

## ✨ feat(llm): `toolCallGuardrails` — guardrails on tool-call arguments before execution (2026-11-02)

**Repo:** EDDI (`feat/tool-call-guardrails`)

### What changed and why

An agent designer can now screen the **arguments** of the tool calls a model asks for — the body of a GitHub comment
it is about to post, an e-mail, a handoff brief — with the guardrail types that already screened input and output.
Until now nothing looked at what went *into* a tool: `toolResultGuardrails` governs results, and the approval gate
only asks a human. A public-posting agent needed "never name a prospect", "no PII", "only approved claims" and a
disclosure label enforced before an approver ever saw the call.

```json
"toolCallGuardrails": [
  { "tools": ["mcp:add_issue_comment"], "fields": ["/body"], "type": "regex-filter", "action": "block",
    "parameters": { "patterns": "\\b(acme|globex)\\b" } },
  { "tools": ["mcp:add_issue_comment"], "fields": ["/body"], "type": "disclosure", "action": "redact",
    "parameters": { "text": "— AI-assisted reply" } }
]
```

- **Config** — `LlmConfiguration.Task.toolCallGuardrails`, a list of
  [`ToolCallGuardrailConfig`](../../src/main/java/ai/labs/eddi/modules/llm/model/ToolCallGuardrailConfig.java): a
  guardrail plus `tools` (tool-approval patterns, the same matcher as `toolApprovals`) and `fields` (JSON pointers with
  a `*` segment; `""` the whole arguments; absent = every string). Absent or empty: nothing runs.
- **Phase** — `GuardrailPhase.TOOL_CALL` (`tool_call` in audit keys, metric tags and SSE). Every built-in type opts in:
  `regex-filter`, `pii-redaction`, `max-length`, `prompt-injection`, `judge`, `classifier`, `expression`, `json-object`.
  The judge's `{output}` is the screened field (`GuardrailModelClient.templateData`, one line).
- **New type `disclosure`** ([`DisclosureGuardrail`](../../src/main/java/ai/labs/eddi/modules/llm/guardrails/impl/DisclosureGuardrail.java)) —
  adds a fixed label, idempotently; `redact` only. Runs on output too.
- **Live path** — [`ToolCallGuardrails`](../../src/main/java/ai/labs/eddi/modules/llm/impl/ToolCallGuardrails.java),
  hooked into `ToolLoopRunner` after the call caps and **before** the approval gate. `block` / `reprompt` answer the
  call with a `NOT_EXECUTED` envelope built from configuration and EDDI vocabulary only (the screened text is never
  echoed); `redact` rewrites the call in the model's own message, so transcript, trace, pending batch and tool all see
  the same request. Reprompts are counted per entry per turn from the trace, so a HITL pause does not reset them.
- **Resume** — `ToolLoopResumer` re-screens each approved call, block-only, before the journal claim. Amended calls get

## ✨ feat(llm): cascade judge grades against the request, MCP on the capped client — langchain4j 1.23 follow-ups (2026-11-03)

**Repo:** EDDI (`feat/langchain4j-1-23-adaptations`)

Dependabot moved EDDI to langchain4j 1.23.0 / 1.23.0-beta33 (#1214) with no code change, and CI passed. EDDI
implements no `McpTransport` and uses none of the Jackson 2 MCP methods the release removed (#6824), so nothing
broke. This change adopts what the release made possible, and one lesson from its new Confidence Cascade pattern
(langchain4j#6765).

### What changed and why

- **The `judge_model` cascade judge sees the request.** It was sent only the answer and asked to rate it, so a
  fluent answer to the wrong question scored as well as a right one. langchain4j's cascade grades "does the answer
  fully and correctly address the request?". `ConfidenceEvaluator` now sends the text of the latest user message
  the step's model saw (8,000 characters at most: a single long text keeps its end, where a templated prompt puts the question; with attachments the typed question is kept whole and the head of the attached text fills the rest) together with the
  answer, and asks for the probability that the answer is acceptable for the request. With no user text (an
  image-only message) the judge rates the answer on its own, as before. `CascadingModelExecutor` passes the request
  from both the legacy and the agent-mode step.
- **`modelCascade.acceptanceCriterion`** (optional string): one sentence an acceptable answer must also meet, added
  to the judge's instructions. It is langchain4j's `yesWhen` for the same pattern. Only the judge reads it, so
  `CascadeConfigValidator` warns when it is set without a `judgeModel`. The Manager's cascade editor shows it under
  the judge model editor (all 11 locales).
- **Untrusted text is data, not instructions.** The request and the answer go to the judge as JSON string values
  (Jackson-encoded, so neither can close its field), and the system message tells it to ignore instructions and
  self-reported scores inside them. The author's criterion is trusted config and sits in the system message. The
  docs now say so plainly: this keeps graded text from posing as instructions, but the grade can still be swayed,
  so the cascade is a cost/quality trade-off and not a security boundary.
- **MCP runs on `BoundedJdkHttpClient`.** langchain4j 1.23 made the `StreamableHttpMcpTransport` backend pluggable
  (#6726). The transport now uses EDDI's capped JDK client: a response past `eddi.llm.max-response-bytes` (32 MB)
  fails instead of being read into the heap whole, and the per-request URL re-check against DNS rebinding moved from
  the header hook into the client's request guard, which runs before every send. `followRedirects(false)` stays
  pinned, and `streamingBackpressure(true)` keeps what the transport's own backend set. The cap's error message no
  longer says "LLM provider", since MCP shares it. This puts MCP on the same client as the LLM builders, not on
  `OutboundHttp`: the HTTP client consolidation's Phase 3 (a langchain4j `HttpClient` adapter over `OutboundHttp`) is
  not built yet, and its Vert.x engine is Phase 4. When Phase 3 lands, MCP moves with the builders through this same
  `httpClientBuilder` hook — the hook the October security review noted was missing.
- **Version stamps.** `docs/rag.md`, `InputTypedEmbeddingModelTest` and `VertexGeminiLanguageModelBuilder` named
  1.22. Checked against the 1.23 jars: still only Gemini (and Cohere) declare `INPUT_TYPE`, and the Vertex streaming
  builder still has no `seed`.

### Tests

`ConfidenceEvaluatorJudgeRequestTest` (6): the request and criterion reach the judge, hostile text stays inside its
JSON field, no request means no `request` field, request extraction and its tail truncation.
`CascadingModelExecutorToolReplayTest.judgeSeesRequestAndCriterion` covers the executor wiring.
`McpTransportResponseCapTest` serves a 40 MB handshake answer from a loopback server; it and
`McpTransportRevalidationTest` both fail when the `.httpClientBuilder(...)` line is removed (mutation-checked). In the
Manager, two `task-cascade-section` tests cover editing and clearing the field and hiding it for other strategies.

### Considered, not done

- **Skip the judge on a step that is accepted anyway** (the last step, a null threshold). langchain4j never grades
  its last tier. Here the last step's confidence feeds `audit:confidence`, `cascadeConfidence`, the confidence
  metric and `returnBestAcrossSteps`, so skipping the call would change what those report. That needs its own
  decision.
- **A `decision_model` strategy** on langchain4j's `DecisionModel` (OpenAI Decisions API, Ollama): it returns
  probabilities instead of a number the model writes as text. The API is `@Experimental`, and its token usage goes to
  a `DecisionModelListener`, outside EDDI's cost accounting. Revisit when it stabilises.
- **The agentic layer** (`ConfidenceCascadePlanner`, decision agents, activation conditions) and AiServices-only
  features (tool search strategy, `AiServiceInvocationSummaryEvent`): EDDI's orchestration is config-driven and does
  not use `AiServices`.

## ✨ feat(pricing): correct cost accounting — usage normalization, one price resolution, deployment price catalog, unpriced visibility, strict mode, spend SPI (2026-11-02)

**Repo:** EDDI (`feat/cost-accounting`)

### What changed and why

EDDI's dollar figures — `audit:cost`, every cost ceiling, the tenant's monthly budget, the audit ledger, `/v1`
usage — were only as good as the token counts and prices behind them, and both were off. Anthropic and Bedrock
report prompt-cache reads and writes outside `input_tokens`, so cached prompts cost $0; Gemini reports thinking
outside its output count; the only per-call sum point (`ToolContextBudget.sumTokens`) threw away every provider
field beyond the three base counts; a rolling summary on a cheap model was charged at the task's rates; group
window and stance summaries never reached the tenant budget; and a model with no price on its config was simply
free, with nothing telling anyone. See [Model Pricing](../model-pricing.md).

- **Usage normalization** — the decorators around every chat model
  ([`UsageMetering`](../../src/main/java/ai/labs/eddi/modules/llm/pricing/UsageMetering.java),
  [`UsageNormalizer`](../../src/main/java/ai/labs/eddi/modules/llm/pricing/UsageNormalizer.java)) replace each
  response's usage with a [`MeteredTokenUsage`](../../src/main/java/ai/labs/eddi/modules/llm/pricing/MeteredTokenUsage.java):
  input = all prompt tokens, cache reads/writes kept as subsets, output includes thinking, per-call long-context
  buckets, the pricing model, and the call's price at the catalog entry it matched when it returned. Sums and
  usage-map merges keep every field. `audit:token_usage` gains `cacheReadTokens`/`cacheWriteTokens`.
- **One price resolution** — [`ModelPriceResolver`](../../src/main/java/ai/labs/eddi/modules/llm/pricing/ModelPriceResolver.java):
  config prices, then the task's / cascade step's new optional `pricing` object (cache and long-context prices),
  then the catalog, then fallbacks (cache at the input price, tier at the base price; no price at all is unpriced,
  an explicit `0` is priced). `ModelPrices` and `TokenPricing` delegate to it, so every existing call site gains it.
- **Deployment price catalog** — one CAS-revisioned document (MongoDB `modelpricecatalog`, PostgreSQL
  `model_price_catalog`), `/administration/model-prices` (admin writes; admin/editor read, resolve and unpriced
  sightings), published as a static snapshot every pricing site reads, refreshed every 30 s. Bundled, never-active
  **reference prices** (Anthropic, OpenAI, Gemini list prices as of 2026-11-02, each with its source) for one-click
  adoption in the Manager.
- **Visibility** — `[unpriced-model]` deployment warnings, `audit:pricing` per step (→ `llmDetail.pricing`),
  `eddi.llm.cost.usd`, `eddi.llm.calls.unpriced`, `eddi.llm.pricing.refused`, cache/reasoning token types on
  `eddi.llm.tokens`, catalog gauges, and node-local unpriced sightings.
- **Strict mode** — `unpricedPolicy` `ALLOW` (default) / `REFUSE_WHEN_BUDGETED` / `REFUSE`, never looser than the
  `eddi.llm.pricing.unpriced-policy-floor` property; refused before the call through each caller's existing
  failure path (task fallback with reason `unpriced_model`, failed cascade step, undecided guardrail, truncation
  for group summaries, Dream stops).
- **Spend attribution SPI** — [`ISpendSink`](../../src/main/java/ai/labs/eddi/engine/pricing/ISpendSink.java) /
  [`SpendEvent`](../../src/main/java/ai/labs/eddi/engine/pricing/SpendEvent.java), fired synchronously after each
  accepted tenant charge by `TurnCostMeter` (exactly once per step), `DreamService` and the new
  [`SystemSpendMeter`](../../src/main/java/ai/labs/eddi/engine/pricing/SystemSpendMeter.java), which also charges
  group window and stance summaries to the tenant and admits them against the budget first.
- **Call sites** — summaries and the tool-response summarizer priced at their own model; guardrail, streaming and
  summary usage maps are the metered ones; Dream falls back to the catalog.
- **Manager** — a *Model Prices* page (admin) and a catalog hint plus cache/long-context fields in the LLM task's
  pricing section.

### Design decisions

- No active shipped prices: silently active, code-shipped prices go stale invisibly and an EDDI upgrade would change
  what a tenant is charged. An empty catalog prices exactly as before.
- Static snapshot holder (`ModelPriceCatalogs`) instead of injecting the catalog into the tool loop, cascade executor
  and resumer — every pricing method also has a snapshot-taking overload for tests.
- A provider response metadata subclass (`OpenAiChatResponseMetadata`, …) narrows `tokenUsage()` to its own type, so
  the decorator replaces it with a plain `ChatResponseMetadata` (id, model, finish reason). EDDI reads none of the
  provider-only extras.
- Strict mode never fails a deployment; the warning says the calls will be refused, and the per-call check enforces
  it. Failing deploy would race the catalog load at boot.

### Not done / next

- The MCP tool `read_model_prices` and the Platform Operator grants are deferred to the combined follow-up
  (`planning/operator-followups/cost-accounting.md`).
- Strict mode does not refuse the rolling conversation summary, the tool-response summarizer or the cascade's
  confidence judge yet (they are priced and counted).
- Embeddings are not priced (next gap; the catalog could take `kind: embedding`).
- Summarization retries that failed after consuming tokens stay unpriced.

## ✨ feat(groups): `convergence.judge: "SERVICE"` makes one direct model call (2026-11-02)

**Repo:** EDDI (`feat/group-service-judge`)

### What changed and why

`judge: "SERVICE"` on a phase's `convergence` block used to be accepted, documented and then quietly run as the
moderator agent: the group config carried no model coordinates or credentials for a direct call. A phase can
now name the model in a new `convergence.service` block, and the judge asks it directly — one short call
instead of a full moderator-agent turn, and it works in a group that has no moderator at all.

```json
"convergence": {
  "enabled": true, "minRepeats": 2, "threshold": 0.8, "judge": "SERVICE",
  "service": { "llmProvider": "openai", "llmModel": "gpt-4o-mini",
               "parameters": { "apiKey": "${vault:openai-key}" },
               "inputPricePer1M": 0.15, "outputPricePer1M": 0.60, "timeoutMs": 20000 }
}
```

- **Config** — [`ServiceJudgeConfig`](../../src/main/java/ai/labs/eddi/configs/groups/model/ServiceJudgeConfig.java),
  a sixth component on `ConvergenceConfig` (the five-argument constructor is kept as an overload). Normalized like
  `ContextWindowConfig`/`StanceSummaryConfig`: blank identifiers absent, negative prices unpriced, timeout default
  20 s and ceiling 60 s. The stale Javadoc that said the config "does not carry" provider coordinates is fixed.
- **Engine** — [`ServiceConvergenceJudge`](../../src/main/java/ai/labs/eddi/engine/internal/groups/ServiceConvergenceJudge.java)
  calls `SummarizationService.summarizeWithUsage` with a fixed system instruction and the existing judge prompt
  as the user message (data, never template source), parses it with the same `ConvergenceDetector` parsers, prices
  it through the one-method seam [`JudgeCallPricing`](../../src/main/java/ai/labs/eddi/engine/internal/groups/JudgeCallPricing.java)
  (today `TokenPricing.cost`), books it as `system:judge:<phase>:<repeat>` and announces it with `cost_updated`.
  `PhaseExecutionEngine.runJudge` asks it **before** the no-moderator early return; it is wired by a setter from
  `GroupConversationService`, so no construction site changed. A failure, timeout or unreadable reply is "not
  converged"; the provider's error text never reaches the transcript.
- **Save time** — [`ServiceJudgeValidation`](../../src/main/java/ai/labs/eddi/configs/groups/validation/ServiceJudgeValidation.java),
  one line in `AgentGroupStore.memberAndLimitProblems`: a plaintext credential in `service.parameters`, a
  `${connection:...}` reference (the model registry refuses those) and a half-named provider/model are 400s.
  `SERVICE` without a model and an unknown `judge` value are warnings only, so stored configs keep saving.
- **Vault grants** — [`ServiceJudgeVaultGrants`](../../src/main/java/ai/labs/eddi/configs/groups/validation/ServiceJudgeVaultGrants.java):
  a `${vault:...}` reference in `service.parameters` is refused at group save unless the secret exists and its
  grant contains `"*"` (a group has no agent identity for a narrower grant), and re-checked before the judge
  resolves its parameters; a narrowed grant fails that judge with `outcome=error`, not the discussion.
- **Metrics** — timer `eddi.group.convergence.judge.duration{judge=service, mode, outcome}`.
- **Manager** — the phase editor shows provider, model, API key reference, prices and timeout when Judge is
  Service (`service-judge-fields.tsx`); `normalizeConvergence` carries the block through. New i18n namespace
  `groupServiceJudge` in all 11 locales; the "not yet wired" note is gone.
- **Docs** — new page [Group Convergence Judge: SERVICE](../group-service-judge.md); the convergence paragraph in
  [Group Conversations](../group-conversations.md) now links to it.

### Behaviour of existing configs

Unchanged. `judge: SERVICE` without a `service` model still runs the moderator agent (now counted as
`outcome=fallback_moderator`), and no stored config can fail the new save-time checks because they only read the
new block.

- `JudgeCallPricing` is the seam the cost-accounting work re-points at its central price resolver.

  [`planning/operator-followups/group-service-judge.md`](../../planning/operator-followups/group-service-judge.md).

## ✨ feat(hitl): edit-on-approve everywhere and the HITL decision audit contract (2026-11-02)

**Repo:** EDDI (`feat/hitl-edit-on-approve`)

### What changed and why

An approver can now approve **with an edit**, and every HITL decision is recorded in the audit ledger in one typed
shape that analytics can rely on.

- **Config** — `hitlConfig.review` on agents ([`HitlReviewConfig`](../../src/main/java/ai/labs/eddi/configs/hitl/model/HitlReviewConfig.java))

  [`HitlApprovalAudit`](../../src/main/java/ai/labs/eddi/engine/hitl/audit/HitlApprovalAudit.java) with `schema: 2`:

  [`HitlDecisionValidator`](../../src/main/java/ai/labs/eddi/engine/hitl/review/HitlDecisionValidator.java)
  against `review.reasonCodes` or the built-in vocabulary. `approval-status` lists the vocabulary and the category in

  `review.allowAnswerEdits`. The draft is kept with the pause (also without `onRejection: REVISE`), checked before the
  CAS (not blank, `maxEditChars`, no control characters, a JSON object for a `convertToObject` task), and applied by

  the answer's own output item and data keys, nothing after it, no `postResponse`, no task re-run. Under
  `screenEdits: OUTPUT_GUARDRAILS` the task's output guardrails screen the edit (`reprompt` acts as `block`); a blocked

  `lastEditRefused` on the next pause. `approval-status` serves the redacted draft as `pauseDetails.editableAnswer`.
- **Group edits** — `taskDecisions` on the group approve body (`{verdict, note, editedResult, reasonCode}` per task,
  exclusive with `taskApprovals`) and `decision.editedAnswer` on a PHASE pause after a SYNTHESIS phase, for groups with
  `review.allowResultEdits` ([`GroupReviewEditor`](../../src/main/java/ai/labs/eddi/engine/internal/groups/GroupReviewEditor.java)).
  An edited result replaces `TaskItem.result` (dependents and the summary read it) and is noted in
  `SharedTaskList.reviewerEdits`; a synthesis edit is appended as an unsigned `SYNTHESIS` entry (speaker
  `hitl:<decidedBy>`, `errorReason: "reviewer-edit"`) — signed entries are never rewritten, and the signing guard skips
  reviewer entries.
- **Slack** — approval cards of regular conversations gain "✏️ Edit & approve" and "Reject with reason…"
  ([`SlackHitlEditModal`](../../src/main/java/ai/labs/eddi/integrations/slack/SlackHitlEditModal.java)), opened as

## ✨ feat(groups): native cross-team handoff (2026-11-02)

**Repo:** EDDI (`feat/team-handoff`)

### What changed and why

A standing team could only receive work from a human typing into its backlog. Cross-team handoff lets another team, or a standalone agent, file a task into a team's workspace, under **two-sided consent enforced by code**: the source lists the target (`teamHandoff.targets` on an LLM task, `handoffConfig.targets` on a group) and the target lists the source (`handoffConfig.accept.from`, `agent:<id>` or `group:<id>`, exact ids). Nothing else changes by default: every new field is absent-means-off, and old stored or imported configs and workspaces behave exactly as before.

- **One pipeline.** `TeamHandoffService.file` is the only code that writes to another team's workspace. It checks consent against the target's *current* config, refuses self-handoff, cycles and the hop limit (`eddi.groups.handoff.max-hops`, default 3), cleans the text, reserves a per-run and two per-UTC-day slots (the `toolQuotas` store, so atomic across pods), asks any `HandoffAdmission` bean, then writes through the workspace compare-and-set, re-validating duplicates, decline tombstones and capacity on every retry. A refused attempt gives its slots back.
- **Two entry points.** A `handoff_to_team` tool whose `team` argument is an enum of the aliases the source declared (new approval source `team`), and deterministic `handoffConfig.onDecision` rules that file a task when a discussion completes with a matching `VOTE`/`VERDICT`/`AGREEMENT`/`AWARD`, with an idempotent dedupe key per discussion, round and rule.
- **AUTO vs REVIEW.** REVIEW (the default) puts the item in an intake inbox that is in no task list, so a cadence can never pull it; a human with EDIT accepts (optionally edited) or declines it. Both write an audit entry in the shared approval vocabulary (`team_handoff_intake`, `APPROVED | APPROVED_EDITED | REJECTED`, `reasonCode`).
- **Lineage and provenance.** The origin of a handed-off task lives in a side map keyed by task id, and the cadence stamps the lineage of the tasks it pulled onto the discussion, so A to B to A is caught across discussions. A handed-off task is marked in the cadence question as a request to evaluate, not instructions.
- **New REST** under `/groupstore/groups/{groupId}/workspace`: `GET /handoffs`, `POST /handoffs/{id}/accept`, `POST /handoffs/{id}/decline`, and `DELETE /backlog/{taskId}` (the 200-task backlog had no way to shrink; handoff makes the ceiling reachable). Manager: an Intake section and an origin badge on the workspace page, a handoff section in the group advanced editor.
- `team` is added to the known HITL tool sources and to the tool-cache side-effecting sources (a cached result must never stand in for a write). SSE gets a `team_handoff` event; metrics `eddi_team_handoff_*`.

Not built here: new MCP tools for the intake (the service methods are public and web-free for thin wrappers), and the Platform Operator update, both listed in `planning/operator-followups/team-handoff.md`.

**Rolling upgrade caveat:** an older pod that re-saves a workspace drops the unknown `handoffs` field, losing pending inbox items and origins (same as `reworkCounts`); the audit entries hold the subject and source for recovery.

## ✨ feat(llm): `toolQuotas` — per-subject, per-window caps on tool calls (2026-11-02)

**Repo:** EDDI (`feat/tool-quotas`)

### What changed and why

An agent designer can now cap how often one **subject** — normally the end user — may make a tool run within a
time window, counted **across conversations and across nodes**: "at most 100 content improvements per user per
day". Until now EDDI had a per-tool-per-minute rate limit per conversation (`toolRateLimits`), a per-conversation
budget that a new conversation resets (`maxBudgetPerConversation`) and per-tenant quotas — none of them is per
user per day.

```json
"toolQuotas": {
  "subject": "{context.personId}",
  "tools": {
    "updateAction":        { "limit": 100, "window": "P1D", "pool": "improvements" },
    "updateSession":       { "limit": 100, "window": "P1D", "pool": "improvements" },
    "generateActionImage": { "limit": 30,  "window": "P1D" }
  }
}
```

- **Config** — `LlmConfiguration.Task.toolQuotas` ([`ToolQuotaConfig`](../../src/main/java/ai/labs/eddi/modules/llm/model/ToolQuotaConfig.java)).
  Keys are tool names with the same matching as `toolRateLimits` (dispatch name wins over slug) and work for every
  tool source, HTTP-call tools included. Tools of one `pool` share one counter. Validated at save time
  ([`ToolQuotaConfigValidator`](../../src/main/java/ai/labs/eddi/modules/llm/tools/quota/ToolQuotaConfigValidator.java),
  wired into `LlmStore` like the `toolApprovals` check, so it is a 400): `limit` a positive integer, `window` an
  ISO-8601 duration from `PT1M` to `P31D`, every rule of a pool states the same limit and window. Windows are fixed
  and aligned to the UTC epoch (`P1D` resets at 00:00 UTC).
- **Subject** — an optional template rendered with the turn's template data; default is the conversation's user id.
  Managed conversations use composite user ids (`<user>-<company>-<program>`), so the default counts per program and
  the template is how a deployment counts per person. A blank render falls back to the user id, a caller with no user
  id is capped per conversation, a subject over 256 characters becomes a prefix plus a digest, and the subject is only
  ever logged as a short digest.
- **Counts real executions only.** The reservation is made in one place, `ToolExecutionService.executeToolWrapped`,
  after the rate limit and the cache and immediately before the tool runs (`ToolQuotaGate.reserve`). Cache hits,
  rate-limited calls, calls refused by the conversation or tenant budget, rejected approvals and calls that never ran
  are never counted. A failed call gives its reservation back (`ToolQuotaGate.settle`): an exception, a tool-reported
  error, an HTTP non-2xx or transport failure — judged by the same `ToolOutcomeClassifier` the repeat guard uses. A
  **timed-out** call keeps its count, because the abandoned worker cannot be stopped and may still finish the side
  effect.
- **Atomic, no overshoot, multi-node.** A new counter store, `IToolQuotaStore`, with a MongoDB implementation
  (`findOneAndUpdate` with a `count < limit` filter and upsert; the duplicate-key race on the window's first insert is
  retried as a conditional update; TTL index on `expiresAt`) and a PostgreSQL one (`INSERT … ON CONFLICT DO UPDATE …
  WHERE used < ? RETURNING used`; an hourly sweep removes expired rows). Selected in `DataStoreProducers` like the other
  stores. With three calls left, a batch of five parallel calls runs exactly three.
- **Refusal** is a tool result the model sees, a final `NOT_EXECUTED` envelope with the limit and the reset time
  ("Not run: the daily limit for this tool (100) is reached; it resets at 2026-11-03T00:00:00Z …"), not a thrown error;
  the turn carries on and the model is not invited to retry.
- **Human approval.** Approved calls run on the resume path through the same `ToolLoopRunner.executeToolCall` →
  `executeToolWrapped` pipeline as live calls, so the quota is applied (and counted) at execution time there too. A
  gated call proposed while its quota is already exhausted is refused immediately by a read-only pre-check
  (`ToolLoopRunner.refuseExhaustedGatedCalls`, before the pause is built), so a human is never asked to approve what
  will then be refused; pausing counts nothing.
- **Fails closed.** If the store cannot answer, a stored rule cannot be applied or the subject template fails to
  render, the call is not run and the model is told the limit could not be checked. One WARN a minute with agent,
  conversation and a digest of the user id; every failure is counted.
- **Metrics** — `eddi.tool.quota.decisions{tool, outcome}` (`allowed`, `refused`, `precheck_refused`, `unavailable`,
  `released`) and `eddi.tool.quota.store.failures{operation}`; documented in `docs/metrics.md` and charted on the Full
  Metrics Reference dashboard.
- **GDPR** — counters are keyed by a user identifier, so
  [`ToolQuotaGdprParticipant`](../../src/main/java/ai/labs/eddi/modules/llm/tools/quota/ToolQuotaGdprParticipant.java)
  joins the erasure cascade (delete by subject) and the export (the user's counters). If a deployment's subject
  template derives an identifier other than the conversation's user id, erasure deletes the counters whose subject
  equals the erased user id; counters hold counts only and expire an hour after their window ends.

### Design decisions

- The reservation sits inside `executeToolWrapped`, not in `ToolLoopRunner` around the supplier: only there is it after
  the cache check, and a refusal returned from inside the supplier would have been cached and charged as a result.
- A rule keyed by a slug is one counter for all of that tool's operations (unlike the per-dispatch-name rate-limit
  bucket), because "30 web searches a day" is naturally per tool; `pool` is the explicit way to share across tools.
- Pre-check only refuses an *already exhausted* quota; it does not reserve slots for pending approvals.
- A call with no quota rule takes exactly the old 10-argument `executeToolWrapped` path.

### What's next / not done

- The Manager has no form for `toolQuotas` yet; its LLM task editor spreads the task object on save, so a configured `toolQuotas` is preserved.

## Group HITL transitions are bound to their pause with a multi-field CAS (2026-11-01)

Repo: EDDI, branch `fix/groups-pause-cas` (stacked on #1188).

**Problem:** the group approve, reject, cancel and human-turn timeout-skip writes compared only `state` in their compare-and-set. A resume followed by a re-pause between the read and the write (ABA) left the state `AWAITING_APPROVAL` / `AWAITING_HUMAN_INPUT` again, so a stale decision could act on a newer pause it never saw. The in-memory pause-id checks narrowed the window but could not close it.

**Change:**
- `IResourceStorage.storeIfFieldsEqual(resource, Map)` — an atomic conjunctive conditional write (a `null` expected value means "absent"), implemented in `MongoResourceStorage` (one `replaceOne` filter) and `PostgresResourceStorage` (one `UPDATE ... WHERE a = ? AND b = ?`), with the same 404/409 zero-match distinction as the single-field CAS.
- `GroupConversation.pauseId` is persisted next to `pausedAt` and kept in lockstep by `setPausedAt`, so no pause or resume site can forget it. `IGroupConversationStore.updateIfStateAndPause` writes with state AND pauseId; `GroupHitlCoordinator` uses it for approve, reject, `cancelStored` (so `cancelDiscussion` and `cancelPausedDiscussion`) and the human-turn timeout skip and submit, each bound to the pause it read.

**Design decisions:** a separate string field rather than comparing `pausedAt`, because an `Instant` is stored differently by the two backends while a string compares identically on both. Documents written before the field existed are matched as absent (still state-bound, still atomic) so pauses in flight at upgrade remain decidable; the next write stamps the id. The pause→cancel conversion inside a running leg is unchanged: it acts on the pause that same leg just committed.

**Tests:** coordinator tests per transition (the CAS names the pause that was read and a stale refusal surfaces), store unit tests, and Testcontainers tests on MongoDB and PostgreSQL showing that a decision read before resume + re-pause is refused while the newer pause is untouched.

## fix(hitl,alerts): self-heal the journal TTL index and release digests held by stale rules (2026-11-01)

**Repo:** EDDI (`fix/hitl-alerts-followups`, stacked on `fix/review-engine-hitl-alerts`)

Closes the two items deferred in the HITL/alerts review fixes (`2026-10-31-review-engine-hitl-alerts`).

### What changed and why

- **Journal TTL index self-heals.** During a rolling update an old pod could recreate the unfiltered `idx_journal_ttl_claimed` after a new pod dropped it, silently expiring `EXECUTING` claims again. `IHitlToolJournalStore.reconcileRetention()` (MongoDB: lists the indexes, drops any unfiltered TTL on `claimedAt` or a legacy name with a `WARN`, re-ensures the partial `idx_journal_ttl_completed`) is called by the new `HitlToolJournalMaintenance` scheduled job every `eddi.hitl.tool.journal-reconcile-interval` (`15m`); the constructor still drops the known names at startup. PostgreSQL has no such index (default no-op).
- **Stale-cache digest events are released.** `IAlertEventStore.findDigestPendingRuleIds` (Mongo `distinct`, Postgres `SELECT DISTINCT`) lets `AlertMaintenanceService` release `DIGEST_PENDING` events whose rule is now deleted, disabled or has no digest, so an event created by a replica that still cached the old rule stays in the inbox instead of being held until retention. `AlertMaintenanceService.Result` gained `released`.

### Design decisions

- The reconciliation is a periodic pass over the existing alert maintenance job and a small `@Scheduled` bean for the journal, not a new scheduler or a migration marker: both repairs are idempotent, so every replica may run them.
- The journal job lives in its own bean because the Mongo store is created lazily only on MongoDB; a `@Scheduled` method on the store would instantiate it on PostgreSQL.

## fix(runtime): persist late agent-test charges and fence dead letters behind GDPR erasure (2026-11-01)

**Repo:** EDDI (`fix/runtime-late-charges-erasure`, stacked on `fix/review-engine-runtime`)

The two items the engine-runtime review PR deferred. Each has unit tests that fail without the fix.

### What changed and why

- **Late charges of an abandoned agent-test turn** (`AgentTestRunner`): the terminal record was built from the run's cost at the moment `run()` returned, so a turn that completed afterwards updated only the in-memory total and the reported spend stayed too low. A `LateChargeLedger` now tracks what the terminal record accounted for. Once that record is stored, every further difference (cost, newly seen models) is handed out exactly once and applied to the stored run as an adjustment, and an `AGENT_TEST_LATE_CHARGE` entry carrying just the added cost goes to the audit ledger. Charges that land between building the record and storing it are collected right after the write. A failed adjustment is handed out again with the next charge.
- **Dead letters vs GDPR erasure across nodes** (`ClusterConversationCoordinator`, new `ErasureTombstones`): a node that reconnects between the erasure's shared purge and the deletion of the conversation's snapshot still found the conversation existing and republished its erased dead letter. `purgeDeadLetters(conversationId)` now writes a marker to a shared `ERASED` bucket first; forwarding reads it before publishing (erased: discard), and again after the publish (erased meanwhile: purge the published copy). An unreadable marker defers the entry, as an unreadable conversation store already did.

### Design decisions

- The late-charge adjustment is a compare-and-swap loop on the terminal record's `heartbeatAt`, which no longer means anything once the run is terminal, so it doubles as the version counter. No new store method was needed. The alternative, holding finalisation for abandoned turns, would delay every timed-out run by up to the turn timeout plus the write-back wait.
- The adjustment does not recompute status, cases or `costCeilingReached`: it corrects the figure, not the verdict.
- The marker lives in the coordinator's purge, not in `GdprComplianceService`, so every caller of the purge gets it; if it cannot be written, the shared stream is purged anyway and the failure is reported to the cascade (step `deadLetters`).
- The marker's lifetime is configurable (`eddi.cluster.erasure-marker-ttl`, default `P7D`). It holds only the conversation id as key. Past it, the existing existence check takes over.

## Scheduler keeps claiming due schedules while long fires run (2026-11-01)

**Repo:** EDDI, branch `fix/schedule-claim-cycle` (stacked on #1197)

- `SchedulePollerService.pollDueSchedules()` waited for its whole batch of fires, so with `concurrentExecution = SKIP` one fire running for minutes suppressed every 15-second poll on that instance; schedules that fell due meanwhile (HITL approval deadlines included) waited for the long fire. The poll is now a short claim cycle: it claims due schedules and hands each to a bounded fire executor, then returns.
- New `eddi.schedule.max-concurrent-fires` (default 100) caps fires in flight per instance. A poll takes a slot before claiming, so nothing is claimed that cannot start; the rest stay due.
- Each fire is bounded by its own watchdog (`fire-timeout` plus grace) instead of a shared batch deadline; a timed-out fire is interrupted, counted in `eddi.schedule.fire.timedout`, and gives its slot back even if it ignores the interrupt. The lease invariant (lease > fire-timeout + grace), dead-lettering, `failCount`, expired-claim-as-failed-attempt and the manual-fire path are unchanged.
- Graceful shutdown (`@PreDestroy`): stop claiming, let in-flight fires finish for 5 s, interrupt the rest.
- Tests: a long fire does not block the next poll from claiming another schedule; the in-flight cap holds and slots are returned (also after a lost claim); shutdown drains and cancels; the per-fire timeout frees its slot.
- Docs: `docs/scheduling.md`, `docs/configuration-reference.md`.
