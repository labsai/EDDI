# Throughput collapses under a burst — 2026-10-19

On 2026-10-18 a few load-test runs collapsed while the rest of the same configuration ran normally:
62 instead of about 290 turns/s for a 1,500-limit burst, and 137 instead of about 240 turns/s in
`steady` (`admission-2026-10-17.md` on PR #1085, "Static, CPU-sized in-flight limit"). They clustered in
one quarter of an hour. This investigation reproduced the collapse and looked for its cause.

Stack as before: `labsai/eddi:6.5.0` with a local build of PR #1085 mounted, `-Xmx6g`, 8 GB container,
MongoDB 7.0.43 (standalone, as the harness runs it), 3 s mock LLM, burst to 5,000 users with
`--retry-503 10`, `down -v` before every run. Instrumentation, added outside the harness: a per-second
`/q/metrics` and `docker stats` sampler, GC and safepoint logs, a JFR recording, mongod's slow-operation
log and `serverStatus` journal counters, all saved before `down -v`.

## Host contention triggers the collapse; how far throughput falls is EDDI's

On 2026-10-19 the laptop was busy before any run started: total CPU 40–80 % with the stack idle,
including an antivirus service at about 3.3 cores, browsers, an IDE and WSL. Every 1,500-limit burst
collapsed, four with instrumentation (50, 0, 0 and 0 turns/s) and one without (0 turns/s). JFR is not the
cause. The physical disk was idle (0.1–0.2 ms per write, 1–4 MB/s). The harness's k6 check does not
see contention of this kind.

The 2026-10-18 collapses probably had the same cause, but that is a hypothesis, not a measurement. On
that day a host CPU sampler ran only from 12:16. It showed 2–4 cores going to processes outside Docker
at a steady level. The two worst runs (12:08 and 12:12) came before it started, so no host telemetry
covers them. What supports the hypothesis: the slow runs clustered in one quarter of an hour across
two limits (1,500 and `auto`), and every run started on a fresh stack.

Losing part of the CPU should cut throughput in proportion. It cut it to zero, so the cause was traced
inside EDDI.

## Where the time went

| Finding | Evidence |
|---|---|
| A capped node spends most of its CPU on work other than turns | JFR, 5,000-user burst, EDDI held to 2 CPUs (`LOADTEST_EDDI_CPUS=2`), limit 150: turn execution 17 % of CPU samples, conversation starts 19 %, the Vert.x event loop 27 % |
| Refused starts did reads before being refused | `startConversationWithContext` ran the access check, user resolution, the GDPR restriction read and the agent lookup before `admitTurn` refused the start. Each refused client returns after `Retry-After` (6,261 refused starts in one run). Fixed on PR #1085 |
| Every audit entry read the vault for a signing key that does not exist | `AuditLedgerService` signs each entry with the agent's Ed25519 key, on the turn's thread. Agents almost never have one (`generateKeyPair` has no production caller), so each entry paid a vault query and threw three exceptions (about 8,000 each in one run). The miss is now remembered for 60 s: on `main` since #1055, which landed the same cache independently. PR #1098 moves the audit ledger to `signIfKeyPresent`, so a remembered miss throws nothing either |
| Writes wait for the journal | mongod logged 1,849 slow operations in one run, nearly all inserts and updates that examined 0 documents. 94 % of their time was `waitForWriteConcernDurationMillis`: `w: majority` on a standalone mongod waits for a journal sync |
| Turns park on the connection pool | In the stall window, virtual threads were parked mostly in pool checkout (`MongoResourceStorage.read`, the conversation-memory load). MongoDB socket reads averaged about 0.4 s |
| A cold JVM pins its carriers | In the first 30 s of a burst, class loading from the runner jar pinned carrier threads 1,002 times (70 s in all) |
| The capped runs do not depend on the limit | At 2 CPUs, limits of 1,500, 600 and 150 all collapsed (1.3, 0 and 1.8 turns/s). With 150 in flight, the median turn still took 91 s |

The capped runs reject the idea that only too many turns in flight cause the collapse. With a limit of
150 there is no long queue, yet the CPU goes to handling requests that are refused and come back:
refused starts, the HTTP event loop, and the per-entry vault reads inside every turn. A lower in-flight
limit cannot fix that, because the refused work happens outside the turn.

## Database operations per turn, before and after the missing-key cache

`loadtest.py gate` (PR #1086), 10 conversations × 10 turns, deterministic counters, measured with this
investigation's own version of the cache. #1055 landed an equivalent one on `main`, together with its
other round-trip cuts:

| Counter | `main` (recorded in `db-ops-mongo.json`) | With the fix |
|---|---|---|
| `secretvault_secrets` queries per turn | 3.0 | **0** |
| All queries per turn | 17.5 | 13.96 |
| Total operations per turn | about 23 | 19.88 |

All 100 turns succeeded with both builds, and the gate passed. When #1086 lands, its
`secretvault_secrets` ceiling (3.3) can come down with `gate --record`.

## Not fixed here (follow-ups)

- **The turn timeout did not fire under saturation.** At 2 CPUs and a limit of 1,500, the median turn
  took 113 s, yet no request got the 408 that `RestAgentEngine` sets at `systemRuntime.agentTimeoutInSeconds`
  (60 s). The timeout handler apparently needs the same saturated event loop.
- **`/q/metrics` stops answering under a burst.** It timed out (5 s) for about 110 s while turns were
  still completing, so the dashboards go blind when they are needed most.
- **Turns whose caller has gone still run.** Without an agent `turnDeadlineMs` or the caller's
  `X-EDDI-Turn-Deadline-Ms`, a queued turn that reaches execution after its caller got the 408 runs in
  full: database work and the LLM call.
- **The harness runs mongod standalone**, so `w: majority` means a journal sync per write. A replica set
  behaves differently, and the harness may overstate write latency.

Raw data (timelines, GC logs, JFR recordings, mongod logs) is in the measuring session's scratch
directory, not committed.
