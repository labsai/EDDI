## Findings

- **The ~200-turn ceiling is confirmed (WS2).** `eddi_runtime_executor_max_threads{pool="managed"}` is
  200; at 500 conversations `active{pool="managed"}` stays pinned at 199 while 150–200 turns wait in
  `queued{pool="managed"}`. Throughput flattens at ≈ 61 turns/s ≈ 200 threads / 3.25 s per turn, and p50
  more than doubles (3.1 s → 7.5 s), because each turn waits for a thread first.
- **Overload shows up as latency, not as rejections.** No 503 at 500 conversations: the managed queue is
  unbounded and `eddi.coordinator.max-active-conversations` (10000) is far above the thread ceiling. A
  client with a timeout below about 12 s would see failures here, not a clean `capacity_exceeded`.
- **About 23 MongoDB operations per turn**, and the count does not change with load: 17.5 queries,
  2.0 updates, 3.2 inserts. Per collection, per turn:
  `descriptors` 6.1 queries + 1 update (WS3c `updateTimeStamp`, plus the ownership checks), `conversationmemories`
  5.0 queries + 1 update (WS3a double load, `getRevision`, state), `secretvault_secrets` 3.0 queries,
  `usermemories` 1.2, `agents` 1.0, `audit_ledger` 1.1. `workflows` is only 0.03: back-to-back turns land
  inside `WorkflowTraversal`'s 2 s TTL, so this scenario **understates WS1**; with human think time (> 2 s)
  every LLM turn misses the cache. Re-measure WS1 with `--think-ms 3000`.
- **Audit queue:** peak depth about 600 of 100000, nothing dropped.
- **Unexplained, worth a look:** 3 vault reads per turn even though the agent's API key is set once. The
  plan says resolved secrets are cached (§3), so either those reads are something else (grants, metadata)
  or that claim needs checking.

Not measured yet: `burst`, `same-conversation` and `long-conversation`, plus the 1000-conversation point
WS2's acceptance criterion needs (the container memory would have to grow too).
